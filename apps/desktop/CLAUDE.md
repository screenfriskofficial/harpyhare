# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**harpyhare** — a Tauri 2 desktop app для **macOS 14.2+ и Windows 10 версии 2004+** (процесс маскируется под «Audio System», бренд `harpyhare` — только в UI). Hold a push-to-talk key → capture **system audio** (e.g. voice from a video) → transcribe via Groq Whisper or OpenAI gpt-4o-mini-transcribe (переключаемый провайдер) → edit the text (with pasted screenshots) → stream an answer from the Anthropic API.

**Окон два, и это главное, что надо знать про структуру фронта.** Приложение стартует с **лаунчера** (`launcher.html` → `src/launcher.tsx` → `features/launcher/LauncherApp`) — обычное центрированное окно с настройками, библиотекой контекстов, масками и кнопкой «Запустить». HUD (`index.html` → `src/main.tsx` → `src/App.tsx`) — плавающее фреймлесс always-on-top окно — **создаётся по требованию** командой `launch_main_window` и уничтожается `stop_main_window` (кнопка в шапке HUD возвращает в лаунчер). Оба входа собираются одним Vite-конфигом (`build.rollupOptions.input: {main, launcher}`), делят `src/lib`, `src/ipc`, `src/hooks` и `src/components/ui`, но НЕ делят состояние: у каждого окна свой React-рут и свой стор. Бутстрап рута общий — `render-root.renderWindowRoot` (`src/render-root.tsx`, не `lib/`: тот слой framework-free; поиск `#root` + StrictMode + `QueryClientProvider`), поэтому `main.tsx`/`launcher.tsx` — по три строки; третий вход заводится через него же, а не копией.

Следствия, которые легко нарушить: (1) **`tauri.conf.json` не описывает ни одного окна** (`"windows": []`) — оба создаются кодом (`window::create_launcher_window` из `setup_app`, `window::create_main_window` из `launch_main_window`), поэтому размеры и флаги (`transparent`/`decorations`/`alwaysOnTop`/`contentProtected`/`shadow`) задаются там, а не в конфиге; обе функции принимают `&Settings` параметром, а защита контента ставится ОДИН раз флагом билдера `.content_protected(...)` — пост-билд повторный вызов удалён, `window::apply_content_protection_all` остался только для смены настройки на лету и проходит по обоим окнам; (2) глобальные хоткеи регистрируются на `launch_main_window` и снимаются на `stop_main_window` — в лаунчере их нет; (3) готовность (ключи API + разрешение на запись звука) проверяется в лаунчере (`useLauncherReadiness`), а не в HUD — HUD запускается уже готовым.

Two halves: a **Rust backend** (`src-tauri/src/`) and a **React 19 frontend** (`src/`). The backend does all the privileged/native work; the frontend is pure UI over a typed IPC boundary.

Живёт в `apps/desktop/` монорепозитория **harpyhare** (Nx + npm workspaces; лендинг — `apps/landing`). Все пути и команды ниже — относительно `apps/desktop/` (запускать из этой папки, либо через Nx из корня: `nx <target> desktop`). Обзор монорепо — в корневом `CLAUDE.md`.

## Code style

- **Комментарии в коде уместны и приветствуются.** Пиши их там, где объясняешь «почему»: неочевидный инвариант, грабля платформы, причина выбора. Говорящие имена по-прежнему обязательны — комментарий их дополняет, а не заменяет. Крупные архитектурные «почему», которые не привязаны к одному месту в коде, остаются в этом файле.
- **Хардкод запрещён.** Магические значения → именованные константы; вычислимое — деривация, а не копия; поведение моделей — по capabilities API, а не по спискам имён (единственные допустимые исключения по имени описаны в разделе про модели).
- **Одна ответственность.** Функции/компоненты, делающие несколько вещей, дробятся на маленькие с говорящими именами.
- **Публичные контракты меняются только синхронно по обе стороны.** IPC-команды/события, serde-ключи, форматы на диске (settings.json, chats.json), строковый формат хоткеев (`hotkeyFromEvent` ⇄ `parse_hotkey`).

## The Rust ⇄ frontend contract (read this first)

The backend exposes a **fixed set of commands and events**; the frontend mirrors them 1:1. When changing one side, change the other and keep names identical.

- **Контракт генерируется из Rust, а не пишется дважды.** `src/ipc/bindings.ts` — **сгенерированный файл, руками не править**: его пишет `cargo test` (тест `bindings::tests::typescript_bindings_are_up_to_date`, `tauri-specta` + `specta-typescript`). Внутри: типизированный объект `commands.*` (имена команд и аргументы больше не строки), все типы, пересекающие границу, и константы, объявленные через `.constant()` в `bindings.rs` — `SETTINGS_LIMITS`, `SETTINGS_DEFAULTS` (`Settings::default()` целиком), `MODIFIER_COMBOS`, `HOTKEY_ACTIONS` и `QUICK_ACTION_LIMIT`. Файл исключён из eslint/prettier/knip. Добавил команду → `#[tauri::command] #[specta::specta]` + строка в `collect_commands!` в `bindings.rs` → `cargo test` перегенерит биндинги. **Типы, которые ездят только событием, сами не подхватываются** — их надо перечислить в `.typ::<>()` там же, иначе в биндингах их не будет и `contract.test.ts` не с чем сверять. **specta не экспортирует `u64`/BigInt**: поле помечается `#[specta(type = f64)]` (как байты в `UpdateProgress`) — на границу оно всё равно едет как JS number; `usize` он отвергает тем же `BigIntForbidden`, поэтому `usize`-константа уезжает приведением прямо в `.constant()` (`settings::QUICK_ACTION_LIMIT as u32`) — без приведения падает сам тест генерации биндингов, а не сборка фронта. **`bindings.ts` обязан получаться ОДИНАКОВЫМ на macOS и на Windows.** Файл генерируется на машине сборки и коммитится, а CI гоняет `cargo test` + `git diff --exit-code src/ipc/bindings.ts` (на macos-раннере: на windows-раннере тестовый бинарь не стартует, см. корневой CLAUDE.md) — значение, зависящее от `#[cfg]`, разведёт файл на двух хостах и уронит сборку. Отсюда три следствия: платформенные дефолты уезжают **парой платформ** (`PlatformCombo {macos, windows}` у `HotkeyAction.default_combo`, `MODIFIER_COMBOS.macos`/`.windows`), а не «текущим» значением — `.current()` зовёт только сам Rust; команды, которые на второй платформе не работают, из `collect_commands!` НЕ убираются — они остаются в контракте и возвращают понятную ошибку; константы «какая это платформа» в биндингах нет вовсе — фронт определяет её сам (`lib/platform.ts`).
- **Команды регистрируются в `bindings.rs`** (`collect_commands!`), `lib.rs` только отдаёт `specta_builder.invoke_handler()`. `src/ipc/commands.ts` — **прямой реэкспорт** (`export const {cancelStream, closeApp, …} = commands`); ручная обёртка заводится ТОЛЬКО когда добавляет поведение или рукописный тип: `sendToClaude`/`countChatTokens` (`ChatMessageDto`/`RequestOptions`), `getSettings`/`setSettings` (каст к рукописному `Settings`), `checkForUpdate` (`UpdateInfo`), `redeemAccessCode` (идемпотентность), `startWindowDrag` (не команда, а JS-API окна). Однострочные форварды не писать — их было ~28 и они удалены.
- **Рукописные типы во фронте остались ради эргономики, но сверяются компилятором.** Сгенерированный `Settings` слабее рукописного (`#[serde(default)]` делает все поля опциональными, а `f64` в specta — `number | null`), поэтому `ipc/types.ts` держит чистые интерфейсы, а `ipc/contract.test.ts` содержит тип-уровневые утверждения `SameShape<Ours, Rust.X>` для `Settings`, `AppError`, `UpdateInfo`, `RecorderState`, `PromptPreset`, `OutputDeviceInfo`, `RequestOptions` и payload'ов событий (LLM, `resize-key.dim`, `update-progress`, `update-done`). Переименовал/убрал/переTипизировал поле в Rust → `tsc -b` падает на этом файле. Не удаляй эти утверждения — без них рукописные типы снова начнут расходиться (проверено: переименование поля в биндингах роняет сборку). **`SameShape` сверяет ещё и наборы ключей (`SameKeys`), и эта третья проверка не косметическая**: двух проверок на присваиваемость мало, поле, забытое в рукописном типе, проходило их МОЛЧА — в `Generated` оно опционально (значит `Ours` присваиваем), а лишние свойства структурная типизация разрешает (значит `Loosened<Generated>` присваиваем `Ours`). Так и жили `audio_permission_requested`/`screen_permission_requested`: 28 полей в Rust против 26 объявленных во фронте (счёт на момент находки), при зелёном тесте. Рантайм это переживало только потому, что объект настроек всегда получается спредом реального JSON от Rust; собери его где-нибудь литералом — и `set_settings` получил бы поле отсутствующим, а `#[serde(default)]` молча затёр бы пользовательское значение дефолтом.
- **Границы настроек живут в Rust и экспортируются.** `settings::limits` (сгруппировано: `window`/`chat`/`teleprompter`/`capture`) — единственный источник `default/min/max`; из него берут и `Settings::default()`, и `Settings::clamp()`, и константа `SETTINGS_LIMITS` в биндингах. `lib/window-size.ts` остаётся framework-free (свои числа), но тест `window-size.test.ts` сверяет их с `SETTINGS_LIMITS` — разъедутся, упадёт тест. Новая числовая настройка = запись `Bounds` в нужной группе + поле + контрол; отдельных `DEFAULT_*`/`*_MIN`/`*_MAX` констант больше нет. **Контролы лаунчера берут `min`/`max` из `SETTINGS_LIMITS` напрямую — свою копию границ не заводить**: локальные копии уже разъезжались (слайдер `chat_font_size` был 11–18 при Rust-клампе 10–20, и пользователь не мог выставить значения, которые бэкенд принимает). Локально в секциях остаётся только `step` слайдера — его в реестре нет.
- **`set_settings` возвращает применённые (клампнутые) `Settings`**, а не `()`. Фронт обязан принять их как новое состояние (`useSettingsStore.save` → `adopt`), а не перечитывать `get_settings` вторым раундом: иначе UI держит введённое пользователем сырое значение, пока не придёт ответ второй команды.
- **Опции запроса едут объектом, не россыпью флагов.** `send_to_claude`/`count_chat_tokens` принимают `options: RequestOptions {thinking, webSearch}` (Rust `llm::RequestOptions`, `#[serde(rename_all="camelCase", default)]` ⇄ `lib/chats.RequestOptions`, собирается `chatRequestOptions(chat)`). Новая опция запроса = поле в этих двух типах + контрол в UI; сигнатуры `sendToClaude`/`useClaudeStream.send`/`useSendPipeline` не трогаются. Раньше `thinking`/`web_search` шли позиционными аргументами через пять сигнатур подряд.
### События

Эмитятся **только через типизированные хелперы `events.rs`**, и исключений больше нет: имена, payload-структуры и хелперы всех событий (включая `update-*` и `official-presets-updated`) лежат там, а `Emitter` не импортируется больше нигде. Фронт слушает через `src/ipc/events.ts`, типы — `EventMap` в `src/ipc/types.ts`. Список: `state-changed`, `transcript-ready`, `stt-error`, `llm-delta`, `llm-done`, `llm-error`, `llm-usage`, `update-available`, `update-progress`, `update-done`, `toggle-teleprompter`, `resize-key`, `official-presets-updated`, `screenshot-ready`, `screenshot-error`, `focus-prompt`, `duplicate-chat` (payload пустой, как у `toggle-teleprompter`; единственный эмитент — `window::on_duplicate_chat`, см. «Управление окном»), `toggle-mini` (пустой; `window::on_toggle_mini` по глобальному хоткею скрыть/показать), `hotkey-error` (`AppError`; глобальный хоткей не зарегистрировался — сочетание занято другим приложением или не разобралось; фронт показывает тостом в `useErrorToasts`). LLM-события несут `chatId` И `streamId` (`{chatId, streamId, delta}` / `{chatId, streamId}` / `{chatId, streamId, code, message}`) — стримы независимы по чатам, а `streamId` различает ПОКОЛЕНИЯ стрима внутри одного чата. `resize-key.dim` — не строка, а Rust-enum `ResizeDim` (`serde(rename_all="lowercase")` → union `"width" | "height"` в биндингах).

**Ошибки типизированы кодом, а не текстом.** `stt-error` несёт `AppError {code, message}`, `llm-error` — его же плюс `chatId` (поля перечислены явно, без `serde(flatten)` — иначе specta не экспортирует тип). Коды (`error.rs` в Rust, `lib/errors.ts` на фронте, списки обязаны совпадать): `network | badApiKey | badAccessCode | retryable | api | cancelled | permission | silence | internal`. Ветвление UI — ТОЛЬКО по `code` (`isRetryable` → кнопка «Повторить» в Composer, `isNetworkError` → `ConnectivityOverlay` без тоста). `cancelled` тоже без тоста. Остальные коды — глобальный тост (`notifyAppError` / `useErrorToasts` на `stt-error`/`llm-error`/`screenshot-error`; локальные сбои сохранения и копирования — `notify`). Тосты монтируются в `renderWindowRoot` (HUD и лаунчер), живут `TOAST_DURATION_MS` = 1500мс, позиция `top-center`. Текст ошибки больше не рисуется в шапке StatusBar — там он обрезался. `message` идёт в тост. Раньше фронт парсил русскую прозу регулярками (`/перегружен|соединение|VPN/`) — не возвращай это, переформулировка текста ошибки не должна ничего ломать. Новый вариант ошибки: вариант enum + `CodedError::code()` в Rust ⇄ строка в `ErrorCode` на фронте.

**Дельты коалесируются в Rust и раскрываются плавно во фронте.** `llm-delta` копятся флашером ~25мс в `chat::send_to_claude`; финальный дрен буфера обязан уйти **до** `llm-done`, иначе фронт потеряет хвост ответа. Поверх коалесинга `useClaudeStream` раскрывает буфер не разом, а в rAF-цикле (`lib/stream-reveal`: скорость по dt = max(минимальная, доля отставания в секунду) — отставание показа ограничено ~100мс; срез не рвёт суррогатные пары). При done/stop/error в историю уходит ПОЛНЫЙ буфер, а не раскрытая часть — мгновенный доскок хвоста в конце осознан.

**Заполненность контекста — целиком из API, без хардкода окон:**

- Числитель-фолбэк: `llm-usage {chatId, inputTokens}` из `message_start.usage` стрима — СУММА `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` (при включённом prompt-cache голый `input_tokens` почти нулевой!). Пишется в `Chat.lastInputTokens`, персистится в chats.json — мгновенный фолбэк при входе в чат.
- Знаменатель: `ModelInfo.maxInputTokens`.
- **Основной показатель — проекция через `count_tokens`:** команда `count_chat_tokens` (Rust `AnthropicClient::count_tokens`, `POST /v1/messages/count_tokens`, бесплатный, без лиза на прокси) считает, сколько займёт СЛЕДУЮЩИЙ запрос (system + текущая история); хук `hooks/useProjectedContextTokens.ts` (дебаунс 400мс, для пустого чата — плейсхолдер-сообщение `.`, чтобы учесть вес библиотечных материалов ещё до отправки; `placeholderData` держит прошлое значение ТОЛЬКО в пределах того же `chat.id` — при переключении чата счётчик прошлого на один round-trip выглядел бы как счётчик нового, а фолбэк на `lastInputTokens` как раз для этого момента и персистится).
- Итог: `usedTokens = projected || lastInputTokens` → `ContextUsageGauge` в шапке (StatusBar, перед иконками действий; скрыт, пока данных нет или окно модели неизвестно).
- **Прокси (репо `itech-relay`) обязан маршрутизировать `/v1/messages/count_tokens`** — иначе 404 и проекция не работает.
### Settings (34 поля)

Определён одинаково в `src-tauri/src/settings.rs` и `src/ipc/types.ts` (совпадение сторон проверяет `ipc/contract.test.ts`). Числовые границы НЕ дублируй в этом файле — они живут в `settings::limits` (см. выше). **Дефолты не дублируются**: `DEFAULT_SETTINGS` в `ipc/types.ts` (им инициализируется стор до первого `get_settings`, из него берутся фолбэки `normalizeDraft` в лаунчере) собирается из генерируемой `SETTINGS_DEFAULTS`, а не перечисляет значения руками — пропало или переименовалось поле в Rust, и `tsc` падает прямо на этой сборке объекта. Спред `prompt_presets: [...SETTINGS_DEFAULTS.prompt_presets]` там **обязателен и не подлежит «упрощению»**: specta печатает константу с `as const`, то есть массив приходит `readonly`, а `Settings.prompt_presets` изменяемый (лаунчер правит его прямо в draft) — без копии это ошибка типов.

**Глобального системного промпта и модели в Settings нет** — вместо них `prompt_presets: {id,name,text}[]` (сид «Расшифровка речи», id `transcription`) и per-chat поля. Чат хранит `presetId`, `thinkingEnabled`, `model`, `webSearch` (поповер «Параметры запроса» тулбара Composer — тулбар иконочный внутри карточки промпта, одинаков на любой ширине окна; модель и препромпт — селекты, булевы thinking и веб-поиск — тумблеры `Switch` через `ParamToggle`, прежний `ToggleSelect` из двух пунктов «Вкл/Выкл» удалён и **не возвращается**: те же булевы настройки в лаунчере всегда были тумблером (`SettingSwitch`), а выпадающий список с двумя кликами ради одного бита в HUD был самым заметным признаком «двух разных приложений в одном продукте». **Подпись строки и `aria-label` тумблера обязаны быть одной константой** — `THINKING_PARAM_LABEL`/`WEB_SEARCH_PARAM_LABEL`: подпись рисует `ParamRow`, а `aria-label` висит на самом контроле, и разъехаться они могут только молча — на экране этого не видно) и `context` (диалог «Контекст» — постоянный справочный текст чата). `system` собирается на фронте (`App.dispatchSend`): текст пресета (`lib/presets.presetText`) + выбранные материалы библиотеки контекстов (`lib/context-library.libraryContextBlocks` по `chat.libraryDocIds`) + контекст чата, и всё уходит в `send_to_claude(messages, chat_id, system, model, options)` при каждом запросе (Anthropic API stateless). Дефолты нового чата — `NEW_CHAT_DEFAULTS` в `lib/chats.ts`, они же fallback при десериализации старого chats.json: без препромпта (`presetId=""`), `thinkingEnabled=false`, `model` = `DEFAULT_MODEL` (haiku 4.5, `lib/models.ts`), `webSearch=false`, `context=""`. Старые чаты без соответствующего поля получают тот же дефолт (обратной совместимости с ранее сохранёнными значениями opus/thinking-on специально НЕ держим — реальных пользователей со старым chats.json нет). **Встроенные пресеты read-only, и путь «изменить встроенный» ровно один — «Скопировать в свои»** (группа «Встроенные» в `PresetsSection`: строка разворачивается кликом и показывает полный текст, причём сам текст лежит СНАРУЖИ кнопки-тоггла — внутри неё его нельзя было бы выделить мышью; рядом «Копировать текст» в буфер и «Скопировать в свои», которая заводит свой пресет с тем же текстом, именем + `PRESET_COPY_SUFFIX` и сразу открывает его в редакторе). **Копия обязана получать НОВЫЙ `crypto.randomUUID()`, а не id встроенного оригинала**: `lib/presets.mergePresets` собирает `[...official, ...user.filter((p) => !officialIds.has(p.id))]`, поэтому пользовательский пресет с id встроенного молча выпадает из объединённого списка — правленая копия не появилась бы ни в селекте препромпта чата (`App.tsx`), ни в индексе поиска лаунчера (`LauncherPanel`), а на экране остался бы неизменившийся оригинал. Закреплено тестом «у копии свой id — встроенный оригинал не перекрывается» (`PresetsSection.test.tsx`).

**Распознавание речи:**

- `stt_language`/`stt_translate` — язык распознавания и перевод на английский (см. stt.rs).
- `stt_provider` — `"groq"` (дефолт), `"openai"`, `"xai"` или `"deepgram"`: какой вендор STT собирает `build_stt_client` (различия — в stt.rs). **Список значений живёт в ОДНОМ месте — `stt::registry::PROVIDERS`** (раньше был продублирован константами в `settings.rs` и таблицей в `lib/stt-providers.ts`, и разъезжался молча). Оттуда же приходят лейблы селекта и меню — через константу `STT_PROVIDERS` в `bindings.ts`. Кламп неизвестного значения тоже один: `registry::resolve` (неизвестный id → первая строка реестра), а `settings.clamp` просто зовёт его — второй копии этого правила заводить нельзя. Оба потребителя списка мапят его генерически (селект лаунчера и группа «Голосовая модель» в `ModelCommandMenu`), поэтому третий вендор отрисуется сам: позиционного разбора `STT_PROVIDERS` в коде не осталось, и заводить его заново нельзя. **Связь «провайдер → нужный ключ API» живёт полем `keyId` прямо в записи реестра** (`sttProviderKeyId`, фолбэк — `STT_PROVIDERS[0]`, то есть тот же groq, что и рустовый кламп): тернарник `provider === "openai" ? "openai" : "groq"` из `api-keys.ts` убран, иначе третий вендор нарисовался бы в обоих списках, но гейт готовности требовал бы у него ключ Groq. **Меню моделей гасит вендора без ключа** (`sttProvidersMissingKey` → `disabled` + подпись «нет ключа»): HUD ключи иначе не проверяет вовсе, `build_stt_client` собирает клиент с пустым ключом молча, и переключение посреди интервью убивало бы следующую запись на «Неверный ключ OpenAI». **Вторая после `screen_share_visible` настройка с двумя местами правки:** селект «Провайдер распознавания» в лаунчере и командное меню моделей в HUD (`ModelCommandMenu` — пункт `Cpu` «Модели» в доке действий `StatusBar` плюс хоткей `model_menu`; вторая группа того же меню, «Модель ответа», правит `chat.model`). Мотив тот же, что у индикатора демонстрации: сравнить вендоров на живой речи можно только A/B посреди работы, а попасть в лаунчер = остановить HUD (`stop_main_window` уничтожает окно), то есть прервать разговор ровно там, где и надо сравнивать. Своего пути записи меню не заводит: тот же `saveSettingsReportingError` → `set_settings`, что и у тумблера в лаунчере.
- `capture_device_uid` — UID устройства вывода для захвата (`""` = системный дефолт + автопересоздание тапа при его смене; см. capture.rs).
- `buffer_enabled`/`buffer_seconds` — фоновый кольцевой буфер последних N секунд системного звука (включён по умолчанию): звук непрерывно ресемплируется в 16 кГц и живёт только в RAM (`audio::RollingBuffer` внутри `capture::Shared`), при старте PTT-записи снимок буфера автоматически приклеивается к началу транскрипции (и в стриминговое тело STT-запроса, и в аккумулятор сессии) — подхватывает сказанное до нажатия. Выключение тумблера немедленно очищает буфер, на диск ничего не пишется; side-effects смены полей — `apply_buffer_settings_change` в `set_settings`; при пересоздании tap буфер начинается заново (потеря ≤10 с осознанна).

**Телесуфлёр:** `teleprompter_speed`/`teleprompter_font_size` (клампы дублирует `lib/teleprompter`), персистятся при закрытии суфлёра; сочетание вызова отдельным полем НЕ хранится — оно живёт действием `teleprompter` в реестре (дефолт `F10`); `teleprompter_resume` (дефолт `true`) — суфлёр открывается с сохранённой позиции скролла, если текст ответа тот же, иначе с начала.

**Быстрые действия:** `quick_actions: {id, title, prompt}[]` — полоса кнопок над полем ввода HUD (три сида: `detail`/`brief`/`code`), плюс `quick_action_attachments` (дефолт `false`) — подмешивать ли в такое сообщение вложения черновика. Выключён по умолчанию намеренно: быстрое действие обязано быть предсказуемым и слать ровно свой промпт, а не утаскивать забытый в поле снимок; связка «снял скриншот → нажал кнопку» включается осознанно одним тумблером. Предел `settings::QUICK_ACTION_LIMIT = 9` **выведен из хоткея, а не взят на глаз**: вызов — модификатор с цифрой 1…9, десятой кнопке сочетание взять неоткуда; поэтому `Settings::clamp` режет хвост списка, а лаунчер блокирует «Добавить» на пределе. **Сохранённый пустой массив остаётся пустым**: `#[serde(default)]` подставляет сиды, только когда поля в json нет вовсе, — удалённые пользователем кнопки не воскресают при перезапуске (закреплено тестом `load_saved_empty_quick_actions_stays_empty`). Незаполненные действия Rust НЕ отсеивает: их фильтрует фронт при рендере и лаунчер при сохранении (см. «Быстрые действия» во фронте и `normalizeDraft`).

**Хоткеи:** одно поле `hotkeys: Vec<HotkeyBinding {action, combo}>` вместо прежних семи строк (`hotkey`, `toggle_hotkey`, `teleprompter_hotkey`, `screenshot_hotkey`, `move_modifier`, `resize_modifier`, `scroll_modifier`). Пустой массив = всё по дефолтам реестра; см. «Хоткеи: реестр действий».

**Прочее:** `anthropic_api_key`/`groq_api_key`/`openai_api_key`/`xai_api_key`/`deepgram_api_key`/`xclis_api_key`/`access_token` (см. «API keys» и «Коды доступа»), `auto_send`, `auto_preview_html`, `skipped_version`. **`openai_api_key` — ключ двойного назначения** (STT-вендор OpenAI И ответы GPT), поэтому `rebuild_changed_api_clients` пересобирает на его смену ОБА клиента, а не только STT; отдельного поля под ответы нет намеренно — вендор и ключ те же.
- **Список моделей в UI не равен списку доступных.** `useModels` прогоняет ответ бэкенда через `withLockedModels` (`lib/models`): вендор, которого `list_models` не вернул (нет ни ключа, ни кода доступа), дописывается из статического `FALLBACK_MODELS` и показывается **запертым** — `ModelCommandMenu` и селект Composer гасят его пункты и рисуют подпись «нет ключа», ровно как группа «Голосовая модель» делает это для STT-вендоров. Мотив прямой: пока моделей GPT в списке просто не было, из UI нельзя было понять, умеет ли приложение в OpenAI вообще, — молчание читалось как «не поддерживается». Назвать модель надо ДО того, как появится credential, которым её можно проверить, поэтому оффлайн-каталог обязан существовать — но живёт он в ОДНОМ месте, `llm::registry::PROVIDERS`, откуда `FALLBACK_MODELS` и приезжает через `bindings.ts`. Кто заперт — считает `modelProvidersMissingKey` (`lib/api-keys`, рядом с `sttProvidersMissingKey`) по `MODEL_PROVIDERS[].keyId`; **код доступа отпирает всех**, потому что relay проксирует и Claude, и GPT.
- **Модели — динамические, не хардкод.** Команда `list_models` (Rust `llm::list_models`, `GET /v1/models`, бесплатный) отдаёт модели аккаунта с выжимкой capabilities (`ModelInfo {id, displayName, provider, adaptive, alwaysThinks, codeExec, maxInputTokens}`; `maxInputTokens` — из поля `max_input_tokens` ответа `/v1/models`, у фолбэк-моделей 0 = «неизвестно»); кэш в `App.models`, первичный фетч на старте, фронт берёт через `useModels` (фолбэк — `lib/models.FALLBACK_MODELS`). `useModels` отдаёт не весь список, а курированный: `curatedModels` (lib/models) идёт по реестру `MODEL_PROVIDERS` и у провайдера с непустым `families` оставляет по свежайшей модели семейства (Claude: opus/sonnet/haiku) — первое вхождение семейства в порядке `/v1/models` (API сортирует новыми вперёд), датированные id не хардкодятся и новые версии подхватываются сами; у провайдера с пустым `families` (OpenAI) список приходит уже курированным из Rust и проходит насквозь. Rust-кэш `App.models` остаётся полным (capabilities находятся и для модели старого чата вне тройки, а `selectableModels` подмешает её и в селект, и в меню моделей). **`chat.model` правится из двух мест HUD** — селект в поповере «Параметры запроса» Composer и группа «Модель ответа» в `ModelCommandMenu`; оба идут одним `chats.patchChat(activeId, {model})`, второго пути записи у меню нет. Оба места раскладывают список по вендорам через `lib/models.modelGroups` и **показывают заголовки групп только когда групп больше одной** — с одним Anthropic-ключом UI ровно такой же, как до второго провайдера. Поле `thinking` собирает `llm::thinking_value` по capabilities: вкл → `adaptive` где поддержан; выкл → явный `{"type":"disabled"}` (на Sonnet 5 «опустить поле» = adaptive!); haiku (adaptive не поддержан) и Fable/Mythos («думают всегда» — единственное исключение по имени, capabilities этого не выражают) → поле не отправляется. Тумблер thinking в Composer гасится через `lib/models.thinkingLocked`. Веб-поиск (`llm::web_search_value`) — server-side tool `web_search_20260209` в `tools` (Anthropic ищет сам, внутри того же стрима — клиентского tool-loop нет); моделям без code execution (haiku, `capabilities.code_execution`) обязателен `allowed_callers:["direct"]`, иначе API отвергает запрос (проверено живыми пробами — сами tool-версии в capabilities не выражены).
- **Второй LLM-вендор (OpenAI) — маршрутизация по модели, а не по настройке.** Провайдера выбирает `llm::router::ProviderRouter` (`App.llm` — всегда он, даже когда провайдер один: один код-путь, спецслучая нет): по `request.model` он находит владельца сначала в живом каталоге `App.models` (поле `ModelInfo.provider`), затем в оффлайн-таблицах `LlmProvider::known_models()`, и лишь потом падает на `providers[0]` (Anthropic). Отсюда: **поля «провайдер ответов» в `Settings` нет и заводить его нельзя** — вендор выводится из `chat.model`, поэтому у каждого чата он свой и переключается одним выбором модели. `build_llm_client` заводит `OpenAiClient` в двух режимах: есть `access_token` → `for_proxy` (bearer — сам `itk_`-токен, base_url — воркер, роут `/v1/responses`), токена нет, но задан `openai_api_key` → `new` напрямую в api.openai.com. Нет ни того, ни другого — провайдера в роутере нет вовсе. **В прокси-режиме `list_models()` отдаёт курированную таблицу, НЕ спрашивая `/v1/models`**: этот путь на relay — anthropic-каталог, а заводить воркеру отдельный путь под каталог OpenAI нельзя, это сломало бы симметрию «путь на прокси = путь на upstream», на которой держатся аудио-роуты. Следствие: доступность моделей в прокси-режиме гарантирует не проба, а allowlist воркера (`quota/profiles.ts`, префикс `gpt-5.`) — разъедется с `CURATED_MODELS`, и пользователь увидит модель, на которую relay ответит `model_not_allowed`.
- **`ResponsesClient` (`llm/responses.rs`) — Responses API, а не Chat Completions; это модуль ДИАЛЕКТА, а не вендора (его обслуживают и OpenAI, и Grok)**: `POST /v1/responses`, `system` → `instructions`, история → `input` (у user-хода блоки `input_text`/`input_image`, у assistant-хода — **обязательно `output_text`**), картинки — data-URL в `image_url`, `store: false` (иначе OpenAI хранит ответы у себя — для приложения, которое маскируется под «Audio System», это неуместно). Выбор Responses продиктован веб-поиском: встроенный tool `{"type":"web_search"}` в Chat Completions недоступен, там пришлось бы уводить пользователя на отдельные `-search-preview`-модели. Thinking ложится на `reasoning.effort`: выкл → `"none"`, вкл → `"medium"` (не «опустить поле»: по умолчанию API сам берёт `medium`, и «выкл» молча стал бы «вкл»). **Каталог вендора — курированная таблица в `llm/registry.rs`, пересечённая с живым `/v1/models`**, и это не нарушение запрета на списки имён, а следствие API: `/v1/models` у OpenAI отдаёт 120+ id вперемешку (tts, embeddings, realtime, image) и **не отдаёт ни display name, ни окна контекста, ни capabilities** — отличить чат-модель там не по чему. Живой список используется как фильтр доступности, так что модель, которой у ключа нет, в UI не появится. Capabilities таблицы проверены живыми пробами, а не выведены из имён (`gpt-5.5-pro` — единственная, кто отвергает `effort:"none"`, отсюда `always_thinks: true`). **`maxInputTokens` у моделей OpenAI = 0 («неизвестно») намеренно**: окна контекста API не публикует, а выдуманное число встало бы знаменателем под индикатор заполненности — поэтому на моделях OpenAI индикатор просто скрыт. По той же причине `count_tokens` у `OpenAiClient` возвращает `UNKNOWN_TOKEN_COUNT` (0), а не ошибку: счётчика токенов у OpenAI нет, а 0 фронт уже понимает как «нет данных» (`projected || lastInputTokens`). Диагностика против живого API — `examples/responses_smoke.rs` (каталог, мультитёрн, пустой assistant, веб-поиск, всегда рассуждающая модель и маршрутизация через роутер).

## Frontend architecture (`src/`)

Strict layering — keep each layer's responsibility intact:

- **`src/ipc/`** — the **only** place that imports `@tauri-apps/api`. `commands.ts` (typed `invoke`), `events.ts` (`onEvent`/`onFileDrop`/`onWindowResized`), `types.ts`. Commands/events call Tauri directly — **браузерного мока больше нет**: фронт работает только внутри Tauri (интернет и Rust-бэкенд обязательны). Раньше был `env.ts` c `isTauri()`-гейтами и no-op/fallback в браузере — удалён целиком (см. connectivity ниже).
- **`src/lib/`** — framework-free pure logic with unit tests: `platform.ts` (чистая `detectPlatform(userAgent)` + `PLATFORM` из `navigator.userAgent` — **единственный источник платформы во фронте**: из Rust её не спрашиваем, иначе разъедется `bindings.ts`; всё платформенное — подписи хоткеев, «из Finder»/«из проводника», видимость экранов лаунчера — принимает платформу параметром с дефолтом `PLATFORM`, чтобы тесты гоняли обе), `api-keys.ts` (`missingApiKeys`/`missingKeysNotice` — какие ключи API отсутствуют и текст баннера), `errors.ts` (`ErrorCode`/`AppError`/`isRetryable`/`isNetworkError`/`internalError` — зеркало Rust-кодов ошибок; вся логика «повторить/оффлайн» здесь, не в компонентах), `composer.ts` (attachment limit/downscale, `Attachment` type), `chats.ts` (chat model, `CHAT_LIMIT`, serialize/deserialize), `models.ts` (`ModelInfo`, `FALLBACK_MODELS`, `thinkingLocked`), `hotkey-capture.ts` (`hotkeyFromEvent`, `conflictsWithTyping`), `hotkey-match.ts` (`parseModifier`/`matchesModifier`/`prepareCombo`/`matchesPrepared` — сверка keyboard-события с сочетанием; разбор строки сочетания — ТОЛЬКО через `splitCombo` из `hotkeys.ts`, единственный парсер на фронте, с теми же алиасами и регистром, что у Rust `split_combo`: свой парсер с точным `"Cmd"` молча не матчил `cmd+k`, который Rust принимал; разделитель и канонические имена модификаторов — константы `hotkeys.ts`), `window-controls.ts` (`applyOpacity`/`applyChatFontSize`/`applyTheme`/`isDraggableChromeTarget`), `stream-reveal.ts` (`advanceReveal`/`sliceRevealed` — математика плавного раскрытия стрима для `useClaudeStream`), `stream-markdown.ts` (`splitStableTail` — деление стрима на стабильный префикс/хвост для мемоизации markdown-парса; авторост поля промпта — JS-хук `hooks/usePromptAutosize.ts` через scrollHeight + ResizeObserver на РОДИТЕЛЕ поля (наблюдение за самим полем, чью высоту меняет колбэк, давало «ResizeObserver loop completed with undelivered notifications» на каждый ресайз с переносом), `field-sizing: content` в WKWebView не работает), `teleprompter.ts` (`toReadingText` markdown→проза, `advanceOffset` скролл-мат, `clampSpeed`/`clampFont`).
- **`src/hooks/`** — one hook per contract slice (`useClaudeStream`, `useChats`, `useModels`, `useRecorder`, `useTranscription`, `useWindowControls`, `usePttSuspend`, `usePromptFocus`, `usePermissions`). **Настройки — два слоя:** `useSettingsStore` (общий: загрузка, `save`, `reload`, применение визуальных настроек через колбэк) используется обоими окнами; `useSettings` — надстройка только для HUD (дебаунс-персист `bumpOpacity`/`bumpWindowSize`/`applyNativeWindowSize`: один общий таймер, несохранённый хвост уходит на диск через `flush()`; **откладывается ПАТЧ (`Partial<Settings>`), а не снимок целиком** — на флаше он накладывается на свежие `settings`, а явный `save(next)` кладёт его поверх своего аргумента (`{...next, ...queued}`). Обе прежние крайности были неверны: слать снимок значило дать хоткею размера затереть `screen_share_visible`/`skipped_version`, а просто отменять отложенное — потерять шаг прозрачности, если вызывающий собрал `next` из снимка, снятого до нажатия. Патч сохраняет и то, и другое, и набор полей выводится из самого изменения, а не из списка. Третий случай — хоткей, нажатый ПОКА `set_settings` в полёте: `useSettingsStore.save(next, latePatch)` накладывает накопившийся за `await` патч поверх ответа Rust, иначе `adopt(fresh)` откатывал бы state и CSS на снимок до нажатия, а отложенный персист потом дописывал патч на диск — state и файл расходились; для ресайза мышью откат в state ещё и физически возвращал окно к старому размеру) и `reload` наружу не отдаёт: перечитывание нужно одному лаунчеру после redeem. Лаунчер берёт `useSettingsStore` напрямую. `useChats` owns the chat list, per-chat drafts/attachments, and disk persistence. **Per-chat поля меняются одним `patchChat(id, patch: ChatPatch)`**, а не сеттером на поле (было семь: `setChatPreset`/`setChatThinking`/`setChatModel`/`setChatWebSearch`/`setChatContext`/`setChatLibraryDocs`/`setChatUsage` + `setDraft`). `ChatPatch` (`lib/chats.ts`) — `Partial<Pick<Chat, …>>` по изменяемым полям; `messages`/`id`/`title` через него не правятся (для них отдельные методы). `Composer` принимает `chat: Chat` + `onPatch`, а не 15 пропсов. Новое per-chat поле = поле в `Chat` + в `ChatPatch` + контрол в UI; `ChatsApi` и `ComposerProps` не трогаются. **Каретка в поле промпта — хук `usePromptFocus`, и ref на textarea принадлежит ему**: `App` → `Composer.promptRef` → `PromptTextarea.fieldRef`. Enter без Shift в поле шлёт сообщение и делает `stopPropagation`: иначе дефолтный send-хоткей (⌘/Ctrl+Enter) доходил бы до `useWindowControls` в том же keydown и `dispatchSend` уходил бы дважды — флаг `streaming` ещё не успевал стать true.; это тот же узел, что обслуживает авторост (`usePromptAutosize`), второго ref заводить не надо. Фокус ставится на маунте (запуск HUD) и по событию `focus-prompt` из Rust, каретка — **в конец текста**: иначе после диктовки или снимка области печатать пришлось бы в начало строки. **Гейт подавления — не «не фокусировать», а «снять фокус»**: пока открыт полноэкранный оверлей (суфлёр или `ConnectivityOverlay`), поле получает `blur()`, а при закрытии оверлея каретка возвращается — половинчатый гейт (только запрет нового фокуса) оставлял каретку в поле ПОД оверлеем, печать уходила в невидимый черновик, а `Enter` отправлял сообщение вслепую. Radix-модалки в гейт намеренно НЕ вписаны: их фокус-ловушка и так откатывает наш `.focus()`, а перечислять диалоги значит заводить список, который разъедется. **Но диалог, открытый из дока или тулбара (`ModelCommandMenu`, `ChatContextDialog`), обязан отменять возврат фокуса Radix — `onCloseAutoFocus` с `preventDefault` — и звать `onRestoreFocus` оттуда же**: Radix возвращает фокус на триггер ПОСЛЕ exit-анимации (`setTimeout(0)` в `FocusScope` при размонтировании), то есть позже нашего rAF-`focusPromptSoon`, и без отмены каретка оставалась на кнопке дока, а не в поле. **Наружу хук отдаёт ПАРУ `{ref, focus}`, и `focus` здесь — гейтованный**: сырой `promptRef.current.focus()` мимо него обходит подавление, потому что блюр висит на ПЕРЕХОДЕ в `suspended`, а не на каждой попытке — при уже открытом суфлёре ничто не сработает повторно, и каретка встанет в невидимое поле под оверлеем. Именно так и жил `focusPromptSoon` в `App.tsx`, пока дубликат чата не стал глобальным: гейт `!promptUnavailable` ушёл из `useComboKey`, а фокус остался сырым. Теперь `focusPromptSoon` зовёт `focus` из хука и держит handle `requestAnimationFrame`, отменяя его на следующем вызове и на размонтировании. Флаг подавления читается через `useLatestRef` (`hooks/useLatestRef.ts` — общий шим «всегда свежее значение в ref», переехал из `App.tsx`, когда понадобился и здесь): иначе подписка на `focus-prompt` пересоздавалась бы на каждое открытие и закрытие оверлея. Hooks depend on `ipc`, never on `@tauri-apps` directly; tested with `renderHook` + `vi.mock("@/ipc/...")`.
- **`src/components/`** — presentational, built on shadcn/ui primitives in `src/components/ui/` (run `npx shadcn@latest add <name>` to add more). `App.tsx` composes hooks + components.

Stack: React 19 + Vite + Tailwind v4 (CSS-first `@theme` tokens in `src/index.css`, gray + oxblood dark theme, dark-only) + react-markdown + rehype-highlight. Path alias `@` → `src`. **Форма и глубина заданы токенами, а не литералами в разметке.** `--radius` = 8px и лестница от него (`sm` 4 / `md` 6 / `lg` 8 / `xl` 12; `--radius-xl` задан явно — без него `rounded-xl` брал бы фиксированные 12px тейлвиндовского дефолта и отвязался бы от `--radius`): контролы `rounded-md`, карточки `rounded-lg`, карточка композера `rounded-xl`, `IconButton` по умолчанию `rounded-md` (прежний `rounded-full` снят). Радиус окна — отдельная переменная `--window-radius`, и **литеральных `rounded-[22px]`/`[14px]`/`[10px]` в коде не осталось ни одного**: последним на переменную переехал `ConnectivityOverlay`. Тени — тоже токены `@theme`: `--shadow-btn` (заливные кнопки), `--shadow-raise` (верхний внутренний свет карточек), `--shadow-pop` (меню, поповеры, выдача поиска лаунчера), `--shadow-modal` (диалоги); **у инпутов, textarea и селектов теней нет вовсе** — их отделяет hairline-бордер `--input`, стоковый shadcn'овский `shadow-xs` снят со всех полей и обратно не возвращается. Фокус во всём коде один — `focus-visible:ring-2`, колец `ring-[3px]` не осталось. Толщина штриха иконок задана глобально (`svg.lucide { stroke-width: 1.75 }` в `index.css`), пропом на отдельной иконке её не правят. `--font-sans` задан явно (SF Pro Text на macOS, Segoe UI Variable Text на Windows), чтобы не полагаться на дефолтный UI-стек вебвью: без явного стека WebView2 отдаёт классический Segoe UI без оптического подбора начертаний. Тема dark-only без второй половины: `@custom-variant dark (&)` в `index.css` делает стоковые `dark:`-классы shadcn безусловными, поэтому дублирующий слой из них снят целиком — **в разметке не осталось ни одного `dark:`**, и притащенный из свежего сниппета shadcn он не «включит тёмную тему», а молча перекроет соседний класс. **Правило палитры: primary (окс-красный) НЕ используется как цвет текста** (заголовки секций, ссылки, бейджи, чипы — нейтральные `text-foreground/*`); primary допустим только для индикаторов (точки, эквалайзер, маркеры списков, подчёркивание активного таба), заливок кнопок и `destructive`-ошибок. **У точек-индикаторов язык фиксированный**: `destructive` = «требует действия пользователя» (блокеры готовности в статусе шапки и в сайдбаре), `primary` = «в порядке / бренд / информация» (готовность к запуску, выданный доступ, доступное обновление), приглушённый `muted-foreground` = нейтральное «идёт проверка / не выдано / не задано». Красить блокер в primary «чтобы не пугать» нельзя — тогда две противоположные ситуации выглядят одинаково. Ради этого же языка **`--destructive` разведён с `--primary` по hue И по светлоте** (oklch `0.6 0.21 27` против `0.47 0.17 18`): пока оба сидели на hue 18, точки «блокер» и «готово» размером 6px (`size-1.5` в сайдбаре и в статусе шапки) отличить друг от друга было невозможно — сводить их обратно к общему тону нельзя.

**Подсветка кода:** rehype-highlight в `AnswerPanel` (`REHYPE_PLUGINS`); палитра токенов — в `index.css`. Инвариант: `html` в `plainText` — чип превью (`HtmlBlockChip` через `makePre`) требует, чтобы children код-элемента остались **сырой строкой**; подсветка превратила бы их в массив span'ов и молча сломала чип. Во время стрима markdown-чанки мемоизированы (`MarkdownChunk` + `splitStableTail`) — история и завершённые блоки не перепарсиваются на каждый флаш дельт. `splitStableTail` режет стрим на префикс/хвост ТОЛЬКО по границе абзаца вне fenced-код-блока и только когда за границей уже видна строка, начинающая новый блок. Fence отслеживается одним линейным проходом с состоянием (символ и длина открывающего маркера; закрывает только маркер того же символа не короче — как в CommonMark, иначе `~~~`-блок с ```` ``` ```` внутри навсегда уходил в «открытый код»); регулярка маркера — `^ {0,3}`, не `\s{0,3}`: с флагом `m` пробельный класс захватывал переводы строк, и строка ```` ```js ```` уезжала в тело блока. Граница НЕ ставится, если следующая строка с отступом (хвост пункта списка отдельным чанком стал бы отступным кодом) или это очередной пункт того же loose-списка (список рвался на несколько `<ol>`), а незавершённая последняя строка стрима, которая ещё может дорасти до пункта («2» → «2. Baz»), тоже ждёт. Проход линеен по хвосту: прежний обход «каждый `\n\n` с конца + regex-скан префикса» давал O(k·n) — 10 мс на кадр на длинном открытом код-блоке.

**Скролл чата:**

- **Скролл-к-низу при переключении чата — синхронно ДО пейнта** (`useLayoutEffect` в AnswerPanel, а не `useEffect`): иначе браузер успевает показать кадр со старой позицией → видимый «полёт сверху вниз».
- **Автоскролла во время стрима НЕТ намеренно** (stick-to-bottom раздражал — прокрутка «убегала» и останавливалась только ручным скроллом вверх): вниз прокручивают только переключение чата, отправка СВОЕГО сообщения (рост messages с user-хвостом в AnswerPanel) и кнопка «↓ Вниз»; рост partial лишь обновляет видимость кнопки (`syncJump`).
- `content-visibility` на сообщениях НЕ используется намеренно: он делал `scrollHeight` оценочным (офскрин-элементы схлопнуты в intrinsic-size), из-за чего пре-пейнт-скролл промахивался мимо низа и приходилось добивать rAF-циклом — костыль убран вместе с ним. Для реально огромной истории правильный инструмент — виртуализация (virtua), а не content-visibility (он ломает точность `scrollHeight`).

**Кнопки действий сообщения не отнимают ширину у ответа.** У user-пузыря они стоят слева от него, во flex-строке: пузырь и так не шире 85%, слева пусто, платить нечем. У ответа ассистента жёлоба справа НЕТ и заводить его снова не надо — кластер лежит `absolute right-0 bottom-0` поверх сообщения на непрозрачном чипе (`FLOATING_CHIP_CLASS`, тот же, что у кнопки «↓ Вниз»), а текст занимает всю ширину колонки. Прежняя раскладка резервировала под кнопки 54px справа у КАЖДОГО ответа — в окне шириной 300px это пятая часть строки, и абзацы верстались по обрезанной ширине даже тогда, когда на кнопки никто не наводил. **Почему правый НИЖНИЙ угол, а не верхний:** последняя строка абзаца почти всегда короткая из-за рваного правого края, поэтому чип чаще всего не накрывает ничего, а верхний угол пришёлся бы на первую строку, которая как раз идёт во всю ширину. Чип непрозрачный — там, где он всё-таки лёг на текст, текст закрыт, а не смешан с ним.

- Ховер — обычный CSS `group-hover`, но **БЕЗ `transition-opacity`**: в прозрачном frameless-окне анимация прозрачности выносит элемент в отдельный композитный слой WKWebView, и при его схлопывании остаются несмытые пиксели (кнопки «залипали» видимыми на нескольких сообщениях сразу — при корректном DOM! — до полной перерисовки сменой чата; на скриншотах всплывали даже призраки текста прошлых кадров). События `:hover`/`mouseleave` были ни при чём — JS-трекинг ховера уже пробовался и откачен как лишний.
- Правило: у hover-reveal контролов показ/скрытие мгновенные, никаких opacity-переходов (снято в `AttachmentChip`, `ContextLibraryPanel` и `PresetsSection`). В скрытом состоянии — `pointer-events-none`, снимаемый тем же `group-hover:`/`focus-within:`, что и прозрачность, чтобы невидимые кнопки не ловили клики; в кластерах лаунчера гейт заведён по этому же правилу, а сам набор классов там один на обе строки пресетов (`REVEAL_ON_HOVER_CLASS` в `PresetsSection`) — развёрнутая встроенная строка держит кластер видимым постоянно, reveal висит только на свёрнутой. **`transition-opacity` в кодовой базе не осталось ни одного** — последний жил на кнопке закрытия диалога и заменён переходом цвета (`text-muted-foreground` → `hover:text-foreground`); пустой grep по нему и есть проверка правила. У кнопки удаления ховер дополнительно красит иконку в `destructive` — кнопки безподписные, и это единственное, чем «удалить» отличается от «изменить» до клика.
- **Стрим и история верстаются по одной ширине автоматически.** Пока жёлоб существовал, отступ `StreamingAssistant` обязан был совпадать с ним по арифметике, и добавление кнопки в `MessageActions` требовало пересчёта класса вручную — иначе готовый ответ перевёрстывался при переезде из стрима в историю. С кластером поверх сообщения считать нечего: ширина у обоих полная, и число кнопок на неё не влияет.
- **Копирование сообщения: текст, а если его нет — картинка.** У сообщения из одного скриншота без подписи кнопка иначе копировала бы пустую строку; правило `messageCopyText` → `messageCopyImage` (`lib/message-clipboard`) этот случай и закрывает. Картинка идёт в буфер ЧЕРЕЗ RUST (`clipboard::copy_image_to_clipboard`), а не через `navigator.clipboard`: тот же проверенный путь, что у снимка области. Перед отправкой фронт перекодирует картинку в PNG холстом (`imagePngBase64`), потому что `tauri::image::Image::from_bytes` собран с фичей `image-png` и умеет ТОЛЬКО png, а вложения бывают jpeg/gif/webp; готовый PNG холст не трогает вовсе. Запись PNG в буфер живёт в одном месте — `clipboard.rs` (`write_png` зовёт и `screenshot::deliver`), дублировать её в модулях не надо.

**Быстрые действия — полоса кнопок над полем ввода** (`QuickActionsBar` **снаружи** карточки `Composer`, отдельным рядом над ней; редактор списка — `QuickActionsSection` на экране «Настройки» лаунчера). Кнопка показывает `title`, а в чат уходит `prompt` — самого промпта на кнопке не видно; тот же вызов даёт хоткей «модификатор + цифра» (`useQuickActionKeys`). **Путь отправки у них свой, `appendUserMessage` не переиспользуется:** `useChats.appendQuickActionMessage` НИКОГДА не трогает текст черновика (недописанный вопрос обязан пережить нажатие ⌘1) и снимает `draftAttachments` только если те реально ушли в сообщение; обычная отправка по-прежнему чистит и то, и другое. Вложения подмешиваются, только когда включён `quick_action_attachments`. Сборка system + истории и запуск стрима вынесены в общий `streamChat` внутри `hooks/useSendPipeline.ts` — его делят `dispatchSend`, `dispatchQuickAction` и `resendFromMessage`, своей копии этой сборки новый отправитель заводить не должен.

**У быстрых действий четыре гейта, и каждый закрывает свою дыру:** полоса рисуется только при `!settingsLoading` — иначе на старте видны сиды из `DEFAULT_SETTINGS`, а после ответа `get_settings` пропадают, дёргая высоту композера; `runQuickActionAt` не срабатывает, пока поле промпта недоступно (`promptUnavailable` — суфлёр, `ConnectivityOverlay` или мини-режим), потому что промпт быстрого действия непустой ВСЕГДА и без гейта ⌘1 отправлял бы сообщение вслепую при любом черновике (у обычной отправки предохранитель — пустой черновик, здесь его нет); `useQuickActionKeys` выбрасывает `e.repeat`, иначе удержанная цифра пошлёт второе сообщение ровно в тот момент, когда снимется флаг `streaming`; `onMouseDown` с `preventDefault` висит на КОНТЕЙНЕРЕ полосы, а не на кнопках — полоса почти вся пустая и лежит вплотную над полем, и промах мимо кнопки уводил бы каретку из промпта.

**Нумерация идёт по отфильтрованному `filledQuickActions`** (заполнены И название, И промпт) и обязана совпадать в HUD и в лаунчере: ⌘2 в настройках и ⌘2 на кнопке — одно и то же действие, иначе подписи врут. Подпись собирает `quickActionHint` (`lib/quick-actions`), а склейку «комбо + клавиша» — `formatComboWithKey` (`lib/hotkeys`): раньше это были две копии со своими константами разделителя в двух окнах.

**Интернет обязателен + connectivity-лоадер.** Оффлайн-режим не поддерживается. Детект связи — хук `useConnectivity` (`hooks/useConnectivity.ts`): `offline` инициализируется `!navigator.onLine`. Проба — команда `probe_connectivity` → `LlmProvider::reachable`: авторизованный GET `{base_url}/v1/models` (**любой HTTP-ответ = связь есть**, connect/DNS/timeout = нет; в прокси-режиме бьёт в тот же relay). Это reachability API/прокси, не «бытовой интернет»: из России без VPN проба часто ложна, пока туннель не гоняет Anthropic/Cloudflare, хотя браузер уже открывается.

Проба **не ходит через пул стримингового клиента**. `reachable()` каждый раз собирает отдельный HTTP/1.1-клиент без keep-alive (`pool_max_idle_per_host(0)`, connect 3с / общий таймаут 5с) — иначе после смены VPN/интерфейса HTTP/2-зомби из `build_http_client` (`pool_idle_timeout(None)`) отвечает таймаутом вечно, а оверлей не снимается. У роутера провайдеров первый успешный `reachable` заканчивает пробу; зависший второй вендор не блокирует. Фронт нумерует пробы: поздний провал не перебивает свежий успех. Пока `offline` — опрос каждые 4с **с немедленным первым тиком**; плюс немедленная проба на маунте, на `online`/`offline`, на `reportNetworkError()` и на кнопку «Проверить снова». `reportNetworkError` зовётся из App, когда сводный `error` (`sttError ?? screenshot.error ?? stream.error`) имеет `code === "network"` — поднимает оверлей сразу и сразу же перепроверяет. Успех после неуспеха в `probe_connectivity` пересобирает LLM- и STT-клиенты (`recycle_pooled_http_clients`) — свежий пул после VPN. Пинги HTTP/2 на основном клиенте имеют таймаут 5с (`http2_keep_alive_timeout`), иначе интервал keep-alive без ACK не закрывает мёртвое соединение.

При `offline` рендерится полноэкранный `ConnectivityOverlay` (`absolute inset-0 z-50` над `.app-shell`, рядом с оверлеем телесуфлёра) — **не размонтирует чат/стримы**, закрыть вручную нельзя (интернет обязателен), только повторная проба. Сетевые фолбэки списка моделей (`FALLBACK_MODELS`/`fallback_models()`) и вшитых пресетов оставлены сознательно (мгновенный рендер до первого фетча + сид для `presets:publish`).

### Язык интерфейса launcher и HUD

`Settings.ui_language`: `""` — язык системы, `"ru"` / `"en"` — явный выбор. Список `UI_LANGUAGES` и дефолт принадлежат Rust и генерируются в bindings; неизвестное значение сбрасывается на системное. Выбор находится в «Настройки → Вид», применяется сразу и сохраняется обычным автосохранением. Оба окна применяют настройку при загрузке через `applyUiLanguage`; язык распознавания `stt_language` остаётся отдельным параметром.

`src/i18n/ru.ts` задаёт тип словаря, `en.ts` обязан повторять его ключи. Компоненты подписываются через `useTranslation`, чистые функции берут `t` из `@/i18n` в момент вызова: перевод на уровне модуля замораживает язык. Мемоизированные результаты с переводами нужно пересчитывать при смене языка (поиск лаунчера, блокеры готовности). Реестры экранов и вкладок хранят id/иконки, а поиск использует те же ключи, что видимые настройки. `plural` разворачивает формы в суффиксы i18next; тесты проверяют формы, переменные интерполяции и соответствие подписей хоткеев реестру Rust.

Тестовый setup загружает i18n в `beforeEach`, после установки моков файла: статический импорт раньше времени кеширует bindings с настоящим `invoke` и ломает IPC-тесты. Каждый тест начинает с русского; проверки переключения отдельно меняют язык уже смонтированных элементов HUD и поиска.

## Rust backend (`src-tauri/src/`)

**Провайдеры за портами — командный слой не знает про Anthropic/Groq.** `App.llm: Mutex<Arc<dyn llm::LlmProvider>>` и `App.stt: Mutex<Arc<dyn stt::SttEngine>>` — трейт-объекты, не конкретные клиенты.

- `llm::LlmProvider` — `provider_id()` / `known_models()` / `owns_model(id)` / `stream(LlmRequest, cancel, &mut dyn LlmStreamSink)` / `count_tokens(LlmRequest)` / `list_models()` / `reachable()` / `warm_up()`. `LlmRequest {model, system, messages, options}` нейтрален: ни `thinking`-поля, ни `tools`, ни JSON. Сборка тела Anthropic (`build_request_body`, `thinking_value`, `web_search_value`) живёт ТОЛЬКО внутри `impl LlmProvider for AnthropicClient` — в командном слое (`chat.rs`) её быть не должно; тело диалекта Responses — так же внутри `llm/responses.rs`. Две синхронные части порта нужны маршрутизатору: `provider_id()` — чей это клиент, `known_models()` — что он умеет БЕЗ сети (у Anthropic это `fallback_models()`, у OpenAI — курированная таблица), иначе чат, сохранённый с моделью второго вендора, после холодного старта уехал бы не туда. Третья — `owns_model(id)`: последний резерв роутера перед дефолтным вендором; у Xclis офлайн-таблица пуста по замыслу, и владельца его моделей выдаёт неймспейс `xclis/` — без этого чат с моделью Xclis после холодного старта уходил в Anthropic.
- Capabilities резолвит сам провайдер: `AnthropicClient` держит `catalog: ModelCatalog` (`Arc<Mutex<Vec<ModelInfo>>>`, тот же Arc, что `App.models` и что читает роутер), `capability_fields()` читает. **Пишет каталог только роутер**: `ProviderRouter::list_models` сливает ответы всех вендоров (вендор, чей `list_models` упал, сохраняет прежние записи), а запись из клиента затирала общий каталог одними его моделями, пока роутер ждал остальных. `XclisClient` держит тот же Arc — приватная копия терялась при каждой пересборке клиента вместе с тумблером рассуждения. Прежней `find_cached_model` в `lib.rs` нет — не возвращай. Каталог общий на всех вендоров, поиск в нём — по `id`, поэтому чужие записи не мешают.
- **Стриминговая машинерия общая, вендорский только разбор блока.** `pump_sse_stream` + `SseParser` + `SseOut` живут в `llm.rs` и используются всеми тремя клиентами (Anthropic, `responses`, `xclis`); различается лишь `SseBlockParser` (`SseParser::anthropic()`, `SseParser::with_block_parser(responses::parse_block)`, `…(xclis::parse_block)`). Фреймер байтовый и по спецификации: событие — до пустой строки (`\n\n`, `\r\n\r\n`, `\r\r`), нагрузка — склейка всех `data:`-строк (пробел после двоеточия необязателен), комментарии и `event:` пропускаются; блок-парсер получает уже склеенную нагрузку и отдаёт `Vec<SseOut>`. `SseOut::Done(Option<u32>)` несёт токены не для красоты: у Anthropic usage приходит вперёд, в `message_start`, а у OpenAI — только в терминальном `response.completed`, и без этого поля пришлось бы либо терять usage, либо отдавать `Ok` из потока, оборванного на самом деле (`pump_sse_stream` считает конец потока без `Done` обрывом — кроме потока, где уже был `Finished`). Ещё два варианта: `Finished` — диалект объявил конец ответа раньше терминального события (Chat Completions: `finish_reason`, затем usage-чанк и `[DONE]`), после него EOF штатен; `Retryable {code, message}` — перегрузка или лимит, пришедшие событием внутри 200-стрима (`overloaded_error`/`rate_limit_error`/`api_error` у Anthropic, `server_error`/`rate_limit_exceeded` у Responses), уходят кодом `retryable` с кнопкой «Повторить», а не `api`.
- `LlmError::BadApiKey` несёт имя вендора (`&'static str`, как у `SttError::BadApiKey`) — «Неверный ключ Anthropic/OpenAI» должен указывать на тот ключ, который чинить. `LlmError::BadAccessCode(String)` — 401/403 от relay с его же текстом, симметрично `SttError::BadAccessCode` (раньше LLM отдавал их кодом `api`). `LlmError::Network` строится `llm::network_error` с цепочкой причин reqwest (таймаут/подключение/чтение), а не голым «error sending request». Idle-таймаут чтения стрима — `STREAM_IDLE_TIMEOUT` (5 мин, между чанками): модели с долгим молчаливым рассуждением (gpt-5.5-pro, Xclis) думают дольше минуты, а мёртвое соединение ловит http2 keep-alive; короткие JSON-вызовы ограничены `REQUEST_TIMEOUT`. Клиент проб связи — один на процесс (`probe_http_client`), `warm_up` роутера не чаще раза в минуту.
- `stt::SttEngine` — `transcribe(&[f32], keyterms)` / `transcribe_stream(AudioChunkStream, keyterms, cancel)` / `warm_up()`. `AudioChunkStream = Pin<Box<dyn Stream<Item = Result<Vec<u8>, io::Error>> + Send>>` несёт **сырой PCM** (16 кГц, моно, i16 LE) — контейнер добавляет транспорт: `SttHttpClient` подшивает WAV-заголовок сам, Deepgram шлёт как есть; **`reqwest::Body` через границу порта не проходит**, `wrap_stream` вызывается внутри `SttHttpClient`. Движок по строке реестра собирает **одна фабрика `stt::build_engine(spec, SttClientConfig)`** (диалект → транспорт): её зовут и `build_stt_client`, и `examples/stt_smoke.rs`.
- Дельты стрима идут в `LlmStreamSink` (две колбэк-функции не годятся — обе занимали бы `&mut` на один буфер); в `chat.rs` его реализует `ChatStreamSink` (перф-тайминг ttfb + push в буфер флашера + эмит `llm-usage`).
- Второй провайдер (другая модель/локальный STT) = новый `impl` + строка в `build_llm_client`/`build_stt_client`; ни `lib.rs`, ни фронт не меняются. Так и добавлен `OpenAiClient`: `lib.rs` не тронут, а фронт поменялся ровно на группировку списка по вендорам (`MODEL_PROVIDERS` + `modelGroups`) — новый вендор в UI появляется строкой в этом реестре, отдельного кода под него нет. Второй STT-вендор (OpenAI) добавлен НЕ так и намеренно: Groq говорит на диалекте OpenAI, поэтому это второй конструктор одного `SttHttpClient`, а не второй `impl SttEngine` — дублировать multipart-сборку, error mapping и стриминговое тело ради двух разных базовых URL было бы дороже, чем `match` по вендору (см. `stt.rs`).

### Как добавить нового LLM-вендора

Сколько тут работы — зависит от того, **на каком языке говорит вендор**, и это главное различие.

**Вендор говорит на уже известном диалекте** (Grok — ровно этот случай): правка ОДНА — строка в `llm::registry::PROVIDERS` с `wire: LlmWire::Responses { base_url, key_label, effort_off, effort_on }`. Ни модуля, ни ветки в `build_provider`, ни строчки TypeScript. Так и добавлен Grok: xAI отвечает Responses-API байт в байт (те же пути, те же имена SSE-событий, та же форма usage), поэтому весь его код — это данные.

**Вендор говорит на новом протоколе:** вариант в `LlmWire`, модуль рядом с `llm/responses.rs` (тело запроса, разбор своих SSE-событий, `impl LlmProvider` поверх `llm::http::LlmHttp`) и одна ветка в `app_state::build_provider` — она матчится на **диалект, а не на вендора**, поэтому растёт только от новых протоколов, а не от новых вендоров.

Если вендору нужен НОВЫЙ ключ: поле в `Settings`, ветка в `settings::api_key_for`, запись в `API_KEYS` (`lib/api-keys.ts` — там только UI-подписи) и строка в `apply_key_fallback` для `.env`-фолбэка. Забыл ветку в `api_key_for` — падает тест `every_registry_key_id_resolves_to_a_real_settings_field`, а не пользователь.

**Что выводится само и переписывать это руками нельзя:** `MODEL_PROVIDERS` и `FALLBACK_MODELS` во фронте (из константы `LLM_PROVIDERS`), `DEFAULT_MODEL` (из `llm::DEFAULT_MODEL`), пересборка клиента при смене ключа (`llm_credentials_changed` читает реестр), доступность под кодом доступа (`provider_access` — код открывает только `proxied: true`), маршрутизация к владельцу модели (`ProviderRouter` по `ModelInfo.provider`), замок «нет ключа» в обоих пикерах.

**`proxied` — это заявка про relay, а не про вендора.** `true` у Claude, GPT и Grok (ответы) и у Groq, OpenAI и Grok (речь): их воркер проксирует, и код доступа их открывает; `false` у Xclis и Deepgram — у relay нет их роутов, под кодом они берут личный ключ, и пикеры показывают на них замок, пока ключа нет. У диалекта Xclis прокси-режима нет вовсе: `build_provider` при перевёрнутом флаге пропускает вендора с записью в stderr (а не паникует на старте), и тест `the_xclis_dialect_cannot_be_proxied` держит флаг. **Флаг обязан отставать от деплоя, а не опережать его**: поставить `true` раньше, чем роут появился в задеплоенном `itech-relay`, — самый лёгкий способ сломать всё молча, пользователю прилетит `not_found` воркера посреди разговора. Обратное тоже верно — вендор без роута обязан стоять `false`, тогда UI запирает его сам, без единого списка id.

**Окно контекста берётся из живого `/v1/models`, если вендор его публикует.** xAI отдаёт `context_length` — у Grok индикатор заполненности работает; OpenAI не отдаёт ничего — там окно остаётся неизвестным и индикатор скрыт. Флага для этого нет и заводить не надо: клиент читает поле, если оно есть.

**Инварианты под тестами:** `llm/registry/tests.rs` — конформанс-набор для КАЖДОЙ строки (непустые поля, уникальные id провайдеров и моделей, https-хост, каждое объявленное семейство совпадает с моделью каталога, `DEFAULT_MODEL` кем-то предлагается) плюс проверка, что диалект Responses обслуживает больше одного вендора — то есть что заявка «вендор = строка» всё ещё правда; `llm/responses/tests.rs` — что каждому вендору диалекта уходит именно ЕГО `effort` (OpenAI `none`, xAI `minimal` — измерено живыми запросами, xAI отвергает `none`); `app_state/tests.rs` — что `key_id` каждой строки указывает на реальное поле настроек и что непроксируемый вендор не открывается кодом доступа. Живая диагностика — `examples/responses_smoke.rs`: он прогоняет один и тот же набор по ВСЕМ вендорам диалекта, подхватывая ключи из `.env` по соглашению `<KEY_ID>_API_KEY`, так что новую строку он проверяет без правок.

### Как добавить нового STT-вендора

Как и у ответов, объём работы зависит от того, **на каком диалекте говорит вендор**.

**Вендор говорит на уже известном диалекте** (Groq, OpenAI и OpenRouter — этот случай): транспорт задаётся строкой в `stt::registry::PROVIDERS` с `wire: SttWire::OpenAiMultipart { base_url, transcribe_path, warm_up_path, transcribe_model, translation, temperature }`. `translation: Some(SttTranslation { path, model })` только при наличии перевода; иначе `None`.

**Вендор говорит на своём** (Grok — этот случай): вариант в `SttWire` и две ветки в `SttHttpClient` — `form_with` (какие поля кладём в мультипарт) и всё; путь, прогрев и базовый URL берутся через методы `SttWire`. Авторизация, разбор ответа, маппинг статусов, отмена и стриминговое тело общие и не дублируются.

Если вендору нужен НОВЫЙ ключ: поле и пустой дефолт в Rust `Settings`, ветки в `settings::api_key_for` и `api_key_mut`, поле в `ipc/types.ts` и `ApiKeySettings`, запись в `ApiKeyId`/`API_KEYS`, placeholder в `ApiKeysSection`, назначения ключа в `i18n/{ru,en}.ts`. `apply_key_fallback` и пересборка клиента выводятся из реестра. `cargo test` перегенерирует `bindings.ts`; руками его не править.

**OpenRouter STT (сверено 2026-09-05):** `POST https://openrouter.ai/api/v1/audio/transcriptions`, multipart `file` + `model` + `response_format=json`, необязательный `language`. Модель `openai/gpt-4o-mini-transcribe` выбрана как аналог прямого OpenAI-провайдера, чтобы сохранить прежний выбор для русской речи с английскими терминами. Личный `OPENROUTER_API_KEY` из `.env`/`openrouter_api_key` в настройках; `proxied: false`, поскольку relay не имеет его маршрута. Перевод и keyterms выключены: endpoint перевода не документирован, а выбранная mini-модель не использует prompt-биасинг (см. прямой OpenAI). Путь и модель перевода теперь одна необязательная пара, без выдуманного маршрута для OpenRouter. Multipart ограничен 25 MB; текущий максимум записи 600 с при 16 кГц mono PCM16 даёт около 19.2 MB. Провайдер ограничивает обработку примерно 60 с, поэтому длинная запись всё ещё может завершиться таймаутом. Источники: [API](https://openrouter.ai/docs/api/api-reference/stt/create-transcription), [руководство от 2026-07-22](https://openrouter.ai/blog/tutorials/transcription-on-openrouter/), [каталог STT](https://openrouter.ai/api/v1/models?output_modalities=transcription). Смоук только этого провайдера: `cargo run --manifest-path apps/desktop/src-tauri/Cargo.toml --example stt_smoke -- /path/audio.wav openrouter`; `--stream` проверяет загрузку PCM-чанков с потоковым WAV-заголовком. Это потоковая загрузка файла, а не получение промежуточных транскриптов. API может отказать в аудиозапросе при балансе ниже $0.50; сообщение сервиса отображается пользователю.

**Диалект xAI (`SttWire::Xai`) отличается сильнее, чем кажется**, и каждое отличие — грабля: путь `/v1/stt`, а не `/v1/audio/transcriptions`; **поля `model` нет вообще** (модель не выбирается); `response_format` не шлётся; **аудио-часть обязана идти ПОСЛЕДНЕЙ** — сервер отвергает тело, которое начинается с файла, а приложение как раз стримит эту часть, пока пользователь ещё говорит (закреплено тестом `xai_posts_to_its_own_endpoint_with_the_audio_part_last`; чанкованная загрузка с неизвестной длиной проверена живым запросом). **Эндпоинта перевода у xAI нет**, поэтому в строке стоит `supports_translate: false`.

**`supports_translate` — не косметика.** Тумблер «Перевод на английский» в лаунчере гаснет для вендора, который не умеет переводить, а `registry::effective_translate` глушит сохранённое `true` на стороне запроса. Без этого включённый перевод у Grok молча превращался бы в обычное распознавание — то есть выглядел бы как «настройка сломалась». Инвариант «обещание перевода = наличие второго эндпоинта» держит тест `only_a_vendor_with_a_second_endpoint_claims_translation`.

**Биасинг `keyterm` у xAI и Deepgram используется, но только из объявления в промпте (`[keywords]: [...]`)**, а не из отдельной настройки-словаря: словарь как настройка реализовывали, проверяли на живой речи и откатывали целиком. Предел вендора применяет реестр (`SttKeyterms::accepted`) у ВСЕХ транспортов, включая WebSocket Deepgram — иначе пресет длиннее лимита давал 400 на каждой записи.

**Что выводится само:** селект «Провайдер распознавания» в лаунчере и группа «Голосовая модель» в `ModelCommandMenu` (обе из константы `STT_PROVIDERS` в `bindings.ts`), замок «нет ключа», кламп неизвестного значения в `Settings::clamp`, пересборка клиента при смене ключа или языка, доступность перевода. **На фронт уезжает только то, что нужно пикеру** — `id`, `label`, `keyId`, `supportsTranslate`; `wire` и `key_label` помечены `#[specta(skip)]`, и `contract.test.ts` проверяет это списком ЗАПРЕЩЁННЫХ полей (адреса, пути, модели), а не разрешённых, чтобы тест не падал от каждого нового поля пикера.

**Инварианты под тестами:** `stt/registry/tests.rs` — конформанс-набор для каждой строки (непустые поля, https-хост, пути с ведущим слэшем, у OpenAI-диалекта распознавание и перевод не делят эндпоинт, уникальные id, `resolve` неизвестного → дефолт, диалект обслуживает больше одного вендора) плюс проверка формы строки на вымышленном вендоре; `stt/tests.rs` — wiremock-тесты, читающие ожидаемые пути и модели ИЗ реестра. Живая диагностика на настоящем звуке — `examples/stt_smoke.rs`: прогоняет один WAV по ВСЕМ вендорам реестра через `stt::build_engine` (то есть и по Deepgram), подхватывая ключи по соглашению `<KEY_ID>_API_KEY`.

**Окна создаются ТОЛЬКО с главного потока.** `launch_main_window`/`stop_main_window` — асинхронные команды, и всё их тело уходит в `window::on_main_thread` (`run_on_main_thread` + `oneshot`, результат дожидается await'ом, поэтому главный поток не блокируется и дедлока нет). Причина не косметическая: на Windows создание WebView2 ждёт прокачки очереди сообщений своего потока, а команды Tauri исполняются НЕ на главном потоке — из рабочего потока `WebviewWindowBuilder::build()` не возвращается никогда. Снаружи это выглядит так: HWND появился (белое окно без содержимого), команда висит, лаунчер не уничтожается, кнопка навсегда в состоянии «Запускаю…». На macOS то же самое молча маршалится на главный поток, поэтому баг платформенный и локально невидим. Окно лаунчера при старте создаётся в `setup_app`, то есть уже на главном потоке — потому и работало, когда HUD не открывался.

**`device_event_filter(Always)` в `lib.rs` — не оптимизация, а условие работы перехвата стрелок на Windows.** По умолчанию tao регистрирует raw input на клавиатуру и мышь, и пока сфокусировано НАШЕ окно, каждое нажатие дополнительно грузит главный поток сообщением `WM_INPUT` с принудительной перерисовкой. Колбэк низкоуровневого хука живёт на том же потоке и обязан уложиться в `LowLevelHooksTimeout`; не уложился — Windows снимает хук молча и навсегда, без права узнать об этом. Отсюда симптом «стрелки не работают совсем, но только когда окно активно» ([tauri#13919](https://github.com/tauri-apps/tauri/issues/13919)). `Always` снимает регистрацию целиком (`Never`, вопреки названию, наоборот расширяет её на нефокусное состояние), а `DeviceEvent` в Tauri всё равно никем не читается. По той же причине сам колбэк обязан оставаться дешёвым: решение принимается синхронно, а сдвиг окна и эмит `resize-key` уносятся с потока ввода (`handle_arrow_key` → `spawn` → `run_on_main_thread`).

**`tauri` обязан быть ≥ 2.11.5 (`tauri-runtime-wry` ≥ 2.11.4).** В 2.11.2 DPI-геттер течёт `HDC`, из-за чего у окна с `decorations: false` на Windows отзывчивость ресайза прогрессивно деградирует и не восстанавливается без перезапуска ([tauri#15569](https://github.com/tauri-apps/tauri/issues/15569)). Понижать версию нельзя.

**`lib.rs` — только сборка (≈100 строк): `run()`, `setup_app()` и передача `invoke_handler` из `bindings::builder()`.** Всё остальное разложено по модулям, каждый владеет своими `#[tauri::command]`'ами; новую команду клади в модуль по смыслу и добавляй в `collect_commands!` в `bindings.rs` (единственный список). Реэкспорт-шимов (`pub use app_state::App`, `pub use window::…`) в `lib.rs` намеренно нет — зови модуль по полному пути, иначе `lib.rs` снова начнёт обрастать поверхностью.

Доменные модули (`audio`, `capture`, `stt`, `llm`, `state`, `settings`, `error`) остались как были — они не знают про Tauri. The domain modules are pure and unit-tested. **Юнит-тесты живут отдельно от кода**: в конце `src/<mod>.rs` — только объявление `#[cfg(test)] mod tests;`, тело — в `src/<mod>/tests.rs` (child-модуль, `use super::*` даёт доступ к приватному — поэтому НЕ интеграционные `tests/`, там виден только публичный API); новые тесты класть туда же, инлайновые `mod tests {}` не заводить. Тесты платформенного бэкенда — по той же конвенции этажом ниже: `src/<mod>/macos/tests.rs`.

**Платформенное расщепление — один приём на все модули.** `src/<модуль>.rs` — платформенно-нейтральный фасад со всей переносимой логикой, рядом `src/<модуль>/macos.rs` и `src/<модуль>/windows.rs`, подключаемые `#[cfg(target_os = ...)] mod ...; use ... as backend;`. Так расщеплены `capture`, `platform`, `screenshot`; остальные модули общие. **`#[cfg]`-ветку посреди общего кода не заводить** — платформенный вызов добавляется в ОБА бэкенда, второй при необходимости честной ошибкой или no-op (`disable_cursor_autohide_on_typing` в `platform/windows.rs`): иначе фасад начнёт знать про платформы и разъедется с контрактом (см. инвариант про одинаковый `bindings.ts`). Гейт по `cfg!` в общем коде остаётся только там, где это одно значение, а не ветка логики: `permissions::AUDIO_REQUIRES_PERMISSION = cfg!(target_os = "macos")`, `#[cfg(unix)]`-режим файла в `settings::create_owner_only`. **Платформенные крейты обязаны лежать в `[target.'cfg(target_os = "…")'.dependencies]`** (`cidre`/`objc2*`/`block2`/`plist` — macOS; `windows` 0.61 с явным списком features и `png` — Windows): в общем `[dependencies]` они не «просто тянут лишнее», а роняют сборку второй платформы. **А вот `[build-dependencies]` так гейтить НЕЛЬЗЯ: их `cfg` матчится по ХОСТУ сборки, а не по цели.** `cc` держим в общих build-зависимостях и гейтим только его ВЫЗОВ (`build.rs` компилирует C-оверлей и линкует Apple-фреймворки при `CARGO_CFG_TARGET_OS == macos`). Грабля неочевидна и локально невидима: на macOS-хосте `cfg(target_os = "macos")` в build-зависимостях истинен при любом `--target`, поэтому кросс-проверка Windows-сборки её не ловит — падает только настоящая сборка на Windows-раннере (`cannot find crate cc` в build.rs).

- `audio.rs` — downmix → resample (rubato, 48k→16k) → WAV (hound); RMS silence gate. `StreamResampler` — инкрементальный ресемплинг для стриминга (батчевый `resample_to_16k` идёт через него же — один код-путь, в проде не зовётся и живёт ради тестов и смоуков; к тому же rubato `process_all_into_buffer` дублирует первые `output_delay` фреймов, инкрементальный путь от этого бага свободен); параметры sinc намеренно «речевые» (`sinc_len=32`) — студийный 128 для 16кГц-Whisper уже отвергнут (~4x CPU впустую); `wav_header_streaming` (размеры 0xFFFFFFFF) + `f32_to_i16le_bytes` для тела стриминговой загрузки (заголовок подшивает `SttHttpClient`; конвейер отдаёт сырой PCM).
- `capture.rs` — захват системного звука: переносимый фасад + два бэкенда (**Core Audio process tap** через `cidre` на macOS, **WASAPI loopback** на устройстве вывода на Windows). Самый рискованный нативный кусок; подробности ниже отдельным разделом.
- `stt.rs` — `SttHttpClient`: **один multipart-клиент на всех вендоров OpenAI-диалекта и xAI**, различия между ними — не ветки, а строка в `stt::registry::PROVIDERS`; Deepgram (`stt/deepgram.rs`) — свой транспорт (WebSocket в реальном времени, батч сырым WAV) поверх того же порта, адреса и предел `keyterm` берёт из своей строки реестра. Транспорт выбирает `stt::build_engine` по диалекту строки, доступ (ключ или relay) — `app_state::stt_client_plan` по `Settings.stt_provider` (`::for_provider(id, key)` остался для тестов; прежние `SttVendor`-матчи в `model`/`endpoint`/`warm_up_endpoint`/`key_label`/`temperature` схлопнулись в чтение полей и обратно не возвращаются). Расходится по вендору немногое: base_url, эндпоинты (Groq — с префиксом `/openai/v1/…`, OpenAI — `/v1/…`; свой и у `warm_up`), модели (Groq `whisper-large-v3-turbo`, перевод — `whisper-large-v3`, turbo переводов не умеет; OpenAI `gpt-4o-mini-transcribe`, перевод — **обязательно `whisper-1`**: translations-эндпоинт OpenAI других моделей не принимает) и `temperature` — больше форма запроса у вендоров ничем не отличается: языковое поле единственное (`language`, как у Groq: множественного `languages[]` у 4o-поколения не существует) и не шлётся вовсе при `stt_language=""` (автоопределение) и при переводе (там язык определяет модель). `temperature=0` получает **только** Groq: для 4o-mini он не критичен, а для перспективного `gpt-transcribe` параметр не документирован — отправлять его наугад не надо (закреплено тестом `openai_transcribe_sends_gpt_4o_mini_with_language_and_no_temperature`). **Модель OpenAI-вендора выбрана живым A/B, а не по прайсу: `gpt-4o-mini-transcribe` — единственная из линейки, которая БЕЗ подсказок удерживает английские термины в русской речи латиницей**, ради этого второй вендор и заводился (Groq на смешанной речи их транслитерирует). На фразе «что такое мап в голанг» mini дала «Что такое Map в Go…», `gpt-transcribe` оставил «мап», `gpt-4o-transcribe` выдал «в голанде»; то же говорит независимый бенчмарк русской IT-диктовки (habr.com/ru/articles/1066528, авг 2026) — лучший облачный результат (Q 92.1), к тому же дешевле ($0.003/мин против $0.0045 у gpt-transcribe). «Обновление» на старшую модель линейки здесь регресс, а не улучшение, и проверять замену надо на СМЕШАННОЙ речи: на чистой русской или чистой английской фразе разницы не видно вовсе. **Биасинг терминами вернулся, но в другой форме — и разница принципиальна.** Отвергнут был СЛОВАРЬ: отдельная настройка, которую пришлось бы вести руками. Вместо него термины объявляются прямо в промпте строкой `[keywords]: [golang, gRPC, Kubernetes]` — в препромпте, в материале библиотеки контекстов или в контексте чата. Ведёшь ты их всё равно (написать список надо), но не отдельно от промпта, а внутри него, вместе с темой, к которой они относятся: у пресета «Golang» свои термины, у «DevOps» свои, и переключение пресета меняет их само. **Поля `stt_keywords` в `Settings` по-прежнему нет и заводить его нельзя** — это рантайм-состояние (`App.stt_keyterms`, команда `set_stt_keyterms`), а не настройка. **Тумблера тоже нет намеренно: написать блок — и есть включение.** Если mini перестанет хватать, лестница эскалации известна: `gpt-transcribe` с `keywords[]` (проверено, работает идеально) либо смена провайдера (ElevenLabs Scribe v2 / Gemini Transcribe — не интегрированы). `SttError::BadApiKey` несёт имя вендора (`&'static str`), чтобы «Неверный ключ Groq/OpenAI» указывал на тот ключ, который чинить; остальной error mapping общий. `transcribe_stream` — multipart с телом-стримом (chunked, длина неизвестна; Groq это принимает — проверено живым смоуком); его общий таймаут намеренно щедрый (11 мин): тело живёт всю запись (до 10 мин), обычный 60-секундный таймаут оборвал бы стрим. Таймаут батча (`transcribe`) растёт вместе с записью (`DEFAULT_REQUEST_TIMEOUT` + длительность аудио): десятиминутный WAV с инференсом в 60 с не укладывался. Таймаут при живой сети — `SttError::Retryable(408)`, а не `Network`: последнее поднимает оверлей связи, хотя сеть в порядке; отмена — `SttError::Cancelled` (код `cancelled`). У Deepgram свои дедлайны: хендшейк 10 с, отправка кадра 10 с, весь сеанс 11 мин — без них сетевой столл держал «Расшифровку» до TCP-таймаутов ОС; корни TLS для WebSocket читаются из системного хранилища один раз на процесс (`websocket_tls`, греется в `warm_up`), соединение идёт с `TCP_NODELAY`. Клиент пересоздаётся в `set_settings` при смене `stt_provider`, любого из двух STT-ключей, языка или перевода.
- `llm.rs` — Anthropic request body (image blocks; поле `thinking` готовит `thinking_value`, элемент `tools` веб-поиска — `web_search_value`, оба по capabilities модели; prompt-cache брейкпоинты на system и последнем сообщении; пустые сообщения выбрасываются из истории — API отвергает пустой content), incremental `SseParser` (байтовый фреймер: `feed_bytes` для сетевых чанков, многобайтовый символ на границе чанка дожидается хвоста внутри события; server_tool_use-события веб-поиска игнорируются — до UI доходят только текстовые дельты), streaming client with cancellation; тела ошибок API пробрасываются в UI (`error.message`, не голый HTTP-код). Диагностика тел запросов против живого API — `examples/llm_smoke.rs`.
- **Все reqwest-клиенты шлют `User-Agent`** (`llm::APP_USER_AGENT` = `AudioSystem/<версия>`; llm, stt, access): reqwest без UA попадает под Cloudflare Browser Integrity Check на прокси → интермиттентные `403 error code: 1010`; тела не-JSON ошибок теперь включаются в сообщение (`api_error_message` — сниппет до 120 симв).
- **Прокси `itech-relay` (Cloudflare Worker, репо `screenfriskofficial/itech-relay`).** Правки воркера деплоятся отдельно: `wrangler login` (интерактивно) → `wrangler deploy` (node ≥22, напр. `PATH=/opt/homebrew/opt/node@25/bin:$PATH`). Известные инварианты воркера: (1) **Рейт-лимитов на запросы нет** (снято 2026-07-21): лиз параллельности удалён (чаты приложения стримят одновременно), суточные капы = `MAX_SAFE_INTEGER` — учёт `usage_daily` продолжает вестись для `/admin/usage`, но никогда не отсекает; клампы не ниже клиентских значений (`max_tokens` 64000, `web_search max_uses` 10; клиент шлёт 64000/5). Остались только: IP-лимит на `/v1/redeem`, лимиты размера тела (LLM 32 МБ, STT 26 МБ) и allowlist роутов/моделей. upstream-`fetch` ОБЯЗАН иметь `signal: request.signal` — иначе при отмене клиента (кнопка «Стоп») воркер дочитывает генерацию до конца и владелец платит за полный ответ. (2) `/v1/messages/count_tokens` маршрутизируется явной веткой (без дебита) — нужен для индикатора заполненности контекста. (3) **Аудио-роутов пять, и вендор выбирается по пути**: `/openai/v1/audio/{transcriptions,translations}` → Groq, непрефиксные `/v1/audio/{transcriptions,translations}` → OpenAI, `/v1/stt` → xAI (`audioProviderForPath` в `providers/registry.ts`; секреты `OPENAI_API_KEY` и `XAI_API_KEY`). **`/v1/responses` делят OpenAI и xAI**, и разводит их не путь, а запрошенная модель (`responsesProviderForModel`, префиксы — тем же приёмом, что уже жил в `quota/profiles.modelAllowlist`): префикс пути тут завести было нельзя, он сломал бы симметрию, на которой держится незнание клиента о прокси-режиме. Новая модель Grok правки воркера не требует, незаявленный префикс остаётся за OpenAI. Пути на прокси **симметричны upstream'у** (`/v1/audio/transcriptions` у relay = тот же путь на `api.openai.com`), поэтому `SttHttpClient` про прокси-режим не знает ничего, кроме подменённого base_url — переписывания путей нет ни на одной стороне, и заводить его нельзя. Удаление любой из четырёх веток молча ломает распознавание у всех, кто в режиме кода доступа выбрал соответствующего вендора: до приложения доедет `not_found` воркера вместо текста, а вторая половина пользователей ничего не заметит. Побочный эффект той же симметрии: `warm_up()` OpenAI-вендора в прокси-режиме уходит на `/v1/models`, то есть в anthropic-каталог relay — ответ всё равно отбрасывается, греется только пул соединений. Оба reqwest-клиента (`stt`/`llm`) создаются один раз на весь рантайм, держат пул «вечно тёплым» (`http2_keep_alive_*`, `pool_idle_timeout(None)`) и имеют `warm_up()`; прогрев зовётся на старте приложения и на нажатии PTT (Anthropic; STT-клиент на PTT не греется — стриминговый запрос уходит сразу). В командах клиент клонируется из state (clone шарит Arc пула) — в том числе чтобы не держать MutexGuard через `.await`. Перф-тайминги пишутся в stderr с префиксом `[perf]`.
- **Стриминговая транскрипция.** На нажатии PTT `on_ptt_pressed` открывает запрос к выбранному STT-провайдеру (`App.stt_stream`), тело наполняется 16кГц-чанками через sink капчера (`ChunkCoalescer` склеивает кадры по ~21 мс в чанки по ~100 мс и досылает хвост в `Drop`); на отпускании `finish_transcribe` ждёт уже идущий запрос («отпустил → текст» ≈ инференс + RTT), но не дольше `STREAM_FINISH_TIMEOUT` (60 с) — дальше фолбэк на батч. **События PTT (нажатие, отпускание, Esc, вотчдог) идут через одну очередь `recording::PttEvent` и один воркер на blocking-пуле** — раньше каждое уходило своей задачей, и короткий тап, чьё «нажато» задержалось на пересборке капчера, обрабатывал «отпущено» раньше «нажато». Пересборка капчера (`request_capture_rebuild`) уходит на blocking-пул и решается под `recorder`-локом (раньше между проверкой «свободен» и подменой успевало пройти нажатие, стартовавшее запись на тут же дропнутом капчере); `capture.is_dead()` на нажатии тоже ведёт к пересборке. Задача расшифровки под надзором (`catch_unwind`): паника в ней раньше оставляла рекордер в «Расшифровка» навсегда. Пустая расшифровка — ошибка `silence` («слов не нашлось»), а не пустое событие. Отмена (Esc/тишина/короткая запись) — `cancel_stt_stream`; порядок при отмене записи обязателен: сначала `cancel_stt_stream`, только потом `capture.stop()`. При переполнении канала sink помечает стрим `broken`; любой сбой стрима (кроме `BadApiKey`/`BadAccessCode`) → фолбэк на классический `transcribe` по накопленному буферу (помеченный `broken` стрим, который уже успел завершиться — мгновенный 401, — сначала дочитывается: `settle_stream`/`stream_verdict`) — фича деградирует, но не ломает распознавание. На фронте `transcript-ready` ДОПИСЫВАЕТСЯ к черновику (`lib/composer.appendTranscript`), а не заменяет его; при `auto_send` уходит объединённый текст.
- `error.rs` — `ErrorCode`/`AppError` и трейт `CodedError` (реализуют `LlmError`, `SttError`, `CaptureError`); `AppError::from(&err)` = код + `Display`-текст. Всё, что уходит во фронт как ошибка, проходит через него.
- `state.rs` — recorder FSM (`Idle → Recording → Transcribing → Idle`); min 0.3s / max 10min, Esc cancel.
- `settings.rs` — JSON в `~/Library/Application Support/com.audioservice.helper/settings.json` (macOS) или `%APPDATA%\com.audioservice.helper\settings.json` (Windows), пишется атомарно через `create_owner_only`: режим `0600` ставится только под `#[cfg(unix)]` — на Windows POSIX-режимов нет и приватность даёт сама папка профиля (тест на права гейтится тем же `cfg`). `write_atomic_owner_only` делает `sync_all` перед `rename` — без fsync сбой питания оставлял на месте файла пустой. **Нечитаемый файл уходит в карантин** (`Settings::load_or_quarantine` → `settings.json.broken-<время>`), а приложение стартует с дефолтами: раньше любая ошибка чтения молча превращалась в дефолты, и первый автосейв лаунчера затирал ключи и пресеты; битая запись в `hotkeys` весь файл не валит (`hotkeys::drop_malformed_bindings`). `.env`-фолбэк ключей идёт по реестрам (`apply_key_fallback(lookup)` перебирает `key_id` обоих реестров, переменная `<KEY_ID>_API_KEY`; ключ вендора, которого relay проксирует, под кодом доступа не подставляется). `Debug` у `Settings` скрывает ключи и токен. Read-modify-write настроек — под `App.settings_edit` (`set_settings`, `redeem_access_code`, `clear_access_token`, `mark_requested`), и **`access_token` принадлежит бэкенду**: `set_settings` сохраняет токен из текущего состояния, а не из снимка лаунчера (снимок мог быть взведён до активации кода и стёр бы свежий токен, а код на relay уже потрачен); отвязка — отдельной командой `clear_access_token`. `chats::load` отдаёт `Err` на любую ошибку, кроме отсутствия файла: пустая строка читалась фронтом как «чатов нет» и первым сохранением затирала файл.

Найденный `Update` живёт в `App.pending_update` между check и install; повторный install блокирует `App.update_installing`; `pending_update` при установке клонируется, а не забирается — после неудачной установки повтор раньше отвечал «сначала проверьте новую версию». Прогресс троттлится `progress_step` (по смене целого процента) — как коалесинг `llm-delta`. Ошибка install уходит реджектом команды (отдельного события нет); `Settings.skipped_version` глушит только автобейдж, не ручную проверку. Релиз-пайплайн — `scripts/release.mjs` (ключ подписи `~/.tauri/itech.key`, **бэкапить**; порядок шагов — в самом `scripts/release.mjs`); он **двухплатформенный**: по умолчанию платформа берётся из `process.platform`/`process.arch`, собираются её артефакты, а если релиз с таким тегом уже есть — версия НЕ бампается и тег не ставится, скрипт доливает свои ассеты и вливает свою запись в существующий `latest.json` (ключи `darwin-aarch64` / `windows-x86_64`; `notes`/`pub_date` и чужие платформы берутся из скачанного манифеста, иначе вторая сборка затёрла бы первую; на Windows updater-артефакт и установщик — ОДИН файл, сам `-setup.exe`: `download_and_install` выбирает `WindowsUpdaterType::nsis` по расширению `exe`, отдельный `.nsis.zip` не нужен). Windows-бандл на macOS собрать физически нельзя, но **Windows-машина для релиза не обязательна**: `--windows-setup путь/к/setup.exe` берёт `-setup.exe`, собранный CI-джобой на windows-раннере, подписывает его локально (`npx tauri signer sign` тем же ключом — updater-подпись это minisign по байтам файла, машина сборки для неё безразлична) и заливает вместе со слитым манифестом; сборка в этом режиме пропускается, `resolveTarget` отдаёт Windows-хост и арки от `x64` мимо `process.platform`. Режим работает **только доливом** (нет релиза с таким тегом — понятная ошибка), и имя переданного файла обязано содержать `_<версия>_`: иначе установщик от чужой версии подписывается своим ключом и уезжает пользователям как обновление. **`shell: true` включается только для node-CLI** (`runNodeCli` вокруг `npm`/`npx`, флаг по `process.platform === "win32"`): на Windows `npm` — это `npm.cmd`, `CreateProcess` дописывает к имени только `.exe` и не находит его, а `.cmd`/`.bat` Node без `shell` запускать отказывается (фикс CVE-2024-27980) — из-за этого `execFileSync` падал с ENOENT и скрипт на Windows-хосте не отработал ни разу. На общий `run` шелл распространять НЕЛЬЗЯ: `gh release create --notes` получает многострочный текст с кавычками, и прогон через `cmd.exe` его порвёт. **Платформа, которой нет в `latest.json`, — не «нет обновлений», а ошибка на каждой проверке:** в `tauri-plugin-updater` 2.10.1 `Updater::check()` зовёт `get_urls(&release, &installer)?` ДО ветки `if should_update`, а тот перебирает ключи `{os}-{arch}-{installer}` и `{os}-{arch}` (`windows-x86_64-nsis`, затем `windows-x86_64`) и при отсутствии обоих отдаёт `Err(TargetsNotFound)` — то есть `check()` реджектится независимо от версии пользователя. Так баг и жил: в манифестах v0.9.0…v0.10.3 ключа `windows-x86_64` не было ни разу (установщик заливали в релиз руками, мимо скрипта), и обновления на Windows не приходили никогда. Увидеть это на Windows можно ровно одним способом: релизная сборка идёт с `windows_subsystem = "windows"` (`main.rs`), консоли нет и `eprintln!` автопроверки не виден нигде, поэтому **единственный канал диагностики — строка на экране «Обновления» лаунчера, и она обязана печатать текст ошибки** (`CheckState = "idle" | "checking" | "latest" | {failure}` в `UpdatesScreen`, `catch((e: unknown) => …String(e))` в `LauncherPanel` — идиома из `useUpdater.install`): безликое «Не удалось проверить обновления» без причины прятало отсутствие платформы среди любых других сбоев.

#### capture.rs — инварианты

Продюсер (RT-колбэк Core Audio на macOS, поток захвата WASAPI на Windows) пишет в lock-free ring buffer (`ringbuf`, без мьютексов/аллокаций); поток-консьюмер на лету даунмиксит+ресемплит в 16кГц, копит буфер и отдаёт чанки в опциональный `ChunkSink` (его дроп = EOF для стриминга). `stop()` возвращает готовый 16кГц-моно. Сигнатура — `AudioCapture::system(uid, buffer_secs)`. **У капчера есть `Drop` и протокол завершения**: сначала глушится продюсер (`Running`), потом консьюмеру выставляется `shutdown` и его тред ДЖОЙНИТСЯ — без этого каждая пересборка капчера (смена устройства, «Выдать», `capture_device_uid`) оставляла тред крутиться навечно вместе с кольцом на мегабайты. `rebuild_capture` подменяет капчер под локом `App.capture`, а дропает старый снаружи лока. Флаг `dead` (`is_dead()`): бэкенд отказал окончательно (сменился формат устройства на Windows) или консьюмер не ответил на `stop()` за 5 с — `start()` отказывает, `recording.rs` пересоздаёт капчер на следующем PTT; `start()` также отказывает поверх незавершённой сессии. Тесты протокола — `capture/tests.rs` через backend-free `assemble(spec, buffer_secs)` с фейковым продюсером.

**Вся переносимая часть живёт в `capture.rs`** (кольцо, консьюмер-тред, `Session`/`Shared`/`Scratch`, PTT-сессии, `run_buffering`, `RollingBuffer`, `OutputDeviceInfo`, публичные методы `SystemAudioCapture`), бэкенд обязан дать ровно четыре вещи, и **контракт `open`/`start` двухфазный не случайно**: `open(uid) -> (Source, StreamSpec)` открывает источник и СНАЧАЛА сообщает формат (`sample_rate`, `channels`) — от него зависят размер кольца и поля `Shared`, поэтому создать их до `open` нельзя; `start(source, ctx: Box<CallbackCtx>) -> Running` только запускает подачу сэмплов, а `Running` глушит захват в `Drop`; плюс `list_output_devices()` и `watch_default_output_device(handler)`. **Сэмплы попадают в кольцо только через `CallbackCtx::wants_samples()`/`push_samples()`** — гейт по `recording || buffering` и учёт `produced`/`dropped` живут в общем коде (`push_samples` кладёт только целые кадры: частичная запись при переполнении сдвигала бы раскладку каналов до конца сессии): на `produced` стоит `recording_secs()` (минимальная длительность записи и вотчдог 10 минут), а `dropped` виден только строкой `[perf]` в stderr, так что бэкенд, пишущий в кольцо мимо этих методов, ломает счёт длительности молча. Вариант ошибки — `CaptureError::Backend(String)` с платформой в тексте («Core Audio: …» / «WASAPI: …»), отдельного `CoreAudio` больше нет.

- **Порядок остановки обязателен:** сначала `recording=false`, потом дрен хвоста кольца. Флагом `recording` управляет только консьюмер (протокол `Session` + `stop_requested` исключает гонку «stop до пробуждения консьюмера»).
- **Порядок полей `Running` в `capture/macos.rs` — это порядок drop** (`_started` → `_tap` → `_ctx`; на `_ctx` ссылается C-колбэк): перестановка = use-after-free в IO-потоке. `unsafe impl Send` (тоже в бэкенде, а не на фасаде, с `// SAFETY`) отключает автопроверку компилятора — при добавлении полей пересматривать вручную; доступ — только под Mutex. `io_proc` берёт буфер тапа через `tap_buffer`: у aggregate-устройства с входом (гарнитура) входных буферов больше одного, и слепое `buffers[0]` могло писать микрофон вместо системного звука — тап узнаётся по числу каналов, при нескольких кандидатах берётся последний; паник в колбэке нет (неполный сэмпл и невыровненный буфер отбрасываются). Слушатель `on_default_output_device_changed` ловит панику `catch_unwind` — из `extern "C-unwind"` она раскрутилась бы в кадры HAL.
- **Windows-бэкенд (`capture/windows.rs`) — WASAPI loopback на устройстве ВЫВОДА** (`IAudioClient` + `AUDCLNT_STREAMFLAGS_LOOPBACK`, shared mode, mix format). **COM инициализируется в MTA, но `RPC_E_CHANGED_MODE` — это успех, а не ошибка**: tao/wry уже подняли STA на главном потоке, и `CoInitializeEx(MULTITHREADED)` оттуда возвращает именно этот код; трактовать его как отказ значит не поднять захват вообще ни разу (все входы — `list_output_devices`, `open`, `set_settings` — синхронные команды главного потока). В этом случае `CoUninitialize` звать нельзя — апартамент чужой. Через границу потоков COM-указатели не ездят: `open` резолвит устройство и возвращает **его конкретный id**, а клиент активируется заново уже в потоке захвата — иначе смена дефолта между `open` и `start` давала бы «формат изменился» на ровном месте. Старт синхронно рапортует об успехе/ошибке через канал — без этого `AudioCapture::system` возвращал бы Ok на сдохшем потоке и «Тишина» вместо ошибки доступа. Цикл **опрашивающий**, интервал выводится из `GetDevicePeriod`: событийный режим у loopback не сигналится, когда звук не играет, — на нём захват вставал бы до первого звука. Пакеты с флагом `AUDCLNT_BUFFERFLAGS_SILENT` дополняются нулями, иначе таймлайн рвётся и записанное съезжает. **Тишину приходится синтезировать самим**: loopback вообще не выдаёт пакетов, пока на устройство никто не рендерит, а `recording_secs()` считает время по числу сэмплов — без добивки нулями по настенным часам (`Timeline` в бэкенде) пятисекундное удержание PTT в тишине давало бы «запись слишком короткая», а вотчдог 10 минут не срабатывал бы никогда. Разрыв больше `MAX_SILENCE_GAP` (1 с) не догоняется, а списывается с переякориванием таймлайна, и таймлайн сбрасывается при каждом переоткрытии потока: иначе десятиминутное отсутствие устройства превращалось в одну аллокацию на сотни мегабайт в потоке захвата. **Поток захвата переоткрывает стрим сам**: `AUDCLNT_E_DEVICE_INVALIDATED` (выдернули гарнитуру) не убивает поток молча — он ретраится раз в секунду; а смена ФОРМАТА устройства (`ReopenFailure::Fatal`) с этим `StreamSpec` не откроется никогда — поток помечает капчер `dead` и выходит, следующий PTT пересоздаёт капчер (раньше ретрай шёл вечно, фасад оставался «живым» с нулевым таймлайном, и каждый PTT давал «запись слишком короткая»). Внутренний цикл дренажа сверяется с флагом остановки: `Running::drop` ставит флаг и **джойнит поток захвата** (ожидание `REOPEN_DELAY` нарезано на 50-мс шаги и сверяется с флагом), `rebuild_capture` дропает старый капчер вне лока `App.capture`, а дренаж обязан оставаться конечным. Формат проверяется на декодируемость (float32 / int16 / int32) при открытии — внятная ошибка лучше молчаливой тишины. `E_ACCESSDENIED` → `CaptureError::PermissionDenied`.
- **Отказ TCC не различим по коду ошибки (macOS):** Core Audio отдаёт `kAudioHardwareIllegalOperationError` ('!hog'), и именно он маппится в `PermissionDenied` — «более точного» кода нет. При отказе в state кладётся `None`, UI видит это через `permissions_status`. «Выдать» зовёт `request_permission("audio")` (пересоздание тапа, что триггерит TCC-промпт при статусе «не спрошено»), «Настройки» — `open_permission_settings("audio")`. `NSAudioCaptureUsageDescription` живёт в `src-tauri/Info.plist` и встраивается и в dev-бинарь — без него macOS не спрашивает, а молча отказывает.
- **Системный aggregate на macOS содержит только tap, без физических subdevices.** `capture_device_uid` выбирает конкретный выход для собеседника, `microphone_device_uid` — конкретный вход пользователя. Пустое значение означает явный вариант «Системный по умолчанию». Выбранное недоступное устройство не подменяется другим. На Windows используются те же настройки для WASAPI render/capture endpoints.
- **Захват привязан к устройству на момент создания** — сменился вывод → на macOS тап отдаёт нули («Тишина»), на Windows loopback остаётся висеть на старом эндпоинте. Следит за этим `capture::watch_default_output_device` (macOS — слушатель свойства `kAudioHardwarePropertyDefaultOutputDevice`, Windows — отдельный тред, раз в две секунды сверяющий id дефолтного эндпоинта: опрос выбран вместо COM-колбэка `IMMNotificationClient` сознательно — он не требует реализовывать COM-интерфейс и не добавляет unsafe-поверхности, а двухсекундная задержка на смене устройства незаметна), но **политика остаётся в `recording.rs` и в бэкенды не переезжает**: колбэк деферится в async runtime и пересоздаёт капчер при смене дефолта только когда uid="", при смене `capture_device_uid` в `set_settings`, а если рекордер занят — лениво на следующем PTT через флаг `capture_rebuild_pending`.
- **Режим непрерывной буферизации:** `set_buffering(true)` переводит консьюмер в цикл `run_buffering` с долгоживущим ресемплером (продюсер пропускает сэмплы по `wants_samples()`, то есть `recording || buffering`), каждый 16кГц-чанк уходит в `audio::RollingBuffer` под мьютексом. PTT-сессия при включённом буфере обслуживается тем же циклом: `take_pending_session` сбрасывает снимок буфера в аккумулятор и `ChunkSink` ДО живых чанков (преролл), rolling-лок берётся только после отпускания session-лока (**session- и rolling-локи никогда не держатся одновременно**), `finish()` ресемплера не зовётся (потеря хвоста ~20 мс речи при отпускании осознанна). При выключенном буфере путь консьюмера прежний. Буферизованная сессия тоже ведёт флаг `recording` (`take_pending_session` ставит, наблюдение стопа и финализация снимают) — гейт продюсера остаётся корректным при выключении тумблера посреди записи, а выход из режима буферизации чистит rolling на стороне консьюмера.
- Списки устройств для UI — `list_audio_devices`: отдельные `inputs`/`outputs` с `is_default`, перечисление не открывает микрофон. Native smoke macOS: `cargo run --example system_audio_smoke -- "AirPods Max"`, затем `-- "VB-Cable" --expect-silence` при выводе тестового тона в AirPods. Проверяет приход сигнала в выбранный выход и отсутствие в другом; без STT и сохранения записи.

### Раздельные источники PTT

`capture_system_audio` и `capture_microphone` — независимые переключатели. Старые конфиги сохраняют выбранный `capture_device_uid`; новый `microphone_device_uid` по умолчанию пустой. UI не выбирает устройство автоматически и не сбрасывает UID при пропаже из списка. Вариант «Системный по умолчанию» показывает текущее имя устройства. Есть обновление списка и предупреждение, что виртуальные устройства могут содержать уже смешанный звук. Разрешение микрофона запрашивается только явной кнопкой; открытие настроек и перечисление устройств не начинают запись.

`AudioCapture::system` и `AudioCapture::microphone` используют общий PCM-конвейер, но отдельные native streams. На macOS системный tap захватывает только выбранный output (`CATapDescription` с output UID, `exclusive=true`, пустым списком исключений), а его aggregate не содержит физических subdevices. `channels-in=0` в словаре физического subdevice не отключает входы; на Shure MV7+ он всё равно включал микрофон. При открытии проверяется отсутствие hardware subdevices и единственный tap-поток нужной ширины. Callback не угадывает источник по числу каналов и не использует fallback на микрофон.

Общий global tap не подходит для разделения при наличии микшеров: OBS может отправлять микрофон в VB-Cable, и этот вывод является частью системного звука, даже если пользователь его не слышит. Пример из диагностики: OBS Mic/Aux = Shure, monitoring_type=2 (Monitor and Output), мониторинг = VB-Cable. Для такого маршрута в приложении надо явно выбрать выход звонка (например AirPods) и вход микрофона (Shure). Это разделение по источникам, без голосовой диаризации и без удаления одинаковых фраз. Уже смешанный сигнал внутри одного выбранного устройства не разделяется; при акустическом попадании динамиков в микрофон нужны наушники.

На Windows используются раздельные WASAPI render/capture endpoints; микрофон открывается без LOOPBACK. На обеих платформах сохранённый недоступный UID вызывает ошибку вместо подмены устройством по умолчанию. Ошибка открытия системного захвата сохраняется в `App.capture_error`, чтобы отсутствие устройства не превращалось в ложную ошибку разрешения. Микрофон открывается только во время PTT, без pre-roll; вход фиксируется на всю запись. Системный pre-roll сохраняется, при смене выхода capture пересоздаётся.

`RecordingSession` владеет микрофоном, потоками STT и снимком engine/keyterms. `AudioCapture::finish` закрывает микрофон до ожидания дренажа. Выход в launcher запрещает новые записи, отменяет распознавание и передаёт StopSession последовательному PTT worker. RAII отменяет транспортные задачи при завершении и ошибках. `RecordedAudio` хранит отдельные PCM и результаты каналов: распознавание параллельное, паники изолированы по каналам, успех кешируется при ошибке второго. Retry обрабатывает только недостающий результат. После успешной доставки PCM освобождается. Один структурированный `transcript-ready` публикуется после завершения каналов; frontend добавляет локализованные метки и копирует тот же текст.

Источники: [Apple Core Audio taps](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps), [VB-Cable routing](https://vb-audio.com/Cable/), [Microsoft capture](https://learn.microsoft.com/en-us/windows/win32/coreaudio/capturing-a-stream).

### Сохранение, восстановление клиентов и обработка потоков

- `write_atomic_owner_only` пишет через отдельный `NamedTempFile` в папке назначения, синхронизирует файл и атомарно заменяет назначение. Общий `<имя>.tmp` запрещён: параллельные сохранения чатов могли обрезать один временный файл или продолжить писать в него уже после переименования. Ошибка публикации удаляет временный файл; Unix-права — `0600`.
- Восстановление HTTP-пулов после офлайна берёт `settings_edit` на чтение настроек **и** публикацию клиентов. Без этого оно могло вернуть старые ключи после успешного `set_settings` / активации / отвязки кода.
- Новая версия пула пресетов сохраняется даже при неизменном содержимом: иначе последующая промежуточная версия могла откатить текст. Импорт читает не больше лимита + 1 байт независимо от предварительной проверки размера; лимит base64 учитывает padding, чтобы PDF ровно 20 МиБ не отклонялся.
- SSE-фреймер сохраняет позицию поиска, перечитывает только возможный хвост разделителя и сдвигает буфер один раз на сетевой чанк. Пустые `data:`-строки сохраняют переводы строк в полезной нагрузке.
- Последняя запись и батч-запрос используют один `Arc<[f32]>`; повторная попытка не копирует весь звук под мьютексом. Оба пути распознавания проходят `supervise_transcription`: паника провайдера превращается в ошибку и освобождает рекордер.

## Non-obvious invariants (do not break these)

### Чаты и библиотека контекстов

**Чаты независимы и параллельны.** Источник истины — фронт (`useChats`: `Chat[]` + `activeId`); Rust хранит чаты как непрозрачную JSON-строку в `chats.json` (атомарно, `0600`, модуль `chats.rs`, команды `load_chats`/`save_chats`; `load_chats`/`load_context_library` реджектятся при любой ошибке чтения, кроме отсутствия файла — фронт тогда не взводит `loaded` и ничего не пишет поверх; тост об этом фронт пока не показывает). `send_to_claude(messages, chat_id, system, model, options)` шлёт всю историю чата; отмена по-чатная через `Mutex<HashMap<chat_id, ActiveLlmStream {stream_id, cancel}>>`.

**У каждого запуска стрима есть `streamId`, и его генерирует ФРОНТ** (`crypto.randomUUID()` в `useClaudeStream.send`), а не Rust: источник истины по чатам и так фронт, а знать идентификатор нужно ещё до первого события. Он едет параметром `send_to_claude(messages, chat_id, stream_id, …)`, кладётся в реестр отмены рядом с токеном и возвращается в КАЖДОМ LLM-событии. Сверяют его три места, и каждое закрывает свою дыру: (1) `useClaudeStream` игнорирует событие, чей `streamId` не совпадает с текущим для чата; (2) `cancel_stream(chat_id, stream_id)` отменяет, только если в реестре лежит именно этот стрим; (3) `unregister_llm_cancel` снимает запись только свою. Без этого «Стоп → сразу новая отправка» ломалось трижды подряд: `cancel_stream` — команда fire-and-forget и успевала приехать ПОСЛЕ нового `send_to_claude`, то есть отменяла свежий стрим; `register_llm_cancel` вытеснял токен, старый стрим отдавал `llm-done`, фронт списывал его на новый и коммитил пустое сообщение; а завершавшийся старый стрим ещё и выкидывал из реестра токен нового, делая тот неотменяемым. Прежний фронтовый счётчик `staleCompletions` (глотал ровно одно «лишнее» завершение) удалён — он лечил симптом и по построению не различал, чьё событие пришло. Чистые хелперы реестра (`replace_stream`/`take_stream`) вынесены отдельно и покрыты тестами в `chat/tests.rs` — сверка id проверяется без Tauri-хендла. **Отправленные картинки видны в пузыре сообщения** — `MessageImages` внутри `UserBubble` (`AnswerPanel`), источник `ChatMessage.images`, data-URL собирает `composer.imageDataUrl`. Долгое время их рисовал только композер (чип вложения), а пузырь принимал один `text`: картинка уезжала в запрос, ответ приходил осмысленный, но в истории её не было — выглядело как «модель видит то, чего нет на экране». Картинки в `chats.json` при этом НЕ сохраняются (стрипаются в `serializeChats`), поэтому после перезапуска у старых сообщений остаётся только текст — это цена компактности файла, а не баг рендера; текстовый `context` чата — сохраняется; `libraryDocIds` — сохраняется, старые чаты без поля → `[]`. Лимит — `CHAT_LIMIT = 6`. **Дублирование чата копирует параметры, но НЕ содержимое** (`createChatFrom` в `lib/chats.ts` → `useChats.duplicateChat`; кнопка `CopyPlus` в `ChatTabs` стоит сразу за «+», гаснет на лимите вместе с ним и дублирует всегда АКТИВНЫЙ чат): переезжают пресет, модель, thinking, web search, `context` и `libraryDocIds` (последний — копией массива, два чата не должны делить одну ссылку), а история, черновик с вложениями, индексный заголовок и `lastInputTokens` остаются дефолтами нового чата — «дубликат» здесь значит «те же настройки, чистый разговор», а не клон переписки. Переключение на новый чат стоит **внутри апдейтера `setChats`** (тот же приём, что в `removeChat`), а не рядом с ним, как в `newChat`: иначе на no-op — упёрлись в `CHAT_LIMIT` или `sourceId` не нашёлся — `activeId` уехал бы на несозданный чат, и тогда ни одна вкладка не подсвечена, композер по фолбэку `active` правит `chats[0]`, а фантомный id ещё и оседает в `localStorage`. С клавиатуры то же самое даёт действие реестра `duplicate_chat` (дефолт ⌘⇧N / Ctrl+Shift+N), и **оно ГЛОБАЛЬНОЕ** (scope Global, строка в `GLOBAL_HOTKEYS`): чаты живут во фронте, поэтому Rust-обработчик `window::on_duplicate_chat` сам чат не создаёт — он зовёт `show_and_focus_prompt` (поднимает скрытое окно) и эмитит `duplicate-chat`, а фронт по событию зовёт `duplicateActiveChat`. Вебвью-слушателя клавиш у действия больше НЕТ и заводить нельзя — глобальный шорткат съедает нажатие до вебвью, второй слушатель был бы мёртвым. Мотив глобальности — решение владельца «создавать чат должна быть возможность всегда»: из скрытого окна, из чужого приложения, из мини-режима. Оба пути — кнопки «+»/дубликата в табах и событие — идут через общие `createChat`/`duplicateActiveChat` в App: создание разворачивает мини-режим (`setMiniMode(false)`) и ставит каретку в поле — `focusPromptSoon` (rAF + `focus()`; из мини фокус добивает mount-эффект `usePromptFocus` после ремоунта Composer; под суфлёром/оверлеем сети попытку фокуса штатно гасит его гейт подавления). В `useWindowControls` обработчик намеренно НЕ встроен — тот отвечает за окно и отправку, управление чатами не его зона.

**Дебаунс-сохранение на диск (500мс) включается только после завершения первичной загрузки** (флаг `loaded` в `useChats`) — иначе стартовое пустое состояние перезаписало бы сохранённые чаты. Тот же инвариант — в `useContextLibrary`.

**Несохранённый хвост сбрасывает НЕ размонтирование React, а явный `flush()` перед уходом из HUD.** `useChats`, `useContextLibrary` и `useSettings` отдают наружу `flush(): Promise<void>` (пишет, только если запись реально отложена), а `App.leaveToLauncher` ждёт все три через `Promise.all` (не `allSettled`: после неудачной записи окно остаётся открытым с тостом, иначе `stop_main_window` уничтожил бы вебвью вместе с несохранённым) и лишь потом зовёт `stopMainWindow`. Дебаунс-персист снимка у чатов и библиотеки один — `hooks/useDebouncedPersist.ts` (`markLoaded` после чтения с диска, чтобы первое сохранение не перезаписывало только что прочитанный файл; оба пути — таймер и unmount — ведут ошибку в `onSaveError`); `useSettings` держит свой патч-дебаунс, но ошибку ловит так же. Клинап-эффекты остались вторым рубежом, но **в проде они не срабатывают**: `window::swap_to_launcher_window` и `swap_to_main_window` убивают вебвью через `w.destroy()` (не `close()`), а `close_app` — через `app.exit(0)`, то есть React-клинапы не выполняются и `beforeunload`/`pagehide` не приходят. Полагаться на размонтирование как на канал сохранения нельзя; ждать промисы обязательно — `invoke` без await мог не доехать до Rust раньше `destroy()`. Остаточный случай, который так не закрывается, — выход по ⌘Q мимо кнопки «Стоп»: там нет ни одной JS-точки, и закрыть его можно только со стороны Rust.

**Активный чат переживает выход и лежит в `localStorage` (`active-chat-id`), а не в `chats.json` и не в `Settings`** — оба «очевидных» места отвергнуты по конкретным причинам. В `chats.json` нельзя: его корень — голый массив, и чтобы дописать туда `activeId`, пришлось бы завернуть его в объект; старая версия приложения прочитала бы такой файл как «чатов нет» (`!Array.isArray` → `null`) и затёрла бы их первым же сохранением — потеря данных при откате. В `Settings` нельзя: чаты и настройки грузятся независимыми асинхронными запросами, и при «настройки приехали позже чатов» пришлось бы задним числом переключать чат под уже кликнувшим пользователем. `localStorage` в проекте уже используется (ключи идемпотентности redeem), переживает пересоздание HUD и не трогает ни один контракт. Запомненный id проверяется на существование среди загруженных чатов (`rememberedActiveId`) — удалённый чат откатывает на первый, а не оставляет пустой экран.

**Библиотека контекстов** — отдельный файл `context-library.json`, тот же паттерн, что chats.json: Rust хранит непрозрачный JSON через `chats::load/save`, команды `load_context_library`/`save_context_library`; модель и (де)сериализация — `lib/context-library.ts`, битые `folderId` чинятся в корень, тексты клампятся `DOC_TEXT_LIMIT_CHARS`. UI — экран «Контексты» лаунчера (`ContextLibraryPanel`, правки применяются сразу через свои команды, мимо draft/автосейва лаунчера); выбор материалов в чате — диалог «Контекст» Composer (чекбоксы + свой текст).

**Импорт файлов** — пикер (`input type=file`) и drag-and-drop из файлового менеджера ОС (в подписи «из Finder» / «из проводника» — по платформе):

- HTML5-drop для файлов ОС в Tauri НЕ работает (webview перехватывает) — используется `getCurrentWebview().onDragDropEvent` (обёртка `ipc/events.onFileDrop`, физпиксели → CSS через devicePixelRatio), папка-цель — `elementFromPoint` по атрибуту `data-drop-folder`.
- Типы — **.md/.markdown/.txt и .pdf** (`context_import.rs` диспетчеризует по расширению): текст читается `read_to_string` (лимит 1 МБ), PDF — `pdf-extract::extract_text_from_mem` в `catch_unwind` (битый PDF не должен ронять процесс; лимит 20 МБ), затем `normalize_extracted_text` (CR/form-feed → `\n`, схлопывание пустых строк, trim). Пустой результат = скан без текстового слоя → ошибка `ERR_PDF_NO_TEXT` (OCR нет). Извлечённый текст всё равно клампится `DOC_TEXT_LIMIT_CHARS`.
- Пути: drop даёт реальный путь → `read_context_import_file(path)`; у пикера реального пути нет ни в WKWebView, ни в WebView2 (`File.text()` для текста, PDF — `File.arrayBuffer()` → `lib/base64.arrayBufferToBase64` → `read_context_pdf_bytes(dataBase64)`). Обе команды парсят в `tokio::spawn_blocking` (парс 20 МБ не блокирует рантайм).
- Перенос материалов между папками — кастомный pointer-драг (`useDocDrag`: mousedown+порог 5px → mousemove → `moveDoc` по `data-drop-folder` под курсором), НЕ HTML5 draggable — внутристраничный HTML5-dnd в Tauri-вебвью ненадёжен.
- **PTT обязан работать при фокусе в поле промпта.** `usePttSuspend` глушит PTT при фокусе в текстовых полях ТОЛЬКО для хоткеев, конфликтующих с печатью (`conflictsWithTyping`: одиночная буква/цифра, в т.ч. с Shift). F-клавиши и комбинации с Cmd/Ctrl/Alt не глушатся никогда — не возвращай безусловную заглушку. **Подписка обязана смотреть на текущий `document.activeElement`, а не только на будущие `focusin`/`focusout`.** С автофокусом поля (`usePromptFocus`) прежняя редкая гонка стала детерминированной: на маунте настройки ещё дефолтные (PTT = `F9`, `conflictsWithTyping` ложна, эффект выходит рано), поле уже сфокусировано, а когда настройки догрузятся с диска и у пользователя PTT на одиночной букве — слушатели встанут уже ПОСЛЕ `focusin`, суспенда не будет, и буква начнёт запись вместо печати. Проверка на подписке намеренно односторонняя: глушим, только если поле уже в фокусе, а `setPttSuspended(false)` там НЕ зовём — эта команда заново регистрирует глобальный PTT (`preferences::set_ptt_suspended` → `register_ptt`), то есть каждое пересоздание эффекта давало бы лишнюю перерегистрацию.
- **Hotkey handlers must defer all work.** `tauri-plugin-global-shortcut` invokes the handler while holding its registry mutex; doing register/unregister synchronously inside (e.g. registering Esc) is a re-entrant deadlock that hard-freezes the app. `hotkey.rs` wraps handlers in `defer()` (spawns onto the async runtime). The same applies to anything a handler triggers.
### Режимы HUD: чат и заметки

**Режим — не булев флаг, а строка реестра `lib/modes.ts`** (`APP_MODES`: `chat` — дефолт, `notes`). Переключение — `nextMode` по кругу, поэтому третий режим = строка в реестре плюс иконка в `MODE_ICONS` (`ModeSwitch`); `Record<AppModeId, LucideIcon>` заставляет компилятор потребовать иконку ровно так же, как `Record<SettingsTabId, ReactNode>` требует секцию у таба настроек. Состояние живёт в `App` и НЕ персистится: приложение всегда стартует в чате (как vim в normal mode), поля в `Settings` под это нет и заводить не надо. **Переключатель стоит внутри пилюли дока действий, слева от «☰»** — слотом `leading` у `ToolbarDock`, отделённый вертикальной чертой. Отдельной пилюлей у орба он уже стоял и был отвергнут владельцем: там он соревновался за место с табами чатов. Прятать его пунктом внутрь дока тоже нельзя — переключение режима обязано быть видно всегда, а не через открытие меню. Хоткей — действие реестра `toggle_mode` (дефолт ⌘⇧L / Ctrl+Shift+L, `scope: hud`, строки в `GLOBAL_HOTKEYS` у него нет и быть не должно), и он же светится чипом в тултипе обеих кнопок. Табы чатов в режиме заметок НЕ прячутся намеренно: кнопка «в контекст» кладёт заметку в АКТИВНЫЙ чат, и без табов было бы непонятно, в какой.

**Заметки — это библиотека контекстов, второго хранилища нет.** Режим читает `useContextLibrary` (тот же `context-library.json`, те же папки), поэтому найденный поиском материал одним кликом уезжает в `chat.libraryDocIds` — то самое поле, что правит диалог «Контекст» композера. Импорт (пикер и drop из ОС) переиспользуется, а не копируется: `hooks/useLibraryImport` (файл → текст → `addDoc`, ошибка в своём стейте) и `hooks/useLibraryFileDrop` (подписка `onFileDrop` + подсветка цели, возвращает id папки под курсором) живут снаружи лаунчера и делят с ним `lib/library-drop` (`data-drop-folder` + `dropTargetAt`). В HUD цель всегда корень: папки правит экран «Контексты», в заметках их не создают. Подписка на drop стабильна (`useLatestRef` внутри хука) — в лаунчере она пересоздавалась на каждый рендер панели, потому что зависела от объекта `ContextLibraryApi`.

**Поиск — MiniSearch** (`lib/notes-search.ts`), тот же движок, что у Obsidian Omnisearch: `prefix: true` (ищет по началу слова), `fuzzy: 0.2` (прощает опечатку), `combineWith: "AND"` (второе слово сужает выдачу), название весит вчетверо против текста. Три неочевидных решения. (1) **Индекс строит `useNotesIndex` лениво и держит между переключениями режима** — он собирается при первом входе в заметки и пересобирается только на смену `docs`; собирать его на каждый ⌘⇧L значит платить видимый фриз на большой библиотеке. (2) **Свёртка `foldForSearch` (регистр + `ё`→`е`) обязана сохранять длину строки** и идёт одна и та же в `processTerm` MiniSearch и в подсветке: цитата ищет позиции в свёрнутой копии, а режет исходную — сдвиг индексов сломал бы `<mark>`. Поэтому `toLowerCase()` применяется посимвольно и откатывается, если символ поменял длину (турецкая `İ`). (3) **Подсвечиваются `result.terms`, а не слова запроса** — MiniSearch отдаёт именно те слова документа, которые совпали, поэтому префиксный и нечёткий хит подсвечиваются целым словом. Цитата и счётчик совпадений — `lib/notes-excerpt.ts` (окно вокруг первого совпадения, схлопнутые переносы, многоточия по краям).

**Поиск — омнибокс с подсказками, а не фильтр экрана.** Ввод в поле НЕ перестраивает то, что под ним: выдача (`NoteSuggestions`) выпадает отдельным слоем под полем, а список библиотеки или открытая заметка остаются на месте — это прямо тот сценарий, ради которого режим и делался: читаешь одну заметку, ищешь вторую. Три грабли зашиты в код. (1) **Обёртка поля обязана быть `relative z-20`** — ровно как обёртка шапки лаунчера: выдача лежит внутри неё, а экран идёт в DOM позже и без поднятого слоя рисовался бы поверх подсказок. (2) **Закрытые подсказки возвращает `↓`, а не фокус поля.** Реоткрытие по `onFocus` выглядит очевидным и ломается: клик по подсказке уводит фокус на кнопку, `openNote` возвращает его в поле, приходит `focus` — и список, только что выбранный мышью, открывается снова. (3) **Подсказки — только переход**: кнопки «в контекст» в них нет намеренно, она живёт в списке библиотеки и в шапке читалки, иначе выдача превращается в панель с двумя разными действиями на строку. Список под полем — `NoteBrowseList`, разложенный по папкам (те же `rootDocs`/`docsInFolder`, что в лаунчере), и цитаты в нём не рисуются: цитата — это про совпадение, а не про заметку.

**Гейты режима — то же правило, что у мини-режима: не показываем поле ввода, значит не даём в него писать.** `promptUnavailable` включает заметки, поэтому каретка уходит из промпта (`usePromptFocus` делает `blur`), а быстрые действия и меню моделей гаснут. Отправка гейтится ОТДЕЛЬНО в `App.sendFromHotkey`: `useWindowControls` слушает ⌘⏎ на уровне документа и без гейта отправлял бы невидимый черновик прямо из заметок. Обратный ход — `revealChat` (`setMiniMode(false)` + режим в `chat`), и его зовут ВСЕ пути, кладущие текст в промпт: готовая расшифровка, снимок области, создание и дубликат чата. Сам переключатель гейтится своим `modeSwitchAvailable` (не `promptUnavailable`!) — иначе из заметок нельзя было бы вернуться хоткеем.

**`Escape` в заметках — поведение виджета, а не команда реестра** (как у дока действий и у переименования папки) и идёт ШАГАМИ: закрыть подсказки → закрыть заметку → очистить запрос → выйти в чат. Действие и `scope: notes` под это не заводились намеренно — иначе пришлось бы разводить его с `Escape` записи, суфлёра и стрима в ОБЕИХ реализациях конфликтов, рустовой и фронтовой. Видимость даёт `fieldHints` в `lib/hotkeys.ts`: группа «Заметки» получает подсказки ↑↓ / ⏎ / Esc там же, где группа «Отправка» получает ⏎ и ⌘V.

**Разметка рендерится из одного места.** `components/markdown-config.ts` (плагины rehype, компоненты, класс прозы) плюс `components/MarkdownChunk.tsx` делят чат и читалка заметок; `makePre` с чипом HTML-превью остался в `AnswerPanel` — он завязан на инвариант `plainText: ["html", "system-design"]` и к заметкам отношения не имеет. Подсветки совпадений ВНУТРИ открытой заметки нет: она рендерится markdown'ом, а вставлять `<mark>` в дерево rehype значило бы трогать тот же инвариант; вместо неё в шапке читалки стоит счётчик совпадений.


### Управление окном идёт через Rust-команды, не через JS

`set_window_size`, `close_app`, `hide_main_window`, позиция и видимость окна — Rust-команды и обработчики хоткеев (нативный монитор стрелок зовёт `set_position` напрямую). JS-путь вроде `getCurrentWindow().setSize()` **молча не работает без соответствующего разрешения** в `src-tauri/capabilities/default.json`, поэтому по умолчанию предпочитай Rust-команду; реально нужна возможность из JS — сначала добавь разрешение туда. Из сеттеров явно выдан ровно один, `core:window:allow-start-dragging` под `startWindowDrag`, — это единственный прямой вызов Tauri-API окна из фронта; **разрешения-сеттеры «про запас» не держим**: `set-position`/`show`/`hide` были выданы явно, но из JS не звались ни разу, и удалены. Геттеры (`scale-factor`, `outer-position`, `inner-size`/`outer-size`, `current-monitor`) входят в `core:window:default`, то есть уже в `core:default`, и перечислять их отдельно не надо — `onWindowResized` со своим `scaleFactor()` работает, хотя `allow-scale-factor` в capability никогда не значился (а `allow-outer-position` там был просто избыточен и тоже удалён). Состав набора сверяй по сгенерированному `src-tauri/gen/schemas/acl-manifests.json`, а не на глаз. Окна перечислены поимённо (`"windows": ["main", "launcher"]`) — окно, забытое в этом списке, не получит даже `core:default`, и любой `invoke` из него будет отвергнут.

**«Поднять HUD и поставить каретку в поле» — одна функция, `window::show_and_focus_prompt`** (`show()` + `set_focus()` + эмит `focus-prompt`; эмит стоит внутри `if let Some(w)` — нет окна `main`, некому и фокусироваться). Её зовут возвраты в ввод: `screenshot::deliver`, обработчик глобального хоткея `focus_prompt` и `on_duplicate_chat`; `on_toggle_mini` (глобальный хоткей скрыть/показать) лишь показывает скрытое окно и эмитит `toggle-mini`, каретку не трогает. Четвёртый случай, запуск HUD, **намеренно не отсюда**: окно создаётся раньше, чем вебвью успевает подписаться на события, и эмит ушёл бы в никуда — на старте каретку ставит эффект маунта во фронте. **Пятый случай — готовая расшифровка — эмитит событие ГОЛЫМ, мимо `show_and_focus_prompt`** (`recording::deliver_transcript`, сразу за `transcript-ready`): окно при этом не поднимается намеренно, потому что PTT спроектирован работать, когда пользователь в ДРУГОМ приложении, и дёргать HUD вперёд после каждой записи значило бы ломать ровно тот сценарий, ради которого хоткей и сделан глобальным — каретка просто встаёт в поле, а поднимать окно пользователь решает сам. Точка выбрана единственная общая для обоих путей транскрипции (стриминговый и фолбэк по накопленному буферу) и не задевает отмену, тишину и ошибки — они идут мимо `deliver_transcript`. Отвергнутая альтернатива событию — слушать во фронте `tauri://focus`: фокусировать поле на ЛЮБОЙ активации окна значит рвать выделение текста в ответе и клики по кнопкам при возврате мышью, а главный случай («окно уже активно, нажали хоткей») так не покрывается вовсе; обрабатывать сам хоткей во фронте тоже нельзя — глобальный шорткат регистрируется только в Rust, а keydown в вебвью не приходит, когда окно не в фокусе.

**Меряем и применяем ОДИН И ТОТ ЖЕ размер — внутренний.** `set_window_size` берёт текущий размер через `inner_size()`, потому что применяет его `set_size`'ом, а тот задаёт именно внутренний размер; события `onWindowResized` во фронте тоже несут внутренний. Стоит взять здесь `outer_size()` — на macOS ничего не заметно (у фреймлесс-окна рамки нет, внешний равен внутреннему), а на Windows у ресайзабельного окна остаётся рамка `WS_THICKFRAME`, разница в несколько пикселей, ранний выход по эпсилону не срабатывает НИКОГДА, и на каждое изменение настроек запускается твин — он дерётся с ручным ресайзом мышью и даёт рваную анимацию.

**Твин ресайза** (`set_window_size`) анимирует ширину+высоту (ease-out) в фоновом треде, диспатчит каждый кадр через `run_on_main_thread`, с генерационным guard'ом `resize_gen`. Верхний край Y фиксирован (рост вниз), целевой `x` — текущий, только клампится в границы монитора (`anchored_target_x` → `window_geom::clamp_window_x`): окно растёт вправо на месте и сдвигается влево лишь упёршись в правый край (не уедет за экран). Центрирования НЕТ намеренно — оно раздражало при хоткей-ресайзе и открытии превью. Ранний выход — по эпсилону размеров; вызов с тем же размером — полный no-op. **Твин обязан обрываться, если между кадрами фактический размер разошёлся с тем, что применил предыдущий кадр** (`tween_superseded`/`frame_still_ours`): иначе он дерётся с ручным ресайзом мышью — Windows во время протяжки ведёт свой drag-rect от точки захвата, и каждый наш `SetWindowPos` откатывается следующим `WM_MOUSEMOVE`, давая рывок каждые 13 мс. Позиция применяется только когда реально отличается от целевой — лишний `SetWindowPos` на кадр дёргает начало координат при протяжке за левый и верхний край.

**Перетаскивание ЛКМ — явным `getCurrentWindow().startDragging()`** (`startWindowDrag` в `ipc/commands.ts`), а НЕ через `data-tauri-drag-region`: атрибутная инъекция Tauri в этом фреймлесс+transparent окне не срабатывала.

- `useWindowDrag` вешает `onMouseDown` на шапку (StatusBar); корневой `.app-shell` в App.tsx тоже стартует драг, но только при клике прямо по нему (`target === currentTarget` — отступы и зазор колонок; иначе клик по тексту чата ломал бы выделение).
- Драг стартует только для ЛКМ и только если `isDraggableChromeTarget` (клик не по интерактиву — селектор `button, a, input, textarea, select, [role='tab'], [data-no-drag]`), поэтому кнопки/табы остаются кликабельными, а клик по значку внутри кнопки (SVG, не HTMLElement) драг не стартует.
- Курсор над драг-зоной остаётся стрелкой (глобальный `cursor: default`) — осознанно.

**Орбы состояний (`thinking-orbs`) заменили `EqBars` в десктопе.** Пакет реэкспортирован шимом `components/ui/thinking-orbs.tsx` (константы `ORB_SIZE_INLINE` = 20 и `ORB_THEME` = "dark" — там же). В UI орб рисует только `StatusOrb`: он же гейтит reduced-motion и подставляет размер/тему, второго пути к `ThinkingOrb` в продуктовых компонентах нет. Состояния: покой → `breathing` (`ORB_STATE_IDLE`, спокойное кольцо — чтобы шапка/мини/лаунчер не были пустыми до первого действия), запись → `listening`, расшифровка → `working`, стрим ответа → `composing`, «Думает…» → `solving`, запуск HUD из лаунчера → `connecting`. Три невидимых из кода решения: (1) **`EqBars` в десктопе больше нет** (лендинг со своей копией не трогаем — это макет сайта, не HUD); (2) **тема прибита `"dark"`**: авто-детект пакета читает `data-theme`/класс `dark`, а у нас на `documentElement` значения `gray`/`black` — auto распознал бы их неверно; (3) **гейт reduced-motion — хук `usePrefersReducedMotion` внутри `StatusOrb`**, потому что canvas-анимацию CSS-медиазапросом не заглушить; отсутствие `window.matchMedia` хук трактует как «анимации выключены» — это не перестраховка, а то, что держит jsdom-тесты подальше от canvas (у jsdom нет ни `matchMedia`, ни 2D-контекста).

**Жидкая рамка окна (`LiquidMetalBorder`).** На рабочих статусах (запись / расшифровка / любой стрим ответа — `isActivityStatus`) вокруг **всего HUD** и вокруг **свёрнутой пилюли** MiniHud рисуется liquid-metal шейдер. Это не кнопка из registry. Слой `z-40` поверх контента (`pointer-events: none`): HUD полупрозрачный (`--app-opacity`), шейдер ПОД ним просвечивал бы на всю площадь. Кольцо — SVG-маска data-URI (белый скруглённый прямоугольник минус внутренний чёрный), не `mask-composite` (в WKWebView на большом окне xor давал пустоту). Толщина `FRAME_WIDTH_PX` = 3. В покое шейдер не монтируется. Reduced-motion / jsdom — тот же гейт, что у орба. `ShaderMount.dispose()` на снятии.

**Док действий (`ToolbarDock`).** Кнопка `Menu` в пилюле (28px: `p-0.5` + утопленный `ring-1 ring-border ring-inset`) справа в шапке, а слева от неё в ТОЙ ЖЕ пилюле — слот `leading` через вертикальную черту (сейчас в нём `ModeSwitch`, см. «Режимы HUD»): пилюля остаётся одной группой контролов, второй такой же рядом не заводим; клик открывает вертикальную колонку всех действий (та же поверхность + `shadow-pop`; вход колонки — CSS `animate-in` (fade+zoom+slide, `origin-top`) с overshoot-кривой `cubic-bezier(0.34,1.56,0.64,1)` — пружинный характер оригинального дока без пакета `motion`; клик-оверлей поверх контента не участвует во flex-раскладке шапки, так что классу багов удалённой полосы тут взяться неоткуда; `motion-reduce:animate-none` обязателен; закрытие мгновенное — клик мимо, `Escape`, повторный клик или выбор пункта, и после закрытия фокус возвращается на тумблер). **Слушатель «клик мимо» обязан пропускать порталы Radix** (`[data-radix-popper-content-wrapper]`, `[data-slot='popover-content']`): `PopoverContent` пункта-`element` рендерится в `document.body`, то есть ВСЕГДА снаружи `wrapperRef`, и без этого пропуска любой mousedown внутри справочника клавиш (протяжка скроллбара, выделение текста, промах мимо строки) схлопывал колонку, а с ней размонтировался и сам поповер. `Escape` при открытом поповере не трогает колонку — первый `Escape` закрывает поповер силами Radix. **Пилюля и колонка несут `data-no-drag`**: обе лежат внутри `<header onMouseDown={useWindowDrag}>`, а `NON_DRAGGABLE_SELECTOR` перечисляет только интерактивные теги — без атрибута промах мимо иконки на зазор `gap-0.5` утаскивал всё окно за курсором. Радиус колонки — `rounded-xl` из лестницы `--radius`, а не литеральный `rounded-2xl`. Пункты собирает `AppHeader` в `App.tsx` (`ToolbarDockItem[]`: мини-режим, видимость при демонстрации с `text-primary`-языком «видно», меню моделей, суфлёр/копирование (в меню ВСЕГДА, при пустом чате `disabled` — исчезающие пункты читались как «кнопки пропали»; это осознанно противоположно отвергнутому дизейблу в бывшей горизонтальной полосе: в выпадающем меню приглушённый пункт — норма, а стабильный состав важнее), справочник клавиш, бейдж обновления, «Стоп»); подписи и шорткаты — наш Radix `Tooltip` слева от пункта (`side="left"`, чип шортката; триггер — обёртка-`span`, поэтому подсказка работает и над `disabled`-пунктами; язык поверхности тот же инвертированный `bg-foreground/text-background`, что был у рельсы; нативные `title` у кнопок дока пустые — двойная подсказка выглядела бы багом, `aria-label` остаётся). Ховер кнопок — только высветление иконки (`DOCK_BUTTON_CLASS` = `rounded-full hover:bg-transparent`, его же получает триггер `HotkeysPopover` пропом `triggerClass`). **Горизонтальная раскрывающаяся полоса с анимируемой шириной и тултип-рельсой (Vercel-стиль, пакет `motion`) ПОЛНОСТЬЮ удалена, и возвращать её вслепую нельзя**: семь итераций подряд в прозрачном frameless-WKWebView она давала неотлаживаемые без живого devtools артефакты — наезды на соседей шапки при авто-сжатии, замороженную на полпути пружину, обрезанную крайнюю иконку при заведомо корректной разметке (включая вариант «полоса — обычный flex без overflow и замеров», где обрезаться нечему — то есть это уже несмытые пиксели композитора), мерцание и несрабатывающие пороги (из ширины окна с формулами и из измеренного ResizeObserver'ом слака — обе линии выброшены). Захочется вернуть — только через живую отладку в devtools вебвью, а не по скриншотам. Пакет `motion` удалён из зависимостей вместе с полосой.
- **Модификатор+стрелки двигают окно нативным перехватом клавиш, а не через вебвью** (`platform::install_move_keys_monitor`: на macOS — локальный NSEvent-монитор, на Windows — низкоуровневый хук `WH_KEYBOARD_LL`), который поглощает keyDown ДО вебвью — иначе каретка прыгала бы по текстовому полю, а сдвиг окна ходил бы через IPC. **Вся логика стрелок — общая `platform::handle_arrow_key(app, mask, dx, dy)`**: чтение настроек, сдвиг окна, эмит `resize-key`; бэкенду остаётся перехватить событие, перевести нативные флаги в `ModifierMask` и поглотить keyDown ровно тогда, когда функция вернула `true` (дублировать разбор настроек в бэкенде нельзя — разъедется полярность и клампы). Перехват ставится один раз в `setup_app` и живёт весь рантайм, поэтому пересоздание HUD его не ломает — но **поглощать keyDown он вправе только тогда, когда действительно его обработал**: нет окна `main` — событие уходит дальше, иначе ⌘+←/→ в текстовых полях лаунчера съедаются вместо перемещения каретки по строке (HUD может быть ещё не создан, а перехват уже живёт). Это горячий путь: **при пустой маске модификаторов выходим ДО взятия лока настроек** — иначе обычная навигация стрелками в поле промпта (с автоповтором) лочит глобальные `Settings` на каждый keyDown. **Хук Windows — глобальный, в отличие от локального монитора macOS**, поэтому в нём обязательна сверка `GetForegroundWindow()` с hwnd HUD: без неё те же стрелки перехватывались бы в чужих приложениях; ставится он один раз, `AppHandle` для него живёт в `OnceLock`. `resize_modifier`+стрелки меняют **размер** окна: монитор поглощает keyDown и эмитит `resize-key {dim, dir}`; фронт (`useWindowControls` → `useSettings.bumpWindowSize`) шагает `Settings.window_width/height` на `resize_step` с клампами из `lib/window-size.ts`, окно применяет `useWindowFrame`, персист — дебаунсом (как opacity). Полярность: ←/↑ меньше, →/↓ больше. **`move_window` и `resize_window` обязаны оставаться `scope: Hud` и НЕ появляться в `GLOBAL_HOTKEYS`.** Регистрация их системными шорткатами (жила с 4f695f6 в v0.13.0, снята) отбирает ⌘←/→ и ⌘↑/↓ у всей ОС: навигация каретки по строке и документу перестаёт работать в любом редакторе, в браузере и в самом поле промпта HUD — системный шорткат съедает нажатие до приложения, поэтому ни гейт `GetForegroundWindow()` в windows-хуке, ни правило «поглощать keyDown только когда обработал» уже ничего не решают. Автофокус окна на стрелке (`focus_main_window_if_unfocused`) удалён вместе с ней: он выдёргивал фокус из чужого приложения на каждое нажатие, а `set_position` работает и на нефокусном окне.
- **Стрелки сдвига и размера принадлежат нативному монитору целиком — параллельной JS-ветки под них нет и заводить её нельзя.** Монитор съедает keyDown СОВПАВШИХ с настройкой комбинаций, поэтому до вебвью долетают ровно те, что пользователь НЕ выбирал: JS-обработчик мог только противоречить его выбору (окно двигалось на чужой комбинации), «фолбэком» он не был никогда — зашитый `metaKey || ctrlKey` (+Shift) был багом, вывернутым наизнанку, а настраиваемая версия того же кода осталась бы багом. Вместе с веткой ушла её обвязка: раскладка «код клавиши → ось и знак» на фронте (ось и знак решает Rust и присылает готовыми в payload `resize-key`) и Rust-команда сдвига окна — монитор двигает окно `set_position`'ом напрямую, звать команду было неоткуда, и в `collect_commands!` её больше нет. `useWindowControls(onSend, onOpacityStep, onResizeKey)` отвечает теперь только за прозрачность, отправку по Cmd/Ctrl+Enter и подписку на `resize-key`. Единственный оставшийся JS-путь модификаторов — скролл чата (`useHotkeyScroll`: его комбо монитор не трогает и пропускает в вебвью), там спека разбирается `parseModifier` ОДИН раз в эффекте, а не на каждый keydown (иначе каждое нажатие в вебвью аллоцирует массив на `split("+")`); в реестр хоткеев комбо приходят полями `moveWindow`/`resizeWindow`/`scrollChat` в `HotkeyConfig`.
- **Словарь модификаторов — один источник, `hotkeys::MODIFIER_COMBOS`** (переехал из `settings.rs`), и он **парный по платформам** (`{macos, windows}`): через `.constant()` в биндинги уезжает пара целиком, селект `WindowSection` берёт свою половину (`MODIFIER_COMBOS[PLATFORM]`, своей копии списка во фронте нет), Rust — через `.current()`. Обе реализации разбора покрыты тестами: `platform/tests.rs` (каждое комбо реестра даёт непустой и уникальный `modifier_mask`, дефолты семейств лежат в реестре) и `lib/hotkey-match.test.ts` (то же для `parseModifier`, прогон по обеим платформам плюс проверка, что в Windows-списке нет комбо с Win). Клавишу Win на Windows нельзя и **захватить** мышью: `hotkeyFromEvent` отдаёт `null`, если зажат Meta, — иначе получался бы мёртвый биндинг, который `assignHotkey` уже отобрал у прежнего владельца, а `RegisterHotKey` с `MOD_WIN` система не отдаёт (ошибка регистрации при этом глотается). Бит `ModifierMask::CMD` в Windows-бэкенде при этом остаётся привязан к `VK_LWIN`/`VK_RWIN` намеренно: `settings.json`, перенесённый с macOS, содержит комбо с `Cmd`, и они обязаны продолжать работать, а не молча игнорироваться. Добавляешь комбо — правишь массив нужной платформы в Rust и гоняешь `cargo test`, чтобы перегенерить биндинги. `formatCombo` обязан сворачивать спеку из одних модификаторов, без клавиши на конце (`Cmd` → ⌘, `Cmd+Shift` → ⌘⇧): regex, требовавший `+` после токена, оставлял подписи вида «⌘Shift»; на Windows глифов нет — токены текстовые (`Ctrl/Shift/Alt/Win`) и соединяются через `+`. **Прозрачность (`+`/`−`) в UI настраиваемой НЕ делаем намеренно** — селект отдаёт пользователю ровно три модификатора (сдвиг, размер, скролл); комбо прозрачности живёт действием `opacity` в реестре `hotkeys.rs`, откуда его одинаково берут подпись в поповере и сверка события в `useWindowControls` (`effectiveCombo(hotkeys, "opacity")`), потому что литерал «⌘⇧ + −» в подписи и `e.metaKey && e.shiftKey` в обработчике уже жили порознь и могли разъехаться.
- **Указатель мыши никогда не прячется и не меняет форму.** WebKit при печати в текстовом поле просит спрятать указатель «до движения мыши» через `+[NSCursor setHiddenUntilMouseMoves:]` в UI-процессе; на старте (`platform::disable_cursor_autohide_on_typing`, зовётся из `setup_app`) этот класс-метод свизлится в no-op — публичный objc-runtime API, детерминированный фикс. Пост-фактум `setHiddenUntilMouseMoves(false)` НЕ работает: скрытие приходит асинхронным IPC и гонку выигрывает (такая компенсация была в прежней команде сдвига окна и удалена как ненужная при свизлинге). Форма указателя — всегда стандартная стрелка: глобальный `cursor: default !important` в index.css намеренно подавляет I-beam/pointer/not-allowed во всех кейсах — не убирай. Правило распространяется и на псевдоэлементы. Отдельный iframe не наследует CSS HUD: `withPreviewCursor` в `PreviewPanel` добавляет первый CSS-слой с important-правилом ко ВСЕМ HTML-превью, включая старые схемы. В `diagram-viewport.html` стрелка закреплена также для автономного экспорта; `grab`/`grabbing`/`pointer` запрещены даже во время pointer-драга. Нативный Windows-оверлей выделения области тоже использует `IDC_ARROW`. У WebView2 такого автоскрытия нет, поэтому `disable_cursor_autohide_on_typing` на Windows — осознанный пустой no-op, а не забытая реализация.
- **`onEvent` uses a `live` flag** to pair subscribe/unsubscribe across the async `listen` promise — required for React StrictMode double-mount safety. `useClaudeStream` likewise cancels its pending rAF on unmount and gates late deltas after `stop`. Частичный ответ на `stop`/`llm-error` НЕ выбрасывается — уходит в историю через `onComplete` (дубля нет: `llm-done` отменённого стрима подавляется, чат уже снят с `active`). Буферы дельт и набор активных стримов живут в ref, а не в state: обработчики событий подписаны один раз и обязаны видеть свежие значения без переподписки — перенос в state/deps сломает роутинг дельт.
- **API keys: `.env` is a fallback only.** `lib.rs` setup reads `ANTHROPIC_API_KEY`/`GROQ_API_KEY`/`OPENAI_API_KEY`/`XAI_API_KEY` (`preferences.rs`) and applies them via `settings.apply_key_fallback` **only when** the corresponding settings.json field is empty (UI-saved keys win). `.env` is read from cwd and from `CARGO_MANIFEST_DIR/..` (so a Finder-launched `.app`, whose cwd is `/`, still finds the project `.env`). `.env` is gitignored. **Гейт «нет ключей» живёт в лаунчере, а не в HUD** (`features/launcher/useLauncherReadiness`): `get_settings` отдаёт настройки уже с применённым `.env`-фолбэком, поэтому пустое поле на фронте = ключа нет нигде. `missingApiKeys(settings)` (`lib/api-keys`) требует Anthropic + ключ **выбранного** STT-провайдера (`stt_provider` → `groq` или `openai`), а не оба STT-ключа сразу: иначе гейт запуска HUD держал бы пользователя Groq за ключ OpenAI, которым тот не пользуется. Ключей в реестре `API_KEYS` три, обязательных всегда два. Он же + разрешение на запись звука (`usePermissions`) дают `ready` (считается один раз в хуке и приходит в панель пропом `readiness`, а не пересчитывается формулой на месте); пока не `ready`, кнопка запуска HUD заблокирована. В HUD баннера про разрешения нет вовсе — гейт лаунчера не выпустит в HUD без доступа к звуку (см. «Доступы»). Поэтому у `Composer` **нет пропа `disabled`**: гейта в HUD не существует, флаг приходил константным `false` и протаскивался через полтора десятка компонентов (`ComposerToolbar` → `RequestParamsPopover` → селекты) — не возвращай его. Проп `disabled` у тумблера thinking при этом остался: `thinkingLocked` → `thinkingDisabled` → `ParamToggle`.
- **Коды доступа (прокси-режим).** Альтернатива своим ключам: пользователь вводит одноразовый код, команда `redeem_access_code` (`access.rs`) обменивает его на bearer-токен прокси-сервера (Cloudflare Worker, репо `itech-relay`) и кладёт в `Settings.access_token`. **Непустой `access_token` глушит ВСЕ ключи** — единый источник истины: `build_llm_client`/`build_stt_client` (`app_state.rs`) строят клиент в прокси-режиме (`llm::AnthropicClient::for_proxy` — `Auth::ProxyBearer`, base_url прокси, `Authorization: Bearer` вместо `x-api-key`; STT — тот же bearer с base_url прокси, причём вендор берётся из `stt_provider` ровно так же, как в прямом режиме: прокси-режим меняет только ключ и base_url, потому что пути relay симметричны upstream'у), `apply_key_fallback` не подставляет `.env`, `missingApiKeys` возвращает `[]`. `rebuild_changed_api_clients` пересобирает ОБА клиента при смене `access_token`. Порядок в `apply_access_token`: сеть (redeem) → `save` на диск → rebuild → in-memory (ошибка save = reject, состояние не тронуто), всё под `App.settings_edit`; 429 IP-лимита redeem отдаёт свой текст («слишком много попыток»), а не «неверный код». Отвязка — команда `clear_access_token` (кнопка «Отвязать» в лаунчере), потому что `set_settings` токен из снимка не принимает. **`set_settings` держит тот же порядок и это не косметика**: сохранение на диск стоит ПЕРЕД побочными эффектами (`reregister_changed_hotkeys` → `rebuild_changed_api_clients` → screen share → буфер) — раньше было наоборот, и упавший `save` (диск полон, папка недоступна) возвращал `Err` уже ПОСЛЕ пересборки клиентов: фронт и `st.settings` показывали старый `stt_provider`, а `st.stt` уже говорил с другим вендором, возможно с пустым ключом. Пересобранный STT-клиент тут же прогревается (`warm_up` в `spawn`) — иначе первый PTT после смены вендора платит DNS+TCP+TLS на холодный хост, а сравнить вендоров можно только A/B посреди разговора. Прокси-URL — константа `access::PROXY_BASE_URL`; env-override `ITECH_PROXY_ENDPOINT` — **только `cfg!(debug_assertions)` и только `https://`** (в релизе игнорируется — защита от редиректа токена/контента). Идемпотентность redeem — ключ из `crypto.randomUUID()` в `localStorage` (`redeem-idem:<норм.код>`), переиспользуется при повторе, чистится при успехе; `normalizeAccessCode` (`lib/access-code.ts`) обязана совпадать с серверной нормализацией. В прокси-режиме `require_ok_status` отдаёт 401/403 relay как `LlmError::BadAccessCode` с телом `error.message` прокси (понятный текст «код недействителен»/«лимит исчерпан») — тот же код `badAccessCode`, что и у STT; STT-инвариант «401→BadApiKey без рефоллбэка» сохранён для всех вендоров (в прямом режиме 401/403 → `BadApiKey` с именем вендора в тексте, в прокси-режиме → `BadAccessCode` с телом прокси).
### Лаунчер автосохраняет `draft` — кнопки «Сохранить» нет

`LauncherPanel` держит локальный `draft: Settings`; любое изменение поля дебаунсится `AUTOSAVE_DEBOUNCE_MS` (600мс) и уходит в `set_settings` через `useSettingsStore.save` (`useDraftAutosave`). Дебаунс не косметический: посимвольный ввод ключа/кода схлопывается в одну пересборку клиентов (`rebuild_changed_api_clients`). Несохранённый хвост сбрасывается на диск при размонтировании (выход из приложения); при `launching` не сбрасывается — запуск сам зовёт `persist(draft)`, иначе был бы второй `set_settings` на уничтожении окна.

- **Раз кнопки нет, сохранение обязано быть видимым.** `LauncherApp` держит флаг `saving` вокруг `persist`, и шапка на это время пишет «Сохраняю…» вместо блокера. Без него был видимый лаг: `useLauncherReadiness` считает блокеры по ПЕРСИСТНУТЫМ `settings`, а не по `draft`, поэтому после вставки ключа статус ещё 600мс дебаунса плюс круг `set_settings` продолжал утверждать «нет ключей» — пользователь читал это как «ключ не принят». Ошибка сохранения показывается баннером в `LauncherPanel` под шапкой, а НЕ строкой в самой шапке: там она делила ряд со статусом и поиском и обрезалась `truncate` на первых словах, то есть текст ошибки было физически не прочитать.
- `onSave` вызывается ЧЕРЕЗ ref (`onSaveRef`), а НЕ из зависимостей эффекта: `save` делает `adopt(getSettings())` → ре-рендер родителя → новая идентичность колбэка, и если бы эффект зависел от `onSave`, каждое сохранение перезапускало бы эффект и зацикливало автосейв (`save → adopt → ре-рендер → save`).
- Эффект сравнивает `draft` с ref `lastQueuedDraft` **по идентичности** (так пропускаются первый рендер и StrictMode-ремоунт; каждое новое изменение сбрасывает таймер через cleanup).
- Нормализуется (`normalizeDraft`: пустые хоткеи → одноимённое поле `DEFAULT_SETTINGS` + отсев незаполненных пресетов `isPresetFilled` и незаполненных быстрых действий `isQuickActionFilled`) только сохраняемая копия — сам `draft` в UI НЕ трогается, иначе пустое поле хоткея заменялось бы фолбэком на глазах у пользователя, а полупустой пресет или наполовину набранное быстрое действие исчезали бы прямо при редактировании. **Свои `FALLBACK_*`-константы под эти фолбэки не заводить**: прежний `FALLBACK_PTT_HOTKEY` был `V` при дефолте `F9`, и очистка поля PTT давала биндинг, которого не бывает при чистой установке.
- При `launching` эффект ранне-выходит, а cleanup гасит отложенный таймер: «Запустить» сам персистит нормализованный `draft` до `launch_main_window`, двойного сохранения нет.
- Слияние `settings.access_token` в `draft` после redeem возвращает ТОТ ЖЕ объект, если токен не изменился, — холостое слияние не должно порождать новую идентичность `draft` и лишний автосейв.
- Автосейв опирается на Rust-инвариант: `reregister_changed_hotkeys` (`preferences.rs`) ранне-выходит, пока main-окна нет, поэтому автосейв хоткеев из лаунчера НЕ дёргает глобальную регистрацию — она происходит один раз в `launch_main_window` из уже персистнутых настроек.
- **Способ достучаться до бэкенда в фиче один: секции импортируют команды из `@/ipc/commands` напрямую** (`SttSection` → `listAudioOutputDevices`, `AppearanceSection` → `applyTheme` из `lib/window-controls`). DI-слой `LauncherPort` был и удалён: половина секций всё равно ходила мимо контекста, и две конвенции в одной фиче стоили дороже прямого импорта. Пропсами приходит только то, у чего есть состояние в `LauncherApp`: `onRedeem` (после успеха дёргает `reload` стора, чтобы токен влился в `settings`), `onCheckUpdates` и целиком `updater` — экран «Обновления» живёт в лаунчере, иначе `update-available` от автопроверки (бьёт через 5 с после старта, когда на экране именно лаунчер) уходил бы в никуда.
### Window chrome (HUD)

Окно `main` — `transparent` + `decorations: false` (фреймлесс, без нативного тайтлбара) + `alwaysOnTop` + `visibleOnAllWorkspaces` + `shadow(false)` + `contentProtected` (невидимо при демонстрации экрана; `Settings.screen_share_visible` снимает защиту через `set_content_protected`). Нативная тень окна снята и у HUD, и у лаунчера (`.shadow(false)` в обоих билдерах): дефолт Tauri — тень включена, и она спорила с liquid-metal рамкой. На Windows `shadow(false)` на декорированном лаунчере молча не действует (тень всегда ON), на HUD (без decorations) — действует; `shadow(true)` у undecorated Windows дал бы 1px белую кайму — не включать. На Windows два других флага из этого набора ведут себя иначе, и это не баг вызова: `visible_on_all_workspaces` молча ничего не делает (в tao не реализован), а `contentProtected` работает через `SetWindowDisplayAffinity` и требует **Windows 10 версии 2004+** — на более старых сборках окно попадёт в демонстрацию экрана.

**Состояние защиты видно в шапке HUD** — пункт «видимость при демонстрации» в доке действий `ToolbarDock` (отдельного `ScreenShareIndicator` больше нет, компонент удалён): перечёркнутый глаз нейтральным цветом = окно скрыто из захвата, обычный глаз цветом `primary` = окно попадёт в запись. Это тот самый санкционированный случай `primary` (индикатор, а не цвет текста), и громким сделано именно «видно» — состояние, которое пользователь обязан заметить. **Пункт кликабелен, и это не украшение:** в остальном `screen_share_visible` живёт только тумблером в лаунчере — строка «Показывать окно при демонстрации экрана» намеренно стоит ПЕРВОЙ в «Поведении» и названа в описании таба, потому что это стержневое приватное свойство продукта, а браузингом её раньше было не найти, а попасть туда можно лишь остановив HUD (`stop_main_window` уничтожает окно) — то есть, заметив посреди звонка «меня видно», исправить это без кликабельного индикатора было бы физически нельзя. Своего пути записи он не заводит: тот же `saveSettingsReportingError` → `set_settings` → `apply_screen_share_visibility_change`, что и у любой другой настройки. **Честный предел:** на Windows старше 10 2004 `set_content_protected` молча не работает, и индикатор будет показывать «скрыто» у реально захватываемого окна; версию сборки мы не детектим — минимально поддерживаемая и так 2004+.

**Размер и скругление:**

- Мышиный ресайз за невидимые края разрешён и синкается в настройки: `useWindowFrame` (`hooks/useWindowFrame.ts`, половина `useSettingsFromNativeResize`) слушает `onWindowResized` (`ipc/events.ts`, физпиксели → логические через `window.devicePixelRatio` синхронно — IPC `scaleFactor()` на каждое событие уходил бы ДО rAF-коалесинга, на Windows это invoke на каждый пиксель протяжки, а параллельные ответы не обязаны приходить по порядку), вычитает превью-экстру и пишет в `Settings.window_width/height` через `applyNativeWindowSize` (кламп + дебаунс-персист; хвост уходит на диск и при размонтировании HUD — `stop_main_window`/выход, иначе ресайз мышью за 400мс до стопа терялся).
- **Цель, совпадающая с эхом нативного размера, означает «размер задал пользователь мышью» — тогда окно не трогаем ВООБЩЕ**: `useFrameFromSettings` внутри `useWindowFrame` выходит до `set_window_size`, а не просто не ставит guard. Эхо считает `lib/window-size.nativeSizeEcho` — ровно то, что записал бы в настройки `applyNativeWindowSize` из последнего нативного размера, вместе с клампом и превью-экстрой; сравнение — `windowSizesEqual`, и его эпсилон обязан быть НЕ строже рустового `RESIZE_EPSILON_LOGICAL_PX`, иначе фронт шлёт запросы, которые Rust отбрасывает сам. Почему просто guard'а мало: цель меряется в момент события ресайза, а текущий размер Rust читает спустя два IPC и ре-рендер (десятки миллисекунд), и при живой протяжке расхождение всегда больше эпсилона — стартует твин, убивает предыдущий, его кадры порождают новые события, и петля не затухает. Guard-окно (600мс) осталось и взводится на программных изменениях. Само событие ресайза коалесится через `requestAnimationFrame`: на Windows `WM_SIZE` приходит на каждый пиксель протяжки, и без коалесинга каждый давал полный ре-рендер HUD с перевёрсткой markdown. Гейт `readyRef` обязателен: событие до загрузки настроек иначе персистнуло бы DEFAULT_SETTINGS (пустые ключи!) на диск.
- Скругление продублировано нативно: `platform::clip_native_window_corners` вешает `cornerRadius = WINDOW_CORNER_RADIUS_LOGICAL_PX` (22, обязан совпадать с CSS-переменной `--window-radius` в `index.css` — её берут шелл `.app-shell`, `DialogOverlay` и `ConnectivityOverlay`) + `masksToBounds` на слой contentView — иначе при твине ресайза WKWebView отстаёт на кадр и правые углы мигали бы острыми. CSS-радиус при этом не убирать (клип рисует форму, CSS — фон). На Windows тот же вызов ставит DWM-атрибут `DWMWA_WINDOW_CORNER_PREFERENCE` = `DWMWCP_ROUND`: радиус там системный (~8px) и под 22px не настраивается — **поэтому вторым атрибутом обязательно идёт `DWMWA_BORDER_COLOR` = `DWMWA_COLOR_NONE`**. Рамку рисует не приложение, а DWM: tao оставляет undecorated-окну стиль `WS_CAPTION` (неклиентская область зануляется в `WM_NCCALCSIZE`), для системы окно остаётся обычным оконным фреймом, и та 1px-линия идёт по СВОЕМУ радиусу — то есть срезает угол шелла на 22px и обводит пилюлю мини-режима (`rounded-full`) прямоугольником по границам окна. Подогнать её радиус нельзя (в API только DEFAULT/ROUND/ROUNDSMALL/DONOTROUND), поэтому линия убирается целиком; `DWMWCP_ROUND` при этом оставлен — в углах контент прозрачный, клип 8px ничего видимого не режет. Атрибут действует с Windows 11 (build 22000+), на Windows 10 вызов молча игнорируется ровно как и сам `DWMWA_WINDOW_CORNER_PREFERENCE`.

**Край окна рисует CSS, а не система.** У `.app-shell` стоит `box-shadow: inset 0 0 0 1px var(--window-edge)` по радиусу окна. Без него развёрнутый HUD не имел края вообще: окно `transparent` + `decorations: false`, нативной рамки нет, нативная тень снята, а фон уходит в прозрачность через `--app-opacity` — граница получалась там, где полупрозрачный тон встречает рабочий стол, то есть почти нигде. Мини-режим этим не страдал и потому выглядел аккуратнее: его пилюля непрозрачная (`bg-background`) и несёт обычный `ring-1 ring-border`. **`--window-edge` намеренно плотнее `--border`**: хайрлайн в 9–10% рассчитан на непрозрачные поверхности, а край окна ложится на полупрозрачный фон и на чужой контент за ним. `LiquidMetalBorder` эту роль не выполняет — она рисуется только при активности и в покое возвращает `null` в обоих режимах. На Windows это ещё и замена снятой DWM-линии: ту убрали, потому что она шла по СВОЕМУ радиусу и срезала угол шелла, а эта идёт ровно по `--window-radius`.

**Прозрачность и порталы:** `html/body` прозрачны, фон рисует корневой `.app-shell` через альфу `--app-opacity` (слайдер прозрачности ставит переменную на `documentElement`; CSS-дефолт `--app-opacity: 0.9` в `index.css` обязан совпадать с дефолтом `window_opacity` — иначе до загрузки настроек окно рендерится с другой прозрачностью). Не переопределяй `.bg-background` глобально: единственный оставшийся его потребитель — `ConnectivityOverlay`, и он обязан быть непрозрачным, иначе сквозь оверлей «нет сети» просвечивает чат. Остальные с класса съехали, и возвращать их на него не надо: бегунок `Switch` красится напрямую (`bg-foreground` выключен / `bg-primary-foreground` включён), `outline`-кнопка — `bg-input/20`, `DialogContent` — `bg-popover` (см. «Модалки»). Портальному контенту (dialog/select/tooltip) нужен `body { color: var(--foreground) }`, потому что он рендерится вне `.app-shell`.

**Модалки:**

- `DialogOverlay` обязан скругляться `rounded-[var(--window-radius)]` под радиус окна: окно прозрачное+фреймлесс, `fixed inset-0` без скругления залил бы угловые треугольники `bg-black/55` и они торчали бы острыми за скруглением.
- **`DialogContent` заливается `bg-popover`, а не `bg-background`** (правка стокового shadcn). Элевация: в лаунчере `bg-background` — самая тёмная ступень (`body.launcher`), и модалка на ней проваливалась ПОД карточки `bg-card`, которые перекрывает; `--popover` в обоих окнах стоит на уровне карточки или выше, поэтому диалог читается как поднятая поверхность.
- `DialogContent` НЕ использует `overflow-hidden`: в WKWebView `overflow:hidden`+`border-radius` на `transform`-элементе даёт острые углы; собственный фон радиус и так уважает, контент внутри `p-5` до углов не достаёт. **Центрирование — не `translate`, а полноэкранный флекс**: `Content` идёт `fixed inset-0 flex items-center justify-center`, а видимая карточка — вложенный `div[data-slot=dialog-panel]`; transform-центрирование мылило текст. Отсюда два следствия, которые легко сломать. (1) **На `Content` обязана оставаться собственная exit-анимация** (`duration-200 data-[state=closed]:animate-out`, без fade/zoom-утилит — она ничего не двигает): Radix `Presence` решает, ждать ли размонтирования, по `getComputedStyle(node).animationName` именно этого узла, и если анимации на нём нет, панель исчезает за кадр, `data-state="closed"` до группы не доезжает и все `group-data-[state=closed]:*` на панели становятся мёртвыми — а `DialogOverlay` при этом доигрывает свои 200мс, то есть модалка пропадает раньше бэкдропа. (2) **Ручной обработчик «клик мимо» обязан композиться с `props.onPointerDown`, а не затирать его** — он стоит после `{...props}`, и без вызова пользовательского обработчика (и проверки `defaultPrevented`) любой `onPointerDown` от вызывающего молча терялся.
- **`CommandDialog` (`components/ui/command.tsx` — shadcn command поверх `cmdk`) построен на нашем `Dialog`/`DialogContent`, а не на обёртке из стокового сниппета**, поэтому предыдущий инвариант держится сам собой: `overflow-hidden` тут нет, `DialogContent` идёт `gap-0 p-0` + `showCloseButton={false}`, а обязательные Radix'у `DialogTitle`/`DialogDescription` лежат внутри контента как `sr-only`. Остальные правки под проект: шрифты на ступенях шкалы (`text-body`/`text-hint` вместо стоковых `text-sm`/`text-xs`), подсветка выбранного пункта — `data-[selected=true]:bg-surface-active`, как у `SelectItem`, иконки `size-3.5`. **Свежий `npx shadcn@latest add command` затрёт всё это разом** — после обновления примитива правки возвращать руками, иначе диалог приедет с острыми углами и чужой шкалой шрифтов. В jsdom cmdk требует `Element.prototype.scrollIntoView` и `ResizeObserver` — стабы намеренно лежат локально в `ModelCommandMenu.test.tsx`, в `test-setup.ts` они переедут, когда потребитель станет не один. **А вот `localStorage` шимится глобально в `test-setup.ts`, и это не перестраховка**: начиная с Node 24 у рантайма есть СВОЙ глобальный `localStorage`, который без флага `--localstorage-file` равен `undefined` и перекрывает выданный jsdom, — на Node 26 из-за этого молча падали все тесты идемпотентности redeem, а CI на Node 22 оставался зелёным. Защитных обёрток вида `globalThis.localStorage?.` в проде из-за этого заводить не надо: они превращают поломку в тихий no-op.
- **Однокадровая вспышка при закрытии — `animation-fill-mode`, и это касается всех четырёх примитивов.** У `tw-animate-css` шорткат `--animate-out` заканчивается на `var(--tw-animation-fill-mode, none)`, а `@keyframes exit` состоит ТОЛЬКО из блока `to` — то есть `from` берётся из вычисленного стиля, и по окончании анимации при `fill-mode: none` элемент к нему же и возвращается: `opacity: 1`, полный масштаб. Radix снимает узел с монтирования из обработчика `animationend`, тот идёт через планировщик React (событие не дискретное, коммит может уступить кадр), и в этом зазоре браузер успевает нарисовать бэкдроп `bg-black/55` и непрозрачную панель ЦЕЛИКОМ — уже отработавшие своё затухание. Отсюда короткая вспышка, причём непостоянная: это гонка с коммитом React, а заметнее всего она на командном меню — самой часто открываемой и самой крупной непрозрачной поверхности. Лечится `data-[state=closed]:fill-mode-forwards` (у панели диалога — через `group-data-[state=closed]:`), который держит конечный кадр анимации до реального размонтирования. Утилита обязана висеть **под `[data-state=closed]`, а не глобально**: так она физически не может залипнуть в открытом состоянии — при быстром пере-открытии посреди exit'а селектор перестаёт совпадать, `fill-mode` возвращается в `none` и enter-анимация играет с чистого листа. Стоит на всех четырёх: `dialog` (оверлей + панель), `popover`, `select`, `tooltip`. **Две гипотезы проверены и оказались мимо — не возвращайся к ним:** `pointer-events-none` на `Content` тут ни при чём, и подмена `animate-out` на самодельный keyframe без `transform`/`filter` вспышку не убирает (полноэкранный слой композитинга её не вызывает), зато ломает инвариант из пункта (1) выше.
- `DialogOverlay` обязан нести `duration-200` под стать `DialogContent`: без него бэкдроп затухал за дефолтные 150мс tw-animate-css, а контент за `duration-200` — фон пропадал раньше модалки.
- **Данные, от которых зависит контент модалки с exit-анимацией, нельзя обнулять синхронно с закрытием** — контент обязан дожить до конца анимации. Модалка, открытая по `open={target !== null}`, обязана рисовать тело из залатченной копии `target` (санкционированный паттерн «adjust state during render»), а не из него самого: иначе при обнулении target тело исчезает мгновенно, пока Radix ещё 200мс проигрывает exit, и модалка дёргано схлопывается по высоте. Латч в таком месте выглядит избыточным — его удаление вернёт дёрганье.

**HTML-превью ответов** рендерится встроенной панелью `PreviewPanel` (правая колонка того же окна). Контент грузится с отдельного origin (кастомная схема `register_uri_scheme_protocol("preview", …)` в `lib.rs`, отдаёт `App.preview_html`, заполняемый командой `set_preview_html`) в `<iframe src sandbox="allow-scripts allow-same-origin">` — `localStorage`/сеть работают, но cross-origin к `tauri://localhost` + отсутствие capability на схему изолируют превью от IPC и ключей. **Адрес схемы платформенный** — `preview://localhost` на macOS против `http://preview.localhost` на Windows, — поэтому origin руками не собирается: его строит `ipc/preview.previewUrl` через `convertFileSrc("", "preview")` самого Tauri, и это **единственное место фронта, знающее о схеме**; захардкоженный `preview://localhost` на Windows просто не загрузится. Нонс в `src` iframe'а (`…/?v=N`) обязателен: заставляет WKWebView перезагрузить iframe даже при том же HTML и гасит гонку быстрых открытий (устаревший ответ `setPreviewHtml` игнорируется). Открытие расширяет окно на месте через `useWindowFrame` (`set_window_size`).

**Компактные системные промпты (пул v9).** Восемь встроенных пресетов в `config/presets.json` укладываются в 3000 символов каждый без `[keywords]`; этот бюджет проверяет `presets.test.ts`. Сокращать нужно повторы, сохраняя исключения для кода, скриншотов и уточнений; пользовательские пресеты и материалы не переписываются. Словари STT остаются в исходных пресетах и вырезаются перед LLM как раньше. Размер текста не доказывает качество ответов: последнее требует сравнения на одних вопросах и одной модели.

**System Design отдаёт данные, приложение строит HTML.** Блок `system-design` содержит JSON `{version:1,TITLE,NODES,EDGES,GROUPS}`. `lib/system-design.ts` проверяет типы, размеры, уникальность id, слои и ссылки; `system-design-template.html?raw` хранит прежний автономный рендерер с зумом. JSON экранируется перед вставкой в script; разметку подписей экранирует рендерер. `previewHtml` используется и `makePre`, и `extractHtmlBlocks`: ручное/автоматическое открытие и копирование превью получают полный HTML, история для модели хранит только JSON. Невалидный/незавершённый JSON остаётся видимым кодом и не запускается; старые `html`-блоки поддерживаются. `version` внутри схемы — версия формата, версия итерации пишется в TITLE. Пул v9 требует этого рендерера: **не публиковать его на общий URL для старых клиентов без совместимого канала обновления**. Локальная сборка использует v9, старый удалённый пул его не откатывает. `build.additionalWatchFolders: ["../../../config"]` в `tauri.conf.json` обязателен для dev: пресеты вшиты в Rust через `include_str!`, и один Vite HMR оставляет backend со старым пулом. После изменения списка отслеживаемых папок перезапускай `tauri dev` целиком; проверка — изменение mtime `config/presets.json` вызывает пересборку Rust.

**Навигация по схеме живёт вне промпта.** `diagram-viewport.html?raw` добавляется через `withDiagramViewport` к новым JSON-схемам и прежнему HTML нашего рендерера (`globalThis.__SVG` / `__LAYOUT`); другие HTML-превью не меняются. Вставка идемпотентна, HTML из кнопки копирования остаётся автономным. Начальный масштаб не ниже 80%, «Вписать» показывает всю схему, кнопка процентов возвращает 100%. Холст двигается левой кнопкой (Pointer Capture), колесом/тачпадом и стрелками; Ctrl/⌘ + колесо приближает к курсору. Capture-обработчик wheel блокирует старый обработчик рендерера, иначе legacy-схема масштабируется дважды. ResizeObserver перевписывает автоматический вид, а после ручного движения сохраняет масштаб и точку в центре. Кнопки вынесены из области холста, чтобы схема и подписи на них не накладывались.

**Телесуфлёр** (`Teleprompter`, оверлей `absolute inset-0` над `.app-shell`) — крупный центрированный текст ответа (`toReadingText` снимает markdown), плавный автоскролл через один rAF-цикл (скролл — программный `scrollTop` на `overflow-hidden`; смещение считает `advanceOffset` по dt, чтобы скорость не зависела от частоты кадров), маска-фейд по краям + фокус-полоса по центру («глаз в одной точке»). Контейнер — `overflow-y-auto` (ручной скролл колёсиком; `onScroll` синхронит `offsetRef`, чтобы автоскролл продолжал с новой позиции, а не прыгал назад). Space — пауза, Esc — закрыть. Позиция/скорость/шрифт персистятся на размонтировании (`onPersist` в cleanup — ловит и закрытие хоткеем): App хранит `{text, offset}` в ref и при повторном открытии восстанавливает offset, если `teleprompter_resume` и текст тот же. Текст — стриминговый `partial`, иначе последний ответ ассистента.

**Левая (чат) колонка — деривированной фикс-ширины** (`chatColumnWidth = window_width − 2·SHELL_PADDING_PX` в App.tsx — симметрично по краям окна), НЕ `flex-1`: иначе при монтировании панели `flex-1` сжимал бы чат на каждом кадре твина (перевёрстка markdown → видимое дёрганье). Ширина меняется только дискретно по хоткею размера; во время твина превью колонка стабильна — панель просто клипается `overflow-hidden` пока окно узкое и проявляется по мере разъезда; чат не релэйаутится и главный поток свободен для твина.
- **Window height меняется только пользователем.** Высота задаётся `Settings.window_height` (хоткей `resize_modifier`+↑/↓); UI-логика высоту не трогает. Ширина — та же база плюс превью: окно = `window_width` + `PREVIEW_EXTRA_WIDTH_PX` при открытом превью, всё через `useWindowFrame` → `set_window_size` (эффект гейтится `!settingsLoading`, иначе дефолт затёр бы персистнутый размер, применённый Rust'ом на старте).
- **Платформ две, и они не равны по возможностям.** macOS 14.2+ (Core Audio process tap) и Windows 10 версии 2004+ (WASAPI loopback). На Windows структурно НЕТ двух вещей: разрешения на запись системного звука (у loopback его не существует — `permissions::AUDIO_REQUIRES_PERMISSION`) и разрешения на запись экрана (`screen_capture_access`/`request_screen_capture_access` возвращают `true`); ещё `0600` там не ставится, а `visible_on_all_workspaces` — no-op. Одинаково на обеих: внешние ссылки открываются платформенным шеллом (`open(1)` / `ShellExecuteW`), но **фильтр «только `http://`/`https://`» живёт в общем `platform::open_web_url`** — намеренная защита от `file://`/`smb://`, дублировать её в бэкендах не надо; панели системных настроек — `x-apple.systempreferences:` против `ms-settings:`.
- **Имя процесса — «Audio System» по умолчанию (сборочно, стелс), бренд `harpyhare.ai` — только подпись в UI.** `productName` + `mainBinaryName` + window `title` = `Audio System`, identifier = `com.audioservice.helper` (`tauri.conf.json`) → `CFBundleName`, исполняемый файл (`Contents/MacOS/Audio System`, т.е. `ps`/`proc_name`/Activity Monitor/меню-бар) и метаданные окна (`CGWindowList` owner+title) единообразно показывают «Audio System»; на Windows тот же `productName` даёт `Audio System.exe` в диспетчере задач и такую же запись в списке установленных программ (NSIS, установка для текущего пользователя, WebView2 докачивается бутстраппером). Бренд `harpyhare.ai` (`lib/brand.BRAND_NAME`) выводится только внутри приложения (подпись в настройках — её видит лишь пользователь). Сменить это имя пользователь не может — оно задаётся сборочно. Осознанный потолок: `contentProtected` скрывает пиксели окна из захвата, но НЕ факт присутствия — процесс и окно (`CGWindowListCopyWindowInfo` на macOS, перечисление окон и процессов на Windows) видны всегда; от выделенного детектора на той же машине скрыться нельзя. Имперсонация системных процессов (`com.apple.*`) намеренно НЕ используется: ad-hoc-подпись + чужой namespace — сама по себе сигнатура фейка и ломает TCC/нотаризацию. Артефакты сборки (`Audio System.app.tar.gz`, dmg, `Audio System_<версия>_x64-setup.exe`) называются с пробелом (Tauri берёт `productName` дословно); в `release.mjs` загружаемые ассеты и URL в `latest.json` используют ASCII-слаг `AudioSystem` — GitHub заменяет пробелы на точки в именах ассетов и сломал бы ссылку апдейтера.
### Снимок области экрана

Хоткей действия `screenshot` (дефолт ⌘⇧S / Ctrl+Shift+S) или иконка `Crop` в тулбаре Composer → выделение области → PNG уезжает вложением в черновик активного чата. Общая часть (`screenshot.rs`) — проверка разрешения, `backend::capture_region()`, base64 и события; оверлей у каждой платформы свой. На macOS это **C-код, вкомпилированный в бинарь приложения** (`src-tauri/native/region_capture.c`, собирается `cc` в `build.rs` **только под macOS**, экспорт `harpy_capture_region`/`harpy_capture_region_free`, Rust-обёртка — `screenshot/macos.rs`). Исходник взят из плагина `harpyshot` (репозиторий `harpyhare-plugins`), но живёт здесь копией: sidecar-процессом его делать нельзя — грант TCC «Запись экрана» ключуется по cdhash, и у отдельного ad-hoc-бинаря он бы переспрашивался после каждой пересборки, тогда как у самого приложения он один на бандл.

Инварианты C-оверлея macOS (нарушишь — крэш или зависший UI):

- **Снимок всего экрана делается ДО показа оверлея** (`CGDisplayCreateImage` через `dlsym` — символ депрекейтнут, но на macOS 26 есть), выделенная область потом вырезается из него `CGImageCreateWithImageInRect`. Иначе в кадр попало бы собственное затемнение. Окно HUD в кадр не попадает вообще — оно `contentProtected`.
- **ObjC-классы оверлея регистрируются один раз**: `objc_getClass` перед `objc_allocateClassPair` обязателен — при втором вызове `allocateClassPair` вернёт NULL, и `objc_registerClassPair(NULL)` уронит приложение (в изначальном плагине проблемы не было: процесс жил одну активацию).
- **NSWindow сабклассится ради `canBecomeKeyWindow = YES`** — borderless-окно иначе не становится key и не получает keyDown, то есть Esc не отменял бы выделение.
- **Каждое событие своего цикла форвардится в `[NSApp sendEvent:]`** — цикл `nextEventMatchingMask` крутится внутри главного потока приложения, и без форварда всё остальное приложение стоит, пока пользователь тянет рамку.
- **Вызов только с главного потока** (`app.run_on_main_thread`) — это AppKit; команда и обработчик хоткея оба идут через `screenshot::on_capture_region`.
- Только главный дисплей (`CGMainDisplayID`); мультимонитор — отдельная задача.

Windows-оверлей (`screenshot/windows.rs`) — свой Win32 на GDI, и грабли те же по смыслу, но другие по механике: **снимок всего ВИРТУАЛЬНОГО экрана делается ДО показа окна** (`SM_XVIRTUALSCREEN`…, мультимонитор поддержан, начало координат может быть отрицательным — не считай его нулём); **класс окна регистрируется один раз за процесс** (`OnceLock`: повторный `RegisterClassW` вернул бы 0 — ровно та же грабля, что с `objc_allocateClassPair` в ObjC-версии, и по той же причине: процесс переживает много активаций); рисование двойной буферизацией с инвалидацией только изменившейся области (рамка + её прошлое положение), иначе полноэкранный перерисов на каждое движение мыши; **`PostQuitMessage` НЕ зовётся** — `WM_QUIT` убил бы цикл сообщений самого Tauri, выход из локального цикла идёт по флагу состояния; отмена — Esc, ПКМ или слишком маленькое выделение; результат — PNG без альфы.

Хост-часть: разрешение проверяется в Rust ДО оверлея (`platform::screen_capture_access`; на Windows такого права нет и функция всегда `true` — ветка «нет доступа» там просто недостижима); нет доступа → уходит `screenshot-error` с кодом `permission` **без системного промпта** (промпты живут только на экране «Доступы», см. ниже). Успех → PNG в base64 → `screenshot-ready` → `useRegionScreenshot` → **`useChats.addDraftImage`, то есть тот же конвейер вложений, что вставка/дроп картинки** (`fileToAttachment`, даунскейл >5 МБ, лимит вложений) — своей ветки обработки изображений у снимка нет. Окно после снимка поднимает `screenshot::deliver` через `window::show_and_focus_prompt`, поэтому возвращается не только окно, но и каретка в поле промпта: вопрос к вложению дописывается сразу, без клика мышью. **Тот же PNG уходит в буфер обмена** (`screenshot::copy_to_clipboard`, симметрично тому, как `recording::deliver_transcript` кладёт туда расшифровку) — снимок можно вставить в любое другое приложение, не пересохраняя. Это стоит фичи `image-png` у крейта `tauri` в `Cargo.toml`: `tauri::image::Image::from_bytes` объявлен под `#[cfg(any(feature = "image-ico", feature = "image-png"))]`, и без неё метода просто НЕ существует — ошибка выглядит как «нет такого метода», а не как «включи фичу». Фича общая для обеих платформ и `#[cfg]`-ветку не порождает, так что `bindings.ts` от неё не разъезжается. ACL трогать не пришлось: `capabilities/default.json` гейтит только `invoke` из вебвью, а мы пишем в буфер из Rust. Хоткей регистрируется в `window::register_main_window_hotkeys` (жизненный цикл HUD, как PTT/toggle/суфлёр) и перерегистрируется в `set_settings`; пока HUD не запущен, он не слушается. UI настройки — группа «Горячие клавиши» на экране настроек; разрешение «Запись экрана» выдаётся на экране «Доступы».

### Доступы (единственное место выдачи прав)

Весь раздел — **про macOS**: на Windows у WASAPI loopback разрешения нет вовсе (`permissions::AUDIO_REQUIRES_PERMISSION = cfg!(target_os = "macos")` — статус звука сразу `granted`, ни промптов, ни проб), у записи экрана тоже, поэтому экран «Доступы» там скрыт целиком (`screens.ts`, поле `platforms`). **Гейт готовности при этом выводится ТОЛЬКО из `permissions_status`, а не из видимости экрана**: на Windows команда отдаёт `granted`, блокера не возникает, и вести в никуда нечему. Соблазн написать «звук требуется, только если экран доступов есть» надо давить: тогда любая правка реестра экранов (перенос доступов внутрь «Настроек», ещё одна платформа) молча снимала бы требование доступа к звуку — ровно тот регресс, ради которого гейт и живёт в лаунчере. Команды доступов остаются в контракте на обеих платформах. Поля `audio_permission_requested`/`screen_permission_requested` на Windows не используются и остаются в `Settings` намеренно: форма настроек и биндинги обязаны совпадать на обеих платформах.

Все TCC-разрешения выдаются с одного экрана лаунчера (`features/launcher/screens/PermissionsScreen`, данные — хук `usePermissions` поверх `permissions.rs`). Модалки нет: на первом запуске лаунчер сам открывается на экране блокера (`LauncherPanel`, реф `landed` + `readiness.blockers[0].screen`), в остальное время экран доступен из сайдбара. Разрозненных точек выдачи больше нет и заводить их нельзя: удалены `useCapturePermission`/`useScreenCapturePermission`, баннер разрешения в HUD, строка «Запись экрана» во вкладке хоткеев и шесть отдельных команд (`capture_available`, `request_audio_capture_permission`, `open_audio_permission_settings`, `screen_capture_available`, `request_screen_capture_permission`, `open_screen_capture_settings`) — вместо них три: `permissions_status`, `request_permission(kind)`, `open_permission_settings(kind)`.

**Ни один системный промпт не должен появляться сам по себе** — только в ответ на кнопку «Выдать». Отсюда два инварианта:

- **`setup_app` НЕ создаёт капчер** (`App.capture` стартует `None`). Создание Core Audio tap и есть запрос разрешения: раньше он строился на старте и macOS показывала промпт при первом запуске, до того как пользователь что-то нажал. Капчер поднимается лениво — `recording::ensure_capture` при запуске HUD и при явном запросе доступа. Не возвращай `build_capture` в `setup_app`. **И не зови его из `launch_main_window` синхронно** — только `spawn_blocking`: создание капчера медленное (на Windows старт WASAPI-потока ждёт готовности до 5 секунд), а `launch_main_window` — синхронная команда, поэтому ожидание внутри неё держит запуск целиком: окно HUD уже создано, но вебвью не успевает отрисоваться (белое окно), а лаунчер не уничтожается, потому что до его `destroy` дело не дошло. Жизненный цикл окна не должен зависеть от готовности звука: нет устройства — HUD всё равно открывается, а PTT честно сообщает об ошибке.
- **Состояние звука знать без промпта нельзя** (у Core Audio нет preflight, в отличие от `CGPreflightScreenCaptureAccess`), поэтому первый запрос фиксируется флагом `Settings.audio_permission_requested`: пока он `false`, статус — `unknown` и проб не делается; после первого нажатия «Выдать» статус определён, и повторная проба уже безопасна (промпт возможен только при статусе «не спрошено»). По той же причине `rebuild_capture_now` (смена аудиоустройства) ранне-выходит, пока капчер ни разу не строился и флаг не взведён.
- **`screen_permission_requested` — про «спрашивали ли», а не про сам доступ.** `CGPreflightScreenCaptureAccess` не отличает «отказано» от «ещё не спрашивали», а без этого различия модалка всплывала бы при каждом запуске у того, кто осознанно отказался от необязательного доступа. Поэтому: preflight `true` → `granted` (даже если флага нет — доступ могли выдать мимо приложения), иначе флаг решает `denied` против `unknown`. Автооткрытие модалки — по `needsAttention` (звук не выдан ИЛИ про экран ещё не спрашивали), а не по `allOk`.

`PermissionState` — `unknown | granted | denied`. Звук required (без него кнопка запуска HUD заблокирована), запись экрана — нет: она нужна только снимку области.

**Геометрия строки доступа не зависит от его состояния** — это не косметика. TCC-промпт на звук асинхронный: команда возвращает `denied` раньше, чем пользователь нажмёт «Разрешить», то есть статус меняется прямо под курсором, и любая зависимость размеров от состояния дёргала бы кнопку из-под пальца. Отсюда: колонка действий фиксированной ширины (`grid-cols-[…_14rem]` — ровно та же колонка контролов, что у `SettingRow` в `fields.tsx`; прежние `10.75rem` не давали контролам соседних экранов встать на общую вертикаль), у «Выдать» `min-w-18`, у пояснения `min-h-9` (одна и две строки занимают одинаково), набор кнопок одинаков для `unknown` и `denied` — у `denied` «Выдать» работает повторной пробой и ловит ровно этот случай («разрешил по промпту после того, как команда уже вернула отказ»); только `granted` убирает кнопки, и по высоте строка от этого не меняется. Про недостающий доступ говорит статус в шапке рядом с кнопкой «Запустить»: он называет блокер словами и кликом ведёт на его экран — `disabled` без объяснения не оставляем.

### Лаунчер: шапка, сайдбар, экраны

Окно лаунчера — три части: **шапка** (`LaunchBar`: бренд, поиск, статус готовности, «Запустить»), **сайдбар** (`Sidebar`) и **экран** (`ScreenShell` + содержимое). Реестр экранов — `screens.ts` (`LAUNCHER_SCREENS`: id, лейбл, описание, иконка, группа и **необязательный список платформ**: без него экран есть везде, с `platforms: ["macos"]` — «Доступы» — на Windows не рисуется вообще); сайдбар рисует группу `content` (Контексты, Пресеты) сверху и группу `system` (Настройки, Доступы, Обновления) прижатой к низу через `mt-auto` — **прижатие проверено на живом виде и подтверждено владельцем: не убирать**, даже если пустота между группами кажется дырой в вёрстке. **Сайдбар — только иконки, без подписей на любой ширине** (`w-10`): подписи были, но при втором рельсе внутри настроек два текстовых столбца съедали треть окна. Название экрана пользователь видит в `title` и в заголовке `ScreenShell`, так что смысл не теряется. Точка на пункте — `SidebarNotice {screen, label, kind}` (блокеры готовности и доступное обновление), и **`label` обязан уходить в `title` пункта** («Доступы — Нет доступа к записи системного звука»): в иконочном сайдбаре без этого висит точка, про которую негде спросить, что она значит.

**Шапка лаунчера живёт на линии «светофора» macOS.** Заголовок окна отдан контенту: `platform::merge_titlebar_into_content` (вызов в конце `create_launcher_window`) через objc ставит `NSWindowStyleMaskFullSizeContentView` + `titlebarAppearsTransparent` + `titleVisibility = hidden`; на Windows это осознанный no-op (там своя рамка). Билдерные `title_bar_style`/`hidden_title` не использованы намеренно — они `#[cfg(target_os = "macos")]`, а `#[cfg]`-ветку посреди общего `window.rs` заводить нельзя (см. правило платформенного расщепления); фасад `platform::` — тот же приём, что у `clip_native_window_corners`. Следствия: шапка (`h-9`) обязана иметь левый отступ под кнопки окна на macOS (`PLATFORM === "macos"` во фронте — из Rust платформу не спрашиваем), а перетаскивание окна за шапку теперь наше (`useWindowDrag`), потому что вебвью накрывает нативный тайтлбар.

**Внутри экрана «Настройки» — второй, вложенный рельс табов** (`settings-tabs.ts` + `SettingsTabsRail`, семь табов по числу секций; реестр устроен как `screens.ts`). До него все семь секций висели одним свитком и найти нужное было тяжело. Три следствия, которые легко нарушить:

- **Брейкпоинт `min-[900px]`, а не `lg`/`md`, и это посчитано, а не на глаз**: окно лаунчера открывается 1000×720 при минимуме 520 (`window.rs`). На `lg` (1024) окно дефолтного размера показывало бы один рельс иконками, на `md` (768) первый рельс уже 160px и подписям второго не остаётся места. 900 — единственный порог, где дефолтное окно с подписями, а узкое не рвётся.
- **Подписи табов короткие намеренно** («Ключи», «Клавиши», «Действия», а не «Ключи и доступ»…): при двух рельсах длинные обрезались многоточием прямо в интерфейсе. Развёрнутый смысл несёт `description`, который экран печатает строкой над секцией.
- **`SettingsScreen` рендерит секции через `Record<SettingsTabId, ReactNode>`, а не `switch`** — компилятор требует, чтобы для каждого таба реестра нашлась секция. Порядок табов в реестре — по частоте задач, а не по алфавиту и не по истории появления, поэтому «Действия» стоят раньше «Окна» (задача редкая) — не пересортировывай.

**Поиск по лаунчеру** (`search.ts` + `LauncherSearch` в шапке, по центру между брендом и кнопкой запуска). Индекс собирается ИЗ РЕЕСТРОВ, а не переписывается руками: экраны из `LAUNCHER_SCREENS` (с тем же платформенным фильтром `screenGroup`), хоткеи из `HOTKEY_ACTIONS`, табы настроек из `SETTINGS_TABS` (лейбл И описание — таб находится по тому, что в нём лежит), строки доступов из `PERMISSION_ROWS`, ключи API из `API_KEY_IDS`, шаги окна и строка «Сочетание» быстрых действий деривированы из `hotkeyAction(...)`; пользовательские пресеты, быстрые действия и материалы библиотеки приходят параметром `SearchSources`. Руками задан только список обычных строк настроек (`SETTINGS_ROWS`) — их подписи И хинты обязаны совпадать с текстом в секциях дословно, иначе поиск будет находить формулировки, которых на экране нет; поэтому и переименование строки («Язык» → «Язык распознавания»), и переписывание её хинта («Whisper распознаёт точнее…» → «Распознавание точнее…», когда вендоров стало два), и новая строка вроде «Провайдер распознавания» — всегда парная правка секции и `SETTINGS_ROWS`. **Реестр `PERMISSION_ROWS` вынесен в `features/launcher/permission-rows.ts`, а не оставлен в файле экрана**: потребителей у него два (экран и поиск), а экспорт данных из файла с компонентом ломает fast refresh (`react-refresh/only-export-components`; массив под `allowConstantExport` не подпадает, и правило выключено только для `components/ui/**`). Хиты доступов гейтит видимость самого экрана (тот же `screenGroup`), поэтому на Windows их в выдаче нет. **`API_KEY_IDS` (`lib/api-keys.ts`) — единственный список ключей**: в поиске завелась было третья копия, и разъезжаться она стала бы молча. **Действие `opacity` из индекса исключено** константой `HOTKEYS_WITHOUT_SETTINGS_ROW`: строки настройки модификатора прозрачности нет ни в одном табе, и хит вёл в «Окно» на строку, которой не существует, — мёртвый маршрут. Появится строка — исключение снять. **Таб для хоткея выводится из `kind`, а не из списка id**: `combo → hotkeys`, `modifier_arrows`/`modifier_plus_minus → window`, `modifier_digits → quick-actions` — иначе «Прозрачность» и «Скролл чата» уводили бы в «Клавиши», где их не настраивают. Клик по результату переключает экран И таб одним `goTo({screen, tab})`. **Выдача поиска — однострочные хиты** (title слева, breadcrumb справа `text-hint`, контейнер на `shadow-pop`), а не двухэтажные строки: это паттерн командных палитр (Raycast/VS Code), а прежние два этажа повторяли одинаковый breadcrumb «Настройки → …» на каждой строке подряд — половина высоты списка уходила на дубли. **Обёртка шапки в `LauncherPanel` обязана быть `relative z-30`, и это не украшение**: выдача (`z-20`) живёт ВНУТРИ неё, а `.launcher-rise` — анимируемый элемент, которому WebKit держит собственный stacking-контекст (`animation-fill-mode: both`), так что `z-20` заперт внутри обёртки; блок экрана идёт в DOM позже и без поднятого слоя шапки рисовался ПОВЕРХ выдачи — карточки настроек просвечивали сквозь список, часть хитов пряталась под ними. Поднимать надо именно всю обёртку: во время entry-анимаций stacking-контекстами становятся все три rise-обёртки разом. **Выдача обязана нести `data-no-drag`**: шапка целиком — драг-зона окна (`useWindowDrag`), а список висит под ней, и клик по любому неинтерактивному месту (пустота между строками, «Ничего не найдено», строка переполнения) утаскивал окно вместо выбора. **Глобального сочетания вроде ⌘K у поиска нет намеренно** — в проекте запрещены захардкоженные сочетания, а своей инфраструктуры хоткеев у лаунчера нет; понадобится — заводить действием в реестре `hotkeys.rs`. Фильтрует один `screenGroup(group, platform)`; гейт готовности на видимость экранов НЕ опирается (см. «Доступы»). Модалок в лаунчере не осталось: доступы и обновления — полноценные экраны, а не диалоги.

- **Заголовок и описание экрана рисует только `ScreenShell`**, по данным из `screens.ts`. Панель внутри своих заголовков не заводит — иначе вернётся прежняя тавтология, когда лейбл вкладки повторялся заголовком карточки внутри неё. Оба стоят в ОДНУ строку: заголовок `shrink-0`, описание рядом с ним `truncate` плюс `title` с полным текстом, — поэтому **длинное описание в `screens.ts` не перенесётся, а обрежется**, и рассчитывать на вторую строку нельзя.
- **`[keywords]: [...]` — объявление терминов для распознавания, а не инструкция модели.** Парсер и вырезание — `lib/keywords.ts` (`extractKeyterms`/`stripKeywordBlocks`/`chatKeyterms`), читаются ВСЕ источники системного промпта: препромпт, выбранные материалы библиотеки и контекст чата. Четыре решения, каждое неочевидно. (1) **Блок вырезается из системного промпта** (`chatSystemPrompt` мапит `stripKeywordBlocks`): это конфигурация распознавания, и отвечающая модель не должна получать директиву, которую обязана игнорировать; сырые источники отдаёт `chatPromptSources` — он же кормит сбор терминов. (2) **Термины объявляются, а не извлекаются эвристикой из прозы.** Лимит вендора маленький и жёсткий, и эвристика, потратившая его на частотные слова, ухудшит распознавание, а не улучшит. (3) **Путь до бэкенда — не настройка, а push:** запись стартует с глобального хоткея, React в этот момент не участвует, поэтому `useSttKeyterms` в App.tsx заранее шлёт `set_stt_keyterms` при смене активного чата (эффект сторожится склейкой массива — новый массив с теми же словами не должен слать повторно), а `recording.rs` читает `App.stt_keyterms` в момент запроса. (4) **Термины идут ПОЗАПРОСНО, а не билдером клиента:** они меняются с активным чатом, а пересборка клиента выбросила бы прогретый пул соединений — то самое, на чём держится «отпустил → текст».
- **Умение принимать термины объявлено по вендорам** (`stt::registry::SttKeyterms`) и измерено, а не предположено: xAI — `Repeated { field: "keyterm", max: 100 }` и **выше лимита отвечает ошибкой, а не обрезает**, поэтому кап обязателен (`SttKeyterms::accepted`); Groq — `Prompt { field: "prompt" }`, все термины одной строкой; `gpt-4o-mini-transcribe` — `Unsupported`: он принимает `prompt` и демонстративно его игнорирует, а слать то, что ничего не делает, значит создавать веру в работающую фичу. Ключевое: **у xAI биасинг наблюдаемо меняет вывод** (проверено живым запросом), у mini — нет.
- **Пул пресетов никогда не едет вниз по версии, и это единственное, что позволяет попробовать правку до публикации.** `remote_presets` работает в три слоя: вшитый `config/presets.json` (`include_str!`), кэш `presets.cache.json` в папке приложения и блоб, который опрашивается на старте и каждые 30 минут. Два правила делают эту схему предсказуемой: `load_initial` берёт **более новый** из кэша и вшитого пула (не «кэш всегда важнее» — иначе свежая сборка показывала бы старые пресеты, пока блоб не догонит), а `apply` **отказывается применять пул с версией ниже текущей** и пишет об этом в stderr. Без второго правила цикл обновления затирал бы локальную правку блобом в течение получаса, а неудачная публикация старого файла доезжала бы до всех пользователей. **Поэтому `version` в `config/presets.json` обязан расти при каждой правке** — без бампа новый пул не победит ни кэш, ни блоб. Откат делается публикацией с БОЛЬШЕЙ версией, а не заливкой старого файла.
- **Встроенные пресеты несут свои `[keywords]`** (`config/presets.json`, по 15–27 терминов на тему, русские и латинские написания рядом) — это единственный способ, которым пользователь узнаёт о синтаксисе, кроме подписи под редактором пресета (`KEYWORDS_HINT` в `PresetsSection`). Правка `config/presets.json` не доезжает до пользователей сама: вшитая копия обновится со сборкой, публичная — только `npm run presets:publish`.
- **Готовность не называет вендора — и это главное правило экрана ключей.** `accessGaps` (`lib/api-keys`) проверяет ровно две вещи: есть ли ХОТЬ ОДИН доступный провайдер ответов (`availableAnswerProviders` — по `modelProvidersMissingKey`, то есть с учётом и своих ключей, и кода доступа) и есть ли ключ у ВЫБРАННОГО провайдера распознавания. Раньше здесь стоял `missingApiKeys` с жёстким списком `["anthropic", <stt>]` — наследие времён, когда Claude был единственным способом получить ответ; **не возвращай список обязательных вендоров**: с ключом только от xAI приложение полностью работоспособно, и требовать ключ Anthropic значит блокировать рабочую конфигурацию. Оба гэпа ведут на вкладку `"access"`, потому что чинятся они там же — либо ключом, либо сменой провайдера распознавания.
- **Новый чат открывается на модели, до которой реально дотянуться.** `defaultModelFor` (`lib/models`) берёт `defaultModel` первого НЕзапертого провайдера реестра, `App.tsx` передаёт это в `useChats` **геттером, а не значением** — ключ, добавленный посреди сессии, должен менять следующий чат без перезапуска. Поле `default_model` в строке реестра объявлено явно, а не выведено как «первая модель каталога»: каталог упорядочен флагманом вперёд для пикера, а новому чату нужна БЫСТРАЯ модель — та же причина, по которой глобальный дефолт haiku, а не opus (у OpenAI это `gpt-5.4-mini`, у xAI `grok-4.3`; тест `every_provider_defaults_to_a_model_it_actually_offers` держит дефолт внутри каталога). Без этого пользователь с одним ключом xAI получал бы чат на claude-haiku, который его аккаунт не может вызвать, — экран выглядит готовым, а отправка падает.
- **Экран ключей показывает СОСТОЯНИЕ вендоров, а не два поля.** `ApiKeysSection` рисует строки «Отвечают» и «Распознают речь» с галочкой/замком у каждого вендора (`modelProvidersMissingKey`/`sttProvidersMissingKey`), потому что смысл экрана теперь «любой один отсюда и любой один оттуда», а не «заполни оба поля». **Поля ключей показываются ровно те, которые код доступа не заменяет** — `visibleApiKeys` (`lib/api-keys`) оставляет под активным кодом только ключи вендоров с `proxied: false`, сложенных из ОБОИХ реестров (`MODEL_PROVIDERS` + `STT_PROVIDERS`), руками их перечислять нельзя; пока `proxied: true` стоит у всех, под кодом полей ключей нет вовсе, а свой ключ вводится после «Отвязать». Это единственное место, где зависимая строка ПРЯЧЕТСЯ, а не гасится (общее правило — ниже, в абзаце про слайдеры): четыре пустых поля под работающим кодом читались как незаконченная настройка, а погашенные — как то же самое, только серым. Цена скрытия снята явно: `SearchSources.apiKeys` несёт тот же `visibleApiKeys(draft)`, поэтому поиск индексирует ровно показанные поля и мёртвого маршрута не остаётся. Описание группы и подсказка строки «Код доступа активен» тоже считаются из непроксируемых, а не написаны на один случай.
- **Готовность структурная, а не булева.** `useLauncherReadiness` отдаёт `blockers: {label, screen, tab?}[]`, `checking` и `ready`. `tab` несёт блокер ключей (`"access"`), поэтому и статус в шапке, и посадка первого экрана ведут на конкретную вкладку, а не просто на экран «Настройки»; сейчас `DEFAULT_SETTINGS_TAB` с ней совпадает, но полагаться на это совпадение нельзя — оно косметическое. `checking` (`!permissions.loaded`) обязателен: `audioOk` до ответа `permissions_status` равен `false`, и без этого флага настроенный пользователь на КАЖДОМ запуске видел «нет доступа к звуку» и заблокированный запуск. Кнопка запуска гасится при `checking || !ready || launching`, а статус рядом с ней называет первый блокер словами и ведёт на его экран.
- **Первый экран выбирается по блокеру** (реф `landed` в `LauncherPanel` — ровно один раз за сессию окна, после того как доступы опрошены). Нет ключей → «Настройки» + вкладка из `blocker.tab`, нет звука → «Доступы», всё в порядке → `DEFAULT_SCREEN`.
- **Форма настроек — один язык на все строки** (`fields.tsx`): `SettingGroup` (**заголовок и описание вынесены НАРУЖУ карточки** — `SectionLabel` + пояснение над ней, внутри `rounded-lg`-карточки только строки через `divide-y`; шапки внутри карточки больше нет), `SettingRow` (подпись + пояснение слева, контрол в колонке фиксированной ширины справа), `SettingBlock` (когда контрол занимает всю ширину), `SettingSelect`/`SettingSwitch`/`SettingSlider`. Прежние `Field`/`SelectField`/`SwitchRow`/`SectionColumns` удалены: подпись поля и подпись тумблера рисовались двумя разными способами, а трёхколоночная сетка ломала длинные лейблы.
- **`SectionLabel` — единственная uppercase-микроступень в обоих окнах** (`text-hint` + `font-semibold` + `tracking-wider` + `uppercase`): заголовок `SettingGroup`, группы `HotkeysPopover`, секции диалога «Контекст», папки библиотеки, шапка превью — все через компонент, строку этих классов в разметке не дублировать. Больше капса в интерфейсе нет нигде, кроме брендовой строки `LaunchBar`: uppercase маркирует ровно один уровень иерархии, второй такой ступени не заводить.
- **Ограниченное число задаётся только слайдером с readout.** Голый `type=number` для `move_step`/`resize_step`/`scroll_step`/`buffer_seconds` удалён намеренно: `Number("")` давал 0, а введённое сверх лимита оставалось в UI, хотя Rust уже клампнул значение на диске (`draft` синкается из `settings` только по `access_token`). Слайдер физически не выходит за `SETTINGS_LIMITS` — рассинхрона нет by design. **Зависимая строка гасится, а не прячется**: «Глубина буфера» рендерится всегда и при выключенном `buffer_enabled` уходит в `disabled` (проп `SettingSlider`, он же приглушает readout). Условное скрытие дёргало высоту карточки на переключении тумблера и оставляло в поиске мёртвый маршрут — хит вёл на строку, которой в этот момент нет на экране. Единственное исключение — поля ключей под активным кодом доступа: там скрытие осознанное, и мёртвый маршрут снят на стороне поиска (см. «Экран ключей»).
- **Парные настройки живут в одной строке.** Модификатор и его шаг (перемещение / размер / скролл) настраиваются вместе в `WindowSection`; раньше модификатор был во вкладке «Горячие клавиши», а шаг — во вкладке «Вид», и так трижды.
- **Поверхности лаунчера разведены светлотой, а не альфой.** Переопределения живут в `body.launcher` (и `:root[data-theme="black"] body.launcher` — иначе чёрная тема не доедет из-за равной специфичности): `--background`/`--card`/`--popover`/`--surface`/`--surface-active` — непрозрачные ступени, `--ring` отвязан от `--primary` (бордовое кольцо при 50% альфы было практически невидимым в окне настроек). **Порядок ступеней важен: в лаунчере `--popover` (0.245) СВЕТЛЕЕ `--card` (0.21)** — это и есть элевация меню, поповеров и диалогов над карточками формы; уравняешь их — выпадающий список сольётся с карточкой, над которой висит. Нейтральная база углублена в обеих темах (лаунчер 0.17/0.12, HUD 0.25/0.16 для gray/black) — светлее её не поднимать: на ней держится контраст hairline-бордеров `oklch(1 0 0 / 8…12%)`. Это единственный шов, который не задевает HUD: окна — разные документы, но `index.css` общий, поэтому в `:root` для лаунчера ничего не правим.
- Шкала шрифтов — `--text-hint`/`--text-caption`/`--text-body`/`--text-chat`/`--text-title` (`cn` знает о них через группу `font-size` в `lib/utils.ts`); другие ступени не выдумывать, их нет. **Примитивы `components/ui/*` переведены с сырых `text-sm`/`text-xs`/`text-lg` на ступени шкалы**: тейлвиндовские 14px у кнопки, инпута и селекта против 12.5px `--text-body` у подписи рядом означали, что контрол крупнее собственного лейбла. Примитивы общие для обоих окон, поэтому та же шкала досталась HUD — это не побочный эффект, а условие: две шкалы в одном наборе примитивов не удержать. Менять `--text-body`/`--text-caption` глобально по-прежнему нельзя — на них стоит вся вёрстка чата.
- **Смена экрана и таба — entry-анимация, и она обязана иметь `motion-reduce`-выход.** Обёртки контента несут `key={screen}` / `key={tab}` (без ремоунта анимация не перезапустится) и `animate-in duration-150 fade-in-0 slide-in-from-bottom-1 motion-reduce:animate-none` — тот же паттерн и та же длительность tw-animate-css, что у `SelectContent`/поповеров; каскад входа окна — `.launcher-rise` 0.38s с шагом `RISE_STEP_MS` = 50мс на обёртку. **`@media (prefers-reduced-motion: reduce)` в `index.css` гасит и въездной каскад, и бесконечный шиммер — `.launcher-rise`, `.thinking-shimmer`**: заводишь свой `@keyframes` — дописывай его в тот же селектор, иначе с выключенной анимацией в системе останется единственная дёргающаяся деталь. Canvas-орб туда не входит — его глушит `StatusOrb` через `usePrefersReducedMotion`. Transform- и opacity-анимации над карточками здесь разрешены, хотя в HUD запрещены (см. «Кнопки действий сообщения»): несмытые пиксели композитных слоёв — артефакт ПРОЗРАЧНОГО frameless-окна, а лаунчер непрозрачен (`body.launcher` заливает фон, окно строится без `transparent`) — прецедент `.launcher-rise` живёт там давно и следов не оставляет.

### Размер шрифта чата — хоткей со скобками

`chat_font_size` — действие реестра вида `modifier_brackets` (дефолт ⌘ / Ctrl со скобками `[` и `]`, `scope: hud`). Оно живёт по тем же правилам, что и прозрачность: у семейства хранится только модификатор, подпись «[ ]» даёт `KIND_HINTS`, а собственной строки настройки в лаунчере у него нет — модификатор не редактируется, работает дефолт из реестра (`HOTKEYS_WITHOUT_SETTINGS_ROW`). Поиск лаунчера ведёт на вкладку «Вид», где стоит слайдер того же размера.

- **Голый ⌘ уже занят двумя семействами** (сдвиг окна стрелками и быстрое действие цифрами), и это не конфликт: по правилам реестра разные семейства на одном модификаторе сосуществуют, потому что их клавиши не пересекаются.
- **Шаг хоткея (1px) крупнее шага слайдера (0.5px) намеренно:** слайдером подбирают точно, хоткеем — на ходу во время разговора, и половина пикселя за нажатие означала бы двадцать нажатий на весь диапазон.
- **Матрица конфликтов больше не расписана попарно.** Раньше каждый вид добавлял по девять веток в `key_spaces_overlap`; теперь вид объявляет своё семейство клавиш в `family_keys`, а правило («два полных сочетания — по клавише, два семейства — по модификатору и только одинаковые, сочетание против семейства — по попаданию клавиши») записано один раз. Матч в `family_keys` исчерпывающий, поэтому новый вид по-прежнему обязан объявиться, иначе крейт не соберётся. Зеркало во фронте — `fallsIntoFamily` в `lib/hotkey-conflicts.ts`, и оно тоже требует новой ветки.

### Нумерация строк кода

Номер стоит на каждой строке блока, как в редакторе. **Строки нарезает `splitRenderedLines` (`lib/code-lines`), а не `text.split("\n")`:** после подсветки содержимое — дерево `span`'ов, и перенос строки почти всегда лежит ВНУТРИ токена (блочный комментарий, многострочная строка, шаблон). Функция обходит дерево рекурсивно и переоткрывает попавший на границу `span` на следующей строке — иначе подсветка разъезжается ровно на тех конструкциях, ради которых её и включали.

- **Каждая строка — свой узел, и это не прихоть.** Отдельная колонка с номерами рядом с монолитным `pre` рассыпается при включённом переносе: визуальных строк становится больше, чем номеров. С узлом на строку перенос ведёт себя как в IDE — номер остаётся у первой визуальной строки, продолжения идут без номера.
- **Колонка номеров липкая (`position: sticky; left: 0`)** и красится в `--code-surface`, поэтому при горизонтальной прокрутке длинной строки номера не уезжают. Ради этого горизонтальные отступы сняты с `pre` и отданы частям строки: липкий элемент цепляется за край прокрутки, а не за край padding-бокса.
- **`user-select: none` на номерах обязателен** — иначе выделение кода мышью утаскивает в буфер и нумерацию. Кнопка копирования этим не затронута: она берёт сырой `code`, а не выделение.
- Ширина колонки выводится из числа строк (`--code-gutter` в `ch`), минимум две цифры, чтобы блок не дёргался на переходе через десяток во время стрима.

### Поверхность кода непрозрачна намеренно

`--code-surface` — сплошной тёмный тон, а не альфа поверх фона. Прежние `oklch(0 0 0 / 30%)` накладывались на и без того полупрозрачный `.app-shell`, поэтому сквозь блок кода читался рабочий стол за окном: на светлом документе позади код становился нечитаемым первым, хотя ради него ответ и открывают. Островки непрозрачности в прозрачном окне уже есть (док, `ConnectivityOverlay`), и код — такой же случай. Тот же токен несёт html-чип, так что оба выглядят одинаково.

### Кластеры иконок выглядят одинаково

Группа иконочных кнопок оформляется **одним классом** — `ICON_CLUSTER_CLASS` (`components/IconCluster`): пилюля `rounded-full` на `bg-background` с внутренним кольцом. Его носят док действий, кластер над сообщением ассистента и кластер у пузыря пользователя. Своя поверхность под каждый кластер заводиться не должна: именно так кнопки над сообщением получили модальный чип с тенью и размытием (`FLOATING_CHIP_CLASS`) и стали выглядеть чужеродно рядом с плоским доком. **`FLOATING_CHIP_CLASS` остаётся только у кнопки «↓ Вниз»** — она одиночная и висит над лентой, а не над конкретным сообщением.

Поверхность даёт кластер, поэтому у кнопки внутри своей заливки нет — только ховер (`ICON_CLUSTER_BUTTON_CLASS`).

### Диалог «Контекст чата» не выше экрана

У панели диалога есть общий потолок `max-h-[calc(100dvh-2rem)]` (в `ui/dialog`), и это страховка для ВСЕХ диалогов: без неё содержимое просто уезжало за край без возможности доскроллить. Считалось легко — при минимальной высоте окна 520px шапка, список библиотеки (192px), описание, поле своего текста (160px) и футер давали около 556px, и кнопки «Отмена/Сохранить» оказывались за экраном.

- **Шапка и футер закреплены, прокручивается только тело** (`min-h-0 flex-1 overflow-y-auto`): кнопки сохранения обязаны быть достижимы при любом числе материалов.
- **Список библиотеки ограничен относительно экрана** (`max-h-[min(12rem,32dvh)]`), а не фиксированными пикселями: фиксированный потолок на низком окне съедал место у поля ввода, а на высоком зря прокручивался.
- **Фильтр появляется от восьми материалов** (`LIBRARY_FILTER_MIN_DOCS`): до этого порога он только мешает, после — без него материал ищут прокруткой.
- **Счётчик выбранного стоит в заголовке секции**, потому что выбранные материалы разбросаны по списку и при прокрутке не видны.
- Длинные имена обрезаются с `title`: без него обрезанное имя нечитаемо совсем.

### Блок кода: одна оболочка на стрим и на историю

Фенсед-код рисует `CodeBlock` — шапка с языком и числом строк плюс копирование и перенос строк. **Оболочка одна на оба пути рендера**: `makePre` (готовое сообщение, содержимое подсвечено) и `OpenFenceBlock` (незакрытый fence во время стрима, содержимое сырое). Это не дублирование ради симметрии: пока fence открыт, подсветку намеренно не гоняют, и если бы у стрима была своя разметка, блок прыгал бы на закрывающем маркере — менял бы высоту, рамку и положение текста ровно в тот момент, когда пользователь его читает.

- **`html` проверяется ДО `CodeBlock`.** Html-блок уходит в `HtmlBlockChip` с кнопкой превью, и инвариант `plainText: ["html", "system-design"]` (children код-элемента остаются сырой строкой) по-прежнему держит именно чип, а не блок.
- **Сырой текст блока достаёт `reactChildrenText`**, потому что после подсветки children — дерево `span`'ов. Он кормит и счётчик строк, и кнопку копирования: копировать разметку вместо кода — тихая порча буфера.
- **Число строк склоняется** (`linesLabel` в `lib/code-block`): «3 строки», а не «3 строк». Тот же хелпер считает строки в html-чипе — двух реализаций счётчика быть не должно.
- **Язык берётся из класса `language-*`**, а служебные подписи подсветки (`hljs`, `plaintext`, `text`) за язык не считаются: подпись «plaintext» в шапке хуже, чем нейтральное «код». У стрима язык читается из инфо-строки открывающего маркера (`openFenceLanguage`).
- **Рамку, фон и радиус несёт контейнер, а не `pre`**: отступы и `overflow-x` остаются на `.prose-answer pre`, потому что тот же `pre` без оболочки рисует читалка заметок. Перенос строк — атрибут `data-wrap` на контейнере, а не класс на `pre`.
- **Перенос длинных строк включён по умолчанию.** Окно узкое и висит поверх созвона: горизонтальная прокрутка там требует второй руки, перенос — нет. Форму кода он ломает, но прочитать строку целиком важнее; выключается одной кнопкой, и нумерация это переживает (номер остаётся у первой визуальной строки).
- **Кнопки блока — нативный `title`**, как и остальные кнопки внутри ленты сообщений (см. раздел про подсказки).

### Подсказки: один провайдер на окно, две системы намеренно

`TooltipProvider` Radix стоит **один раз на окно** — в `render-root.renderWindowRoot`, рядом с `QueryClientProvider` и `Toaster`. Заводить его внутри `ShortcutTooltip` нельзя: провайдер держит общий таймер задержки и пропуск задержки при переходе между соседними триггерами, и по провайдеру на подсказку эта координация ломается, а на каждую кнопку дока и каждый таб приходится свой контекст.

**Кнопки действий сообщения (`MessageActions`) намеренно остались на нативном `title`, а не на `ShortcutTooltip`.** Это не забытая унификация: их три на сообщение, и в истории на сотню сообщений Radix-подсказка означала бы триста смонтированных оверлейных корней в том самом списке, ради которого мемоизируется `ChatHistory`. Плюс кнопки и так проявляются по ховеру — мгновенная подсказка поверх только что появившейся кнопки мигала бы при каждом движении мыши вдоль ленты. Шапка (табы, «плюс», дубликат, док, переключатель режимов) — на `ShortcutTooltip`, и это граница: **в ленте сообщений — нативный `title`, в шапке и оверлеях — свой тултип.**

Подпись сочетания уходит в проп `shortcut` отдельным чипом `<kbd>`, а не вклеивается в текст подписи: в чипе глиф вроде `␣` или `⏎` читается как клавиша, а в прозе — как опечатка. Поэтому хелпера «подпись плюс сочетание в скобках» в `lib/hotkeys` нет и заводить его не надо.

### Хоткеи: реестр действий

Все клавиатурные команды приложения перечислены **в одном месте** — `src-tauri/src/hotkeys.rs`, константа `HOTKEY_ACTIONS` (уезжает в биндинги через `.constant()`, фронт читает её же). У действия есть `id`, `group`, `label`, `hint`, `kind`, `scope` и `default_combo`. Захардкоженных сочетаний в коде больше нет и заводить их нельзя: и Rust, и фронт спрашивают `hotkeys::effective(&settings.hotkeys, ACTION_X)` / `effectiveCombo(settings.hotkeys, "x")`.

- **`kind`** — `combo` (полное сочетание), `modifier_arrows` (модификатор + стрелки), `modifier_plus_minus` (модификатор + `+`/`−`) `modifier_digits` (модификатор + цифра 1…`QUICK_ACTION_LIMIT`; единственный носитель — `quick_action`) и `modifier_brackets` (модификатор + `[`/`]`; носитель — `chat_font_size`). Семейства не разворачиваются в биндинг на каждую клавишу: у них хранится только модификатор, а подпись семейства даёт `comboLabel` по таблице `KIND_HINTS` в `lib/hotkeys.ts` — «1…9» там тоже деривировано из `QUICK_ACTION_LIMIT`, а не выписано литералом.
- **`scope`** — где действие слушается: `global` (шорткат ОС, живёт вместе с HUD), `recording` (только пока идёт запись), `hud` (обработчики вебвью), `teleprompter` (только пока открыт суфлёр), `streaming` (только пока идёт ответ; носитель — `cancel_stream`).
- **`scope: global` описан в реестре, но регистрируется вторым, независимым списком — таблицей `GLOBAL_HOTKEYS` в `window.rs`** (тройки id + `register_*`/`unregister_*`). Разъезд между ними молчаливый: глобальное действие, забытое в таблице, не регистрируется НИКОГДА и не даёт ни ошибки, ни строки в stderr — в лаунчере поле настройки есть, в поповере HUD подсказка есть, хоткей просто не работает. Закреплено тестом `window/tests.rs::global_scope_actions_and_the_registration_table_agree`: сверка идёт в обе стороны (каждое `Global`-действие обязано быть в таблице, каждая строка таблицы обязана быть `Global` в реестре) и оба списка читаются кодом, а не перечисляются литералами id, — иначе тест правился бы вместе с багом.
- **Пустой `combo` = «не назначено»**, действие просто не регистрируется. `normalizeDraft` в лаунчере больше НЕ подставляет дефолт вместо пустого значения — иначе снятый хоткей возвращался бы сам собой.
- **`default_combo` — не строка, а пара платформ** (`PlatformCombo {macos, windows}`): Rust берёт своё через `.current()`, фронт — через `defaultCombo(id, platform)` с дефолтом `PLATFORM`. Основной модификатор выводится макросом `primary_combo!` (⌘ на macOS, Ctrl на Windows), поэтому пары не выписываются руками. **На Windows клавиша Win под модификатор не отдаётся** — она занята системным снапом окон, а `Win+Shift+S` вообще системный снимок экрана; закреплено тестом `windows_defaults_avoid_the_super_key` (проверяет и дефолты, и `MODIFIER_COMBOS.windows`). Windows-дефолты: `Ctrl+Enter`, `Ctrl+R` (запись), `Ctrl+T` (суфлёр), `Ctrl+Shift+S`, `Ctrl+Shift+D` (фокус поля ввода), `Ctrl+Shift+H`, `Ctrl+Shift+N` (дубликат чата), `Ctrl+Shift+M` (меню моделей), `Ctrl` (сдвиг окна и быстрое действие), `Ctrl+Shift` (размер и прозрачность), `Alt` (скролл); `Escape`/`Space` общие. **Дефолт `model_menu` — ⌘⇧M / Ctrl+Shift+M, и клавиши редактирования текста под хоткеи не отдаются.** Раньше здесь стоял ⌘X: `useComboKey` слушает `keydown` на уровне `document` и зовёт `preventDefault`, гейт у него один — `!promptUnavailable`, то есть он включён ровно тогда, когда каретка в поле промпта, — и «вырезать» переставало работать во всём HUD (поле промпта, textarea «Контекста», строка поиска самого меню). `conflictsWithTyping` этого не ловит по построению (там только одиночные буквы и цифры), так что защиты снизу нет — свободной должна быть сама клавиша. **Не ставь дефолтом ⌘X/⌘C/⌘V/⌘A/⌘Z**; ⌘⇧M выбран как единственный одно-буквенный `Hud`-комбо, не пересекающийся с редактированием (`R` и `T` — `Global` и с печатью не конфликтуют). Сам хоткей гейтится `!promptUnavailable` (под суфлёром, оверлеем сети и в мини-режиме меню не открывается) — тот же мотив, что у дубликата чата; открытие — тоггл (`setModelMenuOpen((o) => !o)`), повторное нажатие закрывает. Тесты реестра (`hotkeys/tests.rs`) прогоняют разбор и отсутствие конфликтов для ОБЕИХ платформ, а не для текущей: платформа тестового хоста про вторую не говорит ничего.

**Конфликт = пересечение по клавишам И сосуществование областей.** Пересечение: два `combo` совпадают по модификаторам и клавише (регистр и порядок модификаторов не важны, `KeyS` и `S` — одно и то же); два семейства одного вида — по модификатору; `combo` конфликтует с семейством, если его модификатор совпадает, а клавиша попадает в семейство (стрелка, `+`/`−` либо цифра 1…9). Разные семейства на одном модификаторе НЕ конфликтуют — именно поэтому дефолтные «изменить размер» и «прозрачность» оба живут на ⌘⇧ / Ctrl+Shift, а «быстрое действие» мирно делит голый ⌘ / Ctrl с «передвинуть окно». Не сосуществуют любые две РАЗНЫЕ транзиентные области (`recording`, `teleprompter`, `streaming`), поэтому `Esc` штатно стоит и на отмене записи, и на закрытии суфлёра, и на остановке ответа.

**Политика разрешения — отобрать у прежнего владельца** (как в IDE): новое назначение всегда применяется, а конфликтующее действие остаётся без хоткея, о чём в UI пишется строкой «‹сочетание› снят у действия ‹название›». Это правило реализовано дважды и обе реализации покрыты тестами: `hotkeys::normalize` в Rust (последний в списке биндингов побеждает; вызывается из `Settings::clamp`, то есть на каждом `set_settings`) и `assignHotkey` во фронте (`lib/hotkey-conflicts.ts`, даёт мгновенный отклик и список `stolenFrom`). Расходиться им нельзя — правила пересечения зеркальны, тест-кейсы совпадают по смыслу. **Новый `kind` обязан появиться в ОБЕИХ реализациях**, и зеркало уже разъезжалось: Rust про семейство цифр знал, `fallsIntoFamily` во фронте — нет, и назначение `send` на ⌘1 не показывало «⌘1 снят у действия „Быстрое действие“», зато `Settings::clamp` снимал этот хоткей на диске молча, задним числом. **Заметка о краже рендерится там, где пользователь ДЕЙСТВОВАЛ, а не там, где жила жертва**: `stolen` несёт и `from`, и `to`, а `StolenNote` фильтрует по группе действия `to` (без пропса `group` не фильтрует вовсе — так её показывают односекционные `WindowSection` и `QuickActionsSection`). Прежний фильтр по группе жертвы молчал ровно в самом частом случае — краже между группами и между вкладками: назначил в «Клавишах» сочетание, снятое у действия из «Окна», — и объяснения не появлялось нигде.

**Миграция.** `hotkeys::migrate_legacy_fields` правит сырой JSON **до** десериализации в `Settings` (`Settings::load`): семь старых полей превращаются в биндинги, значения, совпадающие с дефолтом, не переносятся, сами поля из json убираются. Если `hotkeys` уже непустой — миграция ничего не делает. Поэтому кастомные сочетания пользователя переживают обновление, а `Settings` не тащит легаси-поля.

**Словарь клавиш.** `Shortcut::from_str` (tauri) принимает буквы, цифры, F1–F24, стрелки, `Space`/`Enter`/`Tab`/`Escape`/`Backspace`/`Delete`, `Home`/`End`/`PageUp`/`PageDown`, знаки препинания и нумпад. Раньше узким местом был фронт: `hotkeyFromEvent` умел только буквы, цифры и F-клавиши — теперь он отдаёт `event.code` для всего перечисленного (буквы и цифры нормализуются в короткую форму). **`Escape` остаётся отменой захвата** в `HotkeyCapture`, поэтому назначить его мышью нельзя — он приходит только дефолтом, а вернуть его можно кнопкой сброса строки. Модификаторы принимаются в любом написании из `hotkeys::MODIFIER_ALIASES` (`Cmd`/`Command`/`Super`/`Meta`, `Ctrl`/`Control`, `Alt`/`Option`, `Shift`) — та же таблица, что `MODIFIER_ALIASES` во фронте, и её же читает `platform::modifier_mask`: раньше `Control+S` из старого JSON плагин регистрировал как Ctrl+S, а разбор конфликтов считал голой `S`.

**Горячий путь.** Обработчики `keydown` не разбирают строку сочетания на каждое нажатие: `prepareCombo` вызывается один раз в эффекте (`useWindowControls`, `Teleprompter`, общий `useComboKey`), скролл чата по-прежнему держит `parseModifier` в эффекте (`AnswerPanel`). Стрелки с автоповтором иначе аллоцировали бы массив на каждый кадр.

**Не настраивается намеренно:** `↵` (отправить) и `⇧↵` (перенос строки) в поле ввода — это поведение текстового поля, а не команда приложения; `⌘V`/`Ctrl+V` — событие вставки, а не хоткей. В справочнике HUD они показаны отдельными подсказками — `fieldHints(platform)` в `lib/hotkeys.ts` (была константа `FIELD_HINTS`, стала функцией: подписи платформенные, и группа берётся из реестра, а не литералом).

### HUD рендерится на каждый кадр стрима — границы мемоизации

`partial` стрима — state в `App`, поэтому `App` рендерится на каждый rAF-кадр раскрытия ответа. Чтобы вместе с ним не реконсилировались шапка, композер и док, границы стоят на `AppHeader`, `Composer`, `ChatHistory`, `ChatTabs` и `ToolbarDock` (`memo`), а `App` отдаёт им **срезы, а не API-объекты** (`chats.chats`, `chats.activeId`, `stream.streaming` вместо `chats`/`stream` целиком) и **только стабильные колбэки** (`useCallback`, `useMemo` для `dockItems`/`contextUsage`). Inline-стрелка в пропсах любого из этих компонентов молча снимает мемоизацию — правило проверяется глазами при добавлении пропа. Сам `App.tsx` — композиция хуков и JSX: логика живёт в `hooks/` по одной ответственности (`useSendPipeline`, `useChatActions`, `useUnreadChats`, `useTeleprompterSession`, `useHudSettingsActions`, `useWindowFrame`, `useProjectedContextTokens`, `useSttFeedback`, `usePreviewPanel`), чистая сборка промпта и DTO — в `lib/system-prompt.ts` и `lib/chat-messages.ts`. Ключ сообщения в ленте — `lib/message-keys.messageKey` (WeakMap по объекту сообщения, объекты неизменяемы): индексный ключ переносил локальное состояние блока кода на соседа при удалении.

**Стрим закрываемого чата выбрасывается, а не коммитится**: `useClaudeStream.discard` (в `removeChatWithUndo`) против `stop` (кнопка «Стоп»). `stop` синхронно зовёт `onComplete`, тот дописывает частичный ответ и может открыть превью — для чата, которого через строку уже нет. Гейт «чат уже стримит» — синхронный `isStreaming(chatId)` того же хука, а не state-флаг `streaming`: state отстаёт на рендер, и два вызова `send` в одном тике проходили оба.

**Суфлёр, дойдя до низа, паузу НЕ ставит**: его текст — стримовый `partial`, он растёт, и автопауза на коротком хвосте останавливала суфлёр после каждой догнанной строки. rAF-цикл крутится только пока `playing`. Хоткей `toggle-teleprompter` гейтится тем же, чем поле промпта (оверлей сети, мини-режим, заметки) плюс наличием текста — под оверлеем суфлёр жил бы невидимым и ловил Space/Esc.

`backdrop-filter` в прозрачном frameless-окне не используется (снят с чипа «↓ Вниз» и с оверлея суфлёра): он пересэмплирует подложку на каждом кадре прокрутки или стрима, а при почти сплошной заливке не виден; чипы — непрозрачный `bg-popover` (`FLOATING_CHIP_CLASS` в `IconCluster`).
